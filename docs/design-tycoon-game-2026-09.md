# 설계서 — 뒷마당(backyard): 동물의 숲을 우리 제약으로 줄인 타이쿤

설계일: 2026-09-05. 지시서: `docs/research-game-design-brief.md`.
선행: `docs/research-game-library-2026-09.md`(엔진 조사, Phaser 추천).
병행: `docs/research-sandbox-verify-brief.md`(sandbox 실행 검증, 이 문서 작성 시점에 진행 중).

이 문서는 **무슨 게임을 만들 것인가**를 정한다. 코드는 쓰지 않았다.

## 0. 한 문장

> **작은 마당에 물건을 놓는다. 시간이 지나면 익고, 열어서 거두고, 그것으로 물건을 하나 더 놓는다.
> 칸이 유한하므로 "많이 나오게"와 "예쁘게"가 같은 칸을 두고 다툰다. 그리고 그 마당을 배우자가 본다.**

## 1. 먼저 확인한 것 — 제약은 지시서보다 좁다

지시서의 제약 표 외에, 이 저장소의 기존 코드가 이미 정해 둔 것이 있다. 설계가 여기서 어긋나면
"만들 수 없는 설계"가 된다. 확인한 근거를 함께 적는다.

| 확인한 사실 | 근거 | 설계에 주는 제약 |
|---|---|---|
| 저장은 **가구 단위**다. `member_id`가 유니크 키에 없다 | `packages/database/drizzle/0061_play_states.sql` | 두 사람이 **같은 마당 하나**를 공유한다. 개인 마당은 마이그레이션 없이는 불가 |
| 크기 상한이 **두 겹**이다. API가 `Buffer.byteLength(JSON.stringify(state))`로 먼저 재고, DB가 `pg_column_size(state)`로 다시 잰다. 둘 다 8192 | `apps/api/src/play/play.service.ts`의 `MAX_STATE_BYTES`, `0061_play_states.sql`의 CHECK | **실제로 걸리는 것은 API 쪽 raw JSON 8192B**다(DB보다 먼저 거절한다). 즉 설계 목표는 raw JSON 바이트다 |
| 한 미니앱이 **여러 state_key**를 쓸 수 있고, `GET /v1/play/:appKey`가 전부 준다 | `packages/contracts/src/play.ts` | 8KB는 키마다 걸린다. 커지면 키를 쪼개면 된다(탈출구 있음) |
| 미니앱은 **고정 높이 iframe**이다(기존 미니앱 460~480px) | `miniapp-registry.ts`의 `height`, `miniapp-host.tsx`(b88588a^) | 전체 화면 게임이 아니다. 세로 470px·가로 ~360px 안에서 끝나야 한다 |
| 호스트가 로드 직후 `{kind:'ready', appKey, permissions}`를 보냈다 | `miniapp-host.tsx`(b88588a^)의 `onLoad` | 미니앱이 먼저 물어볼 필요가 없다 |
| 브릿지 계약에 **권한 3종**이 설계돼 있었다(`spend.summary`·`merchant.list`·`category.list`) | `packages/shared/src/miniapp-bridge.ts`(b88588a^, 지금은 삭제) | 지출 데이터를 끌어올 **설계는 존재한다**. 되살릴지, 쓸지는 설계 결정이다(§7) |
| `state.set`에 **revision·ACK가 없었다**. 브릿지 헬퍼는 실패를 삼켰다 | `public/miniapps/bridge.js`(b88588a^, 지금은 삭제)의 `set(...).catch(() => {})` | 재구성할 때 그대로 되살리면 동시 편집은 마지막 쓰기가 이기고 저장 실패가 **조용히** 지나간다 |
| 서버가 **마지막으로 바꾼 사람**을 이미 기록한다(`created_by`를 upsert마다 갱신). 단 응답에 담지 않는다 | `play.service.ts`의 `set: { ..., createdBy: userId }`, `toSummary` | "누가 바꿨나"는 **저장돼 있고 노출만 안 된다**. 필드 하나 열면 된다(§11) |
| iframe은 예고 없이 언마운트될 수 있다 | 호스트가 React 컴포넌트로 iframe을 그린다 | `beforeunload`·`visibilitychange`에 저장을 의존할 수 없다 |

이 중 **아래 두 개가 설계 전체를 결정했다.**

1. **저장이 가구 단위다** → 이 게임은 처음부터 2인 공유 게임이다. 선택이 아니라 구조다.
2. **높이 470px이다** → 이동·탐험·NPC 배회 같은 "돌아다니는" 재미는 물리적으로 들어가지 않는다.
   화면에 들어가는 것은 **한 판(board)** 뿐이다.

## 2. 동물의 숲의 무엇이 재미인가 — 그리고 무엇이 우리 제약에서 살아남는가

동물의 숲은 실패 상태·목표·적이 없는 게임이고([ACNH 개요](https://byte-sized-brainz.humspace.ucla.edu/overview)),
섬 꾸미기에 정답이 없다는 것이 핵심 가치로 소개된다([Cambridge Core, ACNH로 가상 박물관 설계](https://www.cambridge.org/core/journals/public-humanities/article/designing-the-virtual-museum-with-animal-crossing-new-horizons/93606C8166446F088E4B7528694E773B)).
현실 시각과 묶인 것이 매 접속을 다르게 만든다는 것도 함께 지적된다.

네 요소를 **재미의 크기가 아니라 우리 제약에서의 비용**으로 나눠 본다.

| 요소 | 동물의 숲에서의 역할 | 우리 제약에서의 비용 | 판정 |
|---|---|---|---|
| **꾸미기** | 정답 없는 저작. 섬이 "내 것"이 되는 이유 | 격자 + 물건 N종. 저장은 배치 좌표뿐(수십 바이트). **아트 비용이 가장 낮고 재미 밀도가 가장 높다** | **채택 — 중심에 둔다** |
| **수집** | 도감·박물관. 반복에 이유를 준다 | 종류 목록 하나. 저장은 id 배열(종류당 3바이트) | **채택 — 꾸미기의 목표로 붙인다** |
| **시간** | 현실 시각. 매 접속을 다르게 만든다 | 타임스탬프뿐, 공짜. 다만 **죄책감이 딸려 온다**(§4) | **채택하되 방식을 바꾼다** |
| **캐릭터** | 주민. 정서적 접착제. 재미의 정점 | 주민 1명당 도트 여러 장 + 대사 수십 줄 + 이동 AI. **1인이 감당 못 하는 유일한 항목**. 게다가 470px에 배회할 공간이 없다 | **v0에서 제외.** 대신 §6의 "반응"으로 최소 대체 |

**결론: 꾸미기가 중심, 수집이 목표, 시간이 박자, 캐릭터는 나중.**

캐릭터를 빼는 것이 가장 아픈 결정이다. 동물의 숲의 정서 대부분이 거기서 온다. 다만
**빼야 하는 이유가 취향이 아니라 산술**이다 — 주민 4명이면 도트 4×(4방향×2프레임)=32장에 대사 100줄이고,
그것은 v0 일주일 전체보다 크다. 대신 §8에서 도형만으로 "귀여움"을 만드는 가장 싼 네 가지를 적는다.

### 이 제약에 가장 가까운 실제 사례: 네코 아츠메

동물의 숲을 모바일·짧은 세션·작은 화면으로 줄이면 무엇이 되는가에 대해 이미 나온 답이 있다.
네코 아츠메는 실패 상태도 결말도 없고 고양이를 실망시킬 방법이 없으며, 타이머·레벨·실패 요소를
의도적으로 배제한 "무압력" 설계로 소개된다. 동시에 **마당의 칸이 유한해서 물건 배치에 트레이드오프가
생기는 것**이 의미 있는 결정을 만든다고 분석된다.
([Alexia Mandeville, Neko Atsume의 단순함 분해](https://alexiamandeville.medium.com/game-design-breakdown-the-simplicity-of-neko-atsume-a8616a937a47),
[Scott Fine Game Design 분석](http://scottfinegamedesign.com/design-blog/2016/1/23/qlv1gudppy2bh6a4vbjoqyniq1noe0))

우리가 가져오는 것은 **"유한한 마당 + 상실 없음 + 도감"** 이 세 개다. 가져오지 않는 것은
"기다리면 손님이 온다"의 무작위성 — 그것은 아트(손님 종류)에 비례해 비싸다.

### 웹 기반 소규모 사례

선행 조사가 확인한 것을 그대로 쓴다(이 문서에서 다시 검증하지 않았다).

- [Weeds & Wires](https://happybats.itch.io/weeds-and-wires) — Phaser로 만든 카드 배치→생산→수확→판매 농장 시뮬레이션.
  **배치가 곧 생산인 루프**가 웹에서 성립한 사례다.
- [Excali-Farm](https://excaliburjs.com/showcase/) — Excalibur 공식 쇼케이스의 작은 농장 게임.

## 3. 핵심 루프

### 한 세션(30초~3분)

```
열기 → [익은 것을 탭해 거둔다]  5~20초
     → [빈 칸에 물건 하나를 놓는다]  10~40초   ← 여기가 이 게임이다
     → [마당을 한 번 본다]  5초
     → 닫기
```

- **거두기**: 익은 물건 위에 표시가 떠 있다. 탭하면 열매가 늘고 그 물건은 다시 자라기 시작한다.
  탭 3~8번, 애니메이션 짧게. **이 구간을 길게 만들지 않는다** — 반복 노동이 되면 자동수확을 원하게 되고,
  자동수확을 넣으면 열 이유가 사라진다.
- **놓기**: 열매가 충분하면 물건을 산다. **어디에 놓을지가 유일하게 어려운 결정이고, 그래서 이 구간이 게임이다.**
- **보기**: 아무것도 안 하는 5초. 이것을 설계에 넣는 이유는 §6.

### 무엇을 얻고 무엇에 쓰는가

**열매 하나뿐이다.** 화폐를 따로 두지 않는다.

> **가계부 앱 안에서 가짜 돈이 불어나는 화면을 만들지 않는다.**
> "코인 12,400" 같은 숫자가 진짜 잔액 옆에 있으면 두 숫자의 감각이 섞인다. 그 위험을 감수할
> 만큼 화폐가 주는 것이 없다 — 자원이 하나면 개념이 하나 줄고 UI가 한 줄 준다.

### 타이쿤은 어디에 있는가

배치가 곧 생산이다. 물건은 **이웃한 칸의 물건에 따라 다르게 작동한다.**

이것이 이 설계의 중심 트릭이다. 아트 자산을 대량으로 만들 수 없으면 **깊이를 콘텐츠 양이 아니라
조합에서 만들어야 한다.** 물건 3종 + 인접 규칙 1개만으로도 16칸의 배치 공간은 이미 사람이 다
못 따져 보는 크기이고, 물건이 8종이 되면 그림은 8장인데 결정은 훨씬 커진다.

그리고 **꾸미기와 최적화가 같은 행동이 된다.** 예쁘게 놓는 것과 잘 놓는 것이 다른 버튼이면
꾸미기는 부록이 되지만, 같은 칸을 두고 다투면 꾸미기가 진짜 결정이 된다.

## 4. 시간 설계 — 실시간에 묶는다. 단, 익히는 데만 쓰고 썩히는 데는 쓰지 않는다

### 결정

**현실 시각 기준 실시간.** 다만 다음 세 가지를 함께 정한다.

1. **감쇠·소멸이 없다.** 시들지 않고, 잡초가 안 자라고, 아무도 떠나지 않는다.
2. **물건은 한 번 익으면 멈춘다.** 익은 채로 무한정 기다린다. 다시 자라는 것은 거둔 다음이다.
3. **시간 상한을 따로 두지 않는다.** 상한은 **마당의 칸 수가 자연히 만든다**(아래).

### 왜 실시간인가

지시서가 든 두 선택지 중 실시간의 값은 "다시 열 이유"다. 그런데 우리에겐 **재방문 동기가 하나 더 있다 —
배우자가 뭔가 바꿔 놨을 수 있다**(§1의 구조상 저장이 공유된다). 즉 시간에만 의존하지 않아도 된다.

**이것이 죄책감 없는 실시간을 가능하게 하는 근거다.** 재방문 동기의 총량을 시간 하나가 다 짊어질
필요가 없으므로, 시간 압력을 약하게 걸어도 게임이 죽지 않는다.

### 왜 감쇠를 두지 않는가

죄책감은 "시간이 흐른다"에서 오지 않는다. **"안 열어서 잃었다"**에서 온다. 동물의 숲의 오래
비운 마을에는 잡초와 바퀴벌레가 차고, 주민이 몇 달 만이냐고 말하고, 떠날 채비를 한다. 실제로
"죄책감이 견디기 어려워 삭제할 뻔했다"는 복귀담이 기록돼 있다
([Kotaku](https://kotaku.com/what-happens-when-you-abandon-your-animal-crossing-new-1844574997),
[Paste Magazine](https://pastemagazine.com/games/animal-crossing/animal-crossing-abandonment)).

우리 사용자는 2명이고 그중 한 명은 이걸 만든 사람이다. 지표를 올릴 이유가 없고, 리텐션 압박이
없다. **압박 장치를 넣을 이유가 애초에 없는데 넣으면, 남는 것은 죄책감뿐이다.**

게다가 이건 가계부 앱이다. 이 앱은 이미 사용자에게 "얼마 썼다"를 보여준다. 같은 앱 안에서
"마당도 방치했다"를 더하면, 앱을 여는 것 자체가 무거워진다.

### 왜 그래도 "익으면 멈추게" 하는가 — 그리고 그 대가

무한 축적을 허용하면 두 가지가 깨진다.

- 오래 안 열수록 유리해진다 → **여는 이유가 사라진다**(3주 뒤에 열면 3주치가 한 번에 온다).
- 진행이 한 번에 소진된다 → 그 뒤로 할 게 없다.

그래서 각 물건이 **자기 것 하나를 들고 기다린다.** 3주 만에 열어도 손해가 아니다("꽉 차 있다"),
자주 열면 총량이 더 크다.

**솔직하게: 이것도 아주 약한 압력이다.** 아이들 게임의 오프라인 상한은 대개 "놓친 기회감을 만들어
복귀를 유도"하려고 설계된다([The Mind Studios, 아이들 게임 설계 관행](https://games.themindstudios.com/post/idle-clicker-game-design-and-monetization/)).
우리는 그 목적으로 쓰는 게 아니지만 **효과는 일부 같다**는 것을 인정한다. 다만 차이가 있다.

> **잃는 것이 "가지고 있던 것"이 아니라 "가진 적 없는 것"이다.**
> 잡초는 내 마당을 망가뜨리지만, 안 열어서 못 받은 열매는 원래 없던 것이다.
> 이 선을 넘는 기능(시들기·연속 접속 보너스·놓치면 사라지는 손님)은 넣지 않는다.

**상한이 마당에서 나온다는 점이 이 설계에서 가장 잘 맞물리는 부분이다.** 생산 칸이 8개면 오프라인
축적 상한이 8이고, 마당을 넓히면 상한이 오른다. 즉 **성장이 곧 상한 해제**이고, 어디에도 임의의
"12시간" 같은 숫자를 적지 않는다.

### 하루 리듬 — v0에는 넣지 않는다

동물의 숲의 "오늘은 다르다"에 해당하는 것(하루 한 번의 씨앗·손님)은 30초 세션을 정당화하는
좋은 장치지만, **놓치면 사라지는 성질이 위 원칙과 가장 가까이 닿아 있다.** v0.1로 미루고,
넣을 때는 "놓쳐도 다음 날 같은 등급의 다른 것이 온다"로 만든다.

### 단말 시계 — 서버 권위 시각이 없다

서버 로직이 없으므로 시각은 단말 것이다. 대응은 **치팅 방지가 아니라 깨지지 않기**가 목표다
(사용자 2명이고 그중 한 명이 개발자다. 시계를 돌려 이기는 것에 방어할 가치가 없다).

| 상황 | 처리 |
|---|---|
| 시계가 뒤로 감(시간대 이동·DST·수동 조정) | 저장된 `t`(마지막 저장 시각)보다 `now`가 작으면 **경과를 0으로 본다.** `readyAt`을 다시 쓰지 않는다 |
| 시계가 앞으로 감 | 익은 것이 익었을 뿐이다. 물건마다 1개 상한이 이미 이득을 막는다 |
| 아주 오래 비움 | 전부 익어 있다. 정상 경로다 |

**무료로 얻을 수 있는 서버 시각 앵커가 하나 있다.** `play_states.updated_at`은 서버가 찍고
`GET /v1/play/:appKey`가 이미 `updatedAt`으로 돌려준다. 다만 브릿지 `state.get`은 `{ state }`만
전달한다. **호스트가 `{ state, updatedAt }`으로 한 필드만 더 넘기면** 미니앱이 "마지막 저장의
서버 시각"을 알 수 있다. v0에 필수는 아니지만 값이 크고 비용이 작은 호스트 확장 요청으로 §11에 남긴다.

### 알림은 붙이지 않는다

앱에 FCM이 이미 있지만 게임 알림은 만들지 않는다.

- **잃는 것이 없으므로 "지금 열어야 한다"가 없다.** 알릴 내용 자체가 없다.
- 가계부 알림(예산·거절·정체)의 신뢰도를 게임 알림이 갉아먹는다. 알림 하나가 무시되기 시작하면
  옆의 알림도 함께 무시된다.

대신 **호스트 화면의 뱃지**만 쓴다(미니앱 목록에 "거둘 것 3"). 열었을 때 보이는 것이고 밀어 넣지 않는다.
호스트가 뱃지를 그리려면 상태를 읽어 해석해야 하는데, `play_states`는 뜻을 모르는 저장소다 —
그래서 뱃지는 **미니앱이 저장할 때 `badge` 숫자 하나를 상태에 같이 적어 두고 호스트가 그 필드만 읽는**
방식이 맞다(§11).

## 5. 성장과 목표 — 끝이 있다

### 쌓이는 것

| 축 | 내용 | 어디서 보이나 |
|---|---|---|
| 열매 | 유일한 자원 | HUD 한 줄 |
| 배치 | 마당에 놓인 물건 | 화면 그 자체 |
| 도감 | 지금까지 만들어 본 종류 | 도감 화면(v0.2) |
| 칸 | 마당 크기(4×4 → 6×6 → …) | 화면 그 자체 |

### 해금

물건은 **순차 해금**한다. 도감을 채운 종류 수가 다음 종류를 연다. 무작위 뽑기를 쓰지 않는다 —
뽑기는 다음에 뭐가 나올지 모른다는 긴장을 주지만, **자원이 하나뿐인 게임에서는 그냥 지연일 뿐이고**
저장에 뽑기 이력이라는 필드가 하나 더 는다.

### 끝

**끝을 만든다.** "마당을 다 채우고 도감을 다 채우면 완료"다.

끝이 없다고 선언하지 않는 이유:

1. **1인이 무한 콘텐츠를 공급할 수 없다.** 끝없다고 해 두면 결국 반복이 드러나고, 그때 그만두는
   것이 "질려서 관둔 것"이 된다. 명시적인 완료 지점이 있으면 **그만두는 것이 성취가 된다.**
2. 사용자가 2명이고 랭킹이 없으므로 붙잡아 둘 이유가 없다. 붙잡는 설계는 지표를 위한 것이다.
3. 끝이 있으면 **범위를 잘라도 된다.** 무한 성장 곡선은 밸런스가 영원히 끝나지 않는다.

완료 후에는 마당이 그대로 남는다(계속 재배치하며 놀 수 있다). 다음 시즌은 **선택**으로 둔다 —
"마당을 도감에 사진으로 넣고 비우고 다시" 는 v1.0 이후이며, 스냅샷 크기 때문에 저장 예산을
다시 계산해야 한다(§7의 한계선).

### 목표 소요

v0 완주 목표는 **하루 2~3회 접속 기준 7~10일**이다. 이것이 "일주일 안에 만드는 것"과 맞는
크기다. 실제 수치는 §9의 초기값 표에 두고, **플레이해 보고 고친다**(현재 값은 검증된 밸런스가 아니다).

## 6. 두 사람 — 랭킹이 아니라 관객

지시서는 "사용자 2명, 랭킹·경쟁·소셜은 의미 없다"고 했다. 동의한다. 다만 구분한다.

- **의미 없는 것**: 순위표, 친구 추가, 자랑하기, 대전. 2명 사이에 순위는 코미디다.
- **이미 존재하고 공짜인 것**: 저장이 가구 단위라 **두 사람이 같은 마당을 본다**(§1).

꾸미기가 재미인 이유는 세 가지다 — (a) 선택이 보이고 (b) 그 선택이 내 것이고 (c) **누군가 본다.**
(c)가 없으면 꾸미기는 금방 시든다. 동물의 숲에서 그 역할을 하는 것이 섬 방문이고, 우리는
그것을 **구조상 이미 가지고 있다.** 안 쓸 이유가 없다.

그래서 v0의 협력 방식은 이렇다.

- **한 마당, 공동 소유.** 누가 놓았는지 기록하지 않는다.
- 왜 기록하지 않나: **미니앱이 지금 누가 플레이 중인지 알 방법이 없다.** `host.info`는 브릿지
  버전과 미니앱 키만 준다. 본인이 직접 고르게 하면(로그인 없는 자기 신고) 틀릴 수 있고, 틀린
  소유권 표시는 없느니만 못하다.
- **다만 서버는 이미 알고 있다.** `play.service.ts`가 upsert마다 `created_by`를 갱신하므로
  "마지막으로 바꾼 사람"이 저장돼 있다. 응답에 담기지만 않았을 뿐이라 **필드 하나 여는 것으로
  "○○이 다녀갔어요"가 된다**(§11의 요청 3). 물건마다의 소유권은 여전히 저장하지 않는다 —
  배치 튜플에 사람 id를 넣으면 크기가 늘고, 공동 마당에서 칸별 소유권은 협력을 경쟁으로 바꾼다.
- 대신 **결과가 보인다.** 다음에 열었을 때 마당이 달라져 있다. v0는 그것으로 충분하다.

### 동시 편집 — 알고 감수한다

`state.set`에 revision도 ACK도 없다. 두 사람이 동시에 열면 **마지막 저장이 이긴다.**

- A가 로드(rev 5) → B가 로드(rev 5) → A 저장 → B 저장 → **A의 작업이 사라진다.**
- 세션이 30초~3분이고 사람이 2명이므로 자주 일어나지는 않는다. 하지만 나란히 앉아 있으면 일어난다.

v0는 감수한다. v0.3의 완화안(둘 다 싸다):

1. **저장 시각 비교**: 로드할 때 받은 `t`를 기억했다가, 저장 직전에 `state.get`을 한 번 더 해서
   `t`가 달라졌으면 "다른 곳에서 바뀌었어요 — 새로고침" 을 띄우고 덮지 않는다. 왕복 한 번이 비용이다.
2. **자리 표시(lease)**: 별도 키 `presence`에 열 때 시각 하나를 쓴다. 2분 안의 값이 있으면
   "지금 마당에 누가 있어요 — 보기만 할게요"로 읽기 전용 전환. 키 하나·PUT 하나가 비용이다.

**두 완화안 모두 v0 밖이다.** v0에서 이걸 만들면 일주일에 루프를 못 만든다.

## 7. 저장 모델

### 형식 — 객체 배열이 아니라 튜플 문자열

`app_key: "backyard"`, `state_key: "garden"` 하나로 시작한다.

```json
{
  "v": 1,
  "t": 1757046000,
  "s": 4821,
  "f": 137,
  "n": 9,
  "k": ["p", "w", "c"],
  "p": ["p:0:1757049600", "p:1:1757052000", "w:9", "c:11"]
}
```

| 필드 | 뜻 | 형 | 왜 필요한가 |
|---|---|---|---|
| `v` | 스키마 버전 | int | 모양이 바뀌었을 때 **조용히 오작동하지 말고 거절**하기 위해 |
| `t` | 마지막 저장 시각(epoch sec) | int | 시계 역행 감지(§4), 동시 편집 감지(v0.3) |
| `s` | 마당 난수 시드 | int | 장식 변주(풀 방향·타일 얼룩)를 **저장하지 않고 재현**하기 위해 |
| `f` | 열매 수량 | int | 유일한 자원 |
| `n` | 지금까지 구매한 화분 수 | int | 가격 계산용. 배치에서 유도하지 않는 이유: **회수해도 가격은 안 내려간다**(무한 재구매 방지) |
| `k` | 해금된 종류 | string[] | 도감 겸 상점 목록 |
| `p` | 배치 | string[] | `"종류:칸인덱스[:익는시각]"`. 생산물이 아니면 시각을 생략한다 |

**엔진 객체를 넣지 않는다.** Sprite·Tween·Scene·이벤트 핸들러·텍스처는 로드할 때 이 데이터에서
다시 만든다. 저장에 들어가는 것은 **종류 id, 칸 번호, 시각, 수량, 해금 목록**뿐이다.

### 왜 `{"type":"p","cell":0,"readyAt":...}`이 아닌가

jsonb는 객체마다 키 문자열을 **매번** 저장한다. 배열 요소 하나당:

| 인코딩 | 요소 1개(raw, 쉼표 포함) | 16칸 | 144칸 | 8192B에 닿는 배치 수 |
|---|---:|---:|---:|---:|
| 객체 `{"t":"p","i":0,"r":1757049600}` | ~31B | ~560B | ~4.5KB | **약 260개** |
| 튜플 문자열 `"p:0:1757049600"` | 17B | ~330B | ~2.5KB | **약 480개** |

객체 쪽이 두 배 가까이 비싼 이유는 **키 문자열(`"t"`·`"i"`·`"r"`)이 요소마다 다시 실린다**는 것이다.
jsonb 저장에서도 같은 현상이 있지만, 실제로 걸리는 상한은 API의 raw JSON 검사이므로 위 표는 raw 기준이다.

**대가**: 문자열 튜플은 사람이 읽기 어렵고 파싱 실수가 난다. 완화는 하나뿐이다 —
**직렬화/역직렬화를 함수 한 쌍에 가두고 라운드트립 테스트로 고정한다.** 이 저장소가
`game-snake.ts` + `game-snake.test.ts`로 순수 로직을 고정했던 것과 같은 패턴이다(그 파일들은 b88588a에서 함께 삭제됐다. 패턴만 가져온다).

### 크기 계산

v0 최대 상태(4×4=16칸 전부 채움, 생산 9 + 나머지 7):

| 부분 | raw |
|---|---:|
| 스칼라 6개(`v`·`t`·`s`·`f`·`n` + 괄호) | ~45B |
| `k` (3종) | ~18B |
| `p` 생산 9개 × 17B | ~153B |
| `p` 비생산 7개 × 7B | ~49B |
| **합계 raw** | **~265B** |

API가 재는 것과 같은 기준(raw JSON UTF-8)으로 8192B의 **약 3%**. 확장했을 때:

| 마당 | 배치 수 | raw JSON | 8192B 대비 |
|---|---:|---:|---:|
| 4×4 (v0) | 16 | ~265B | 3% |
| 6×6 (v0.2) | 36 | ~640B | 8% |
| 12×12 | 144 | ~2.5KB | 30% |
| **한계선** | **~480** | **~8.2KB** | **100%** |

**결론: 저장은 이 게임의 제약이 아니다.** 22×22 마당까지 감당한다. 이 게임의 크기를 정하는 것은
8KB가 아니라 **470px 화면**이다. 그리고 그전에 키를 쪼갤 수 있다(`garden` / `codex` / `presence`) —
상한은 키마다 따로 걸리고 키 개수 제한은 없다(`play.service.ts`에 없다).

DB의 `pg_column_size(jsonb)`는 이 크기대에서 raw와 비슷하거나(작은 값은 압축되지 않는다) 더 작다
(2KB를 넘으면 압축될 수 있다). **API가 항상 먼저 거절하므로 raw JSON 바이트만 관리하면 된다.**
실제 값은 만든 뒤 한 번 재 보고 이 표를 고친다.

### 저장 시점과 실패 처리

**규칙: 확정된 행동 직후에 즉시 저장한다.** 그 외의 시점을 신뢰하지 않는다.

| 시점 | 저장 |
|---|---|
| 물건 배치 확정 · 이동 · 회수 | **즉시** |
| 구매 · 수확 · 해금 | **즉시** |
| 드래그/애니메이션 중간 프레임 | 안 함 |
| `visibilitychange` 숨김 | 보조로만(미저장 변경이 남아 있을 때) |
| iframe 언마운트 | **의존하지 않는다.** 호스트가 컴포넌트를 지우면 이벤트가 안 온다 |

실패 처리 — **기존 `bridge.js`의 `state.set(...).catch(() => {})`를 그대로 쓰지 않는다.**
최고 점수는 삼켜도 되지만 배치는 아니다.

| 상황 | 처리 |
|---|---|
| 저장 실패(`host_error`·`timeout`) | HUD 구석에 "저장 안 됨" 표시 + 지수 백오프 재시도. **다음 행동 때 최신 스냅샷 전체를 다시 보낸다** |
| **로드 실패** | **새 게임을 시작하지 않는다.** "불러오지 못했어요 · 다시" 화면에서 멈춘다 |
| 로드 결과가 `null` | 진짜 신규다. 초기 상태를 만든다 |
| 알 수 없는 `v` | 거절하고 "앱을 업데이트해 주세요". **덮어쓰지 않는다** |
| 파싱 실패(깨진 튜플) | 해당 요소만 버리고 나머지는 살린다. 전체를 버리지 않는다 |

> **가장 위험한 버그는 "로드 실패를 신규 사용자로 착각해 빈 마당을 저장하는 것"이다.**
> 브릿지 타임아웃이 8초이고 호스트가 늦게 뜨는 경우가 실제로 있으므로, 이 분기는 코드에서
> 눈에 띄게 분리하고 테스트로 고정한다.

### 지출 데이터를 쓰지 않는 이유 — 권한 0개로 간다

삭제된 브릿지 계약에 `spend.summary`·`merchant.list`·`category.list`가 있었고, 되살려 등록부에 한 줄만 적으면
켤 수 있다. 그래도 **v0는 권한 0개다.**

- **어떤 매핑이든 인센티브가 뒤집힌다.** 많이 쓰면 자원이 늘게 하면 낭비를 보상하는 게임이 되고,
  적게 쓰면 늘게 하면 **필요한 지출까지 죄책감**이 된다. 가계부에서 이건 가장 비싼 실수다.
- **게임이 데이터 유입에 종속된다.** 카드 문자가 안 들어온 날은 게임도 멈춘다. 게임의 재미가
  파서 상태에 묶이면 둘 다 디버깅하기 어려워진다.
- v0 범위가 커진다. 권한·로딩·실패 경로가 전부 늘어난다.

**나중에 붙인다면 방향은 지출이 아니라 행동이다.** 미분류 거래를 정리하거나 확인하는 것처럼
**사용자가 어차피 해야 하는 잡일**에 보상을 붙이면, 인센티브가 뒤집히지 않는다(쓰는 걸 권하지 않는다).
남는 위험은 "보상 때문에 대충 분류한다"이고, 이건 보상을 작게 두면 완화된다. 다만 지금 필요한
브릿지 메서드가 없다(미분류 건수·확인 행동). §11에 남긴다.

## 8. 아트 범위 — 전부 코드로 그린다

### 결정: 캔버스 도형. 이미지 파일 0개

세 가지 이유가 겹친다.

1. **sandbox에서 이미지 로딩이 되는지 아직 모른다.** 병행 검증(`research-sandbox-verify-brief.md`)이
   진행 중이고, `allow-same-origin` 없는 불투명 출처에서 PNG 로딩이 막힐 가능성이 선행 조사의
   1순위 위험으로 지목됐다. **아트 파이프라인을 이미지에 걸었다가 막히면 v0를 통째로 다시 만든다.**
   도형만 쓰면 v0는 그 검증 결과를 **기다리지 않아도 된다.** 이것이 세 이유 중 가장 중요하다.
2. 1인이 도트 12장을 그리는 시간 > 도형 12개를 조립하는 시간.
3. 도형은 색·크기가 **파라미터**다. 계절 팔레트, 성장 3단계, 선택 하이라이트가 전부 공짜다.
   도트였다면 그림이 3배가 된다.

### v0에 필요한 그림 전부

| # | 무엇 | 상태 수 | 대략 |
|---|---|---:|---|
| 1 | 바닥 타일 | 2톤 | 사각형 + 미세한 색차 체크 |
| 2 | 화분 | 3(빈·자람·익음) | 사다리꼴 + 잎 2~3개 + 열매 원 |
| 3 | 우물 | 1 | 원기둥 + 지붕 삼각 + 물 원 |
| 4 | 의자 | 1 | 사각 3개 |
| 5 | 열매 아이콘 | 1 | 원 + 잎 |
| 6 | 선택 커서 | 1 | 점선 테두리 |
| 7 | 배치 가능/불가 | 2 | 반투명 초록/빨강 채움 |

**그림 7종 · 상태 포함 11개.** 각각 도형 5~15개. 1인 하루 안에 들어간다.

### 도형을 캐릭터처럼 보이게 하는 가장 싼 네 가지

도형만 쓰면 "귀엽지 않다"가 진짜 위험이다. 동물의 숲의 정서 대부분이 캐릭터에서 오는데
그걸 뺐기 때문이다. 비용 대비 효과가 가장 큰 순서로 넷만 한다.

1. **팔레트를 6~8색으로 고정한다.** 색이 적을수록 일관돼 보인다. 아무 색이나 쓰는 도형이
   가장 싸구려로 보인다.
2. **모서리를 둥글게(3~5px).** 한 줄 바꾸는 것으로 인상이 가장 크게 바뀐다.
3. **그림자 한 겹.** 물건 아래 반투명 타원 하나. 물건이 "놓여 있다"고 느끼게 만든다.
4. **idle bob.** 익은 물건만 위아래 2px, 1.4초 주기로 흔든다. 살아 있다는 신호이자
   **"거둘 것이 여기 있다"는 안내를 겸한다**(별도 아이콘이 필요 없다).

### 텍스트와 HUD는 canvas가 아니라 HTML로

iframe 안의 DOM은 자유롭게 쓸 수 있다. canvas 위에 HTML을 겹친다.

- **한글 폰트가 공짜다.** 시스템 폰트를 쓰면 웹폰트 로딩(역시 불투명 출처에서 막힐 수 있다)이 없다.
- 터치 타겟 크기·접근성·레이아웃을 브라우저가 해 준다. canvas 버튼은 전부 직접 만들어야 한다.
- 게임 엔진의 텍스트 렌더링(비트맵 폰트 생성 등)을 아예 안 써도 된다.

canvas는 **마당만** 그린다.

### 시점: 아이소메트릭이 아니라 정면 격자

선행 조사가 iso를 언급했지만 v0는 **탑다운 2D 격자**다.

- iso는 좌표 변환·깊이 정렬·터치 히트 판정이 전부 추가 작업이고, 그 셋 다 틀리기 쉽다.
- **470px 높이에서 iso 격자는 같은 칸 수에 세로를 더 먹는다.**
- 예쁨은 나중에 살 수 있다. **논리 좌표를 행/열로 유지하면 전환 비용이 렌더러에만 남는다.**

## 9. v0 — 일주일 안에 만드는 가장 작은 것

### 넣는 것

### 만드는 순서 (일주일)

**전제: 호스트 런타임 복원이 끝나 있다(§0-1, 0.5~1일). 그것까지 포함하면 8일이다.**

| 일 | 무엇 | 끝났다는 기준 |
|---|---|---|
| 1 | **순수 규칙 모듈** — 격자·배치 검증·인접 계산·가격·시각 → 열매. 엔진 없음 | vitest로 라운드트립·경계·시계 역행 고정 |
| 2 | **저장 계약** — 직렬화/역직렬화 + 로드 실패 분기 | 라운드트립 테스트 통과, 8KB 실측 |

| 4 | 탭 입력 — 선택 → 배치 → 회수, 하이라이트 | 규칙 모듈만 호출해서 동작한다 |
| 5 | 브릿지 연결 — 로드/저장, 실패 표시 | 닫았다 열어도 유지된다 |
| 6 | HTML HUD — 열매·상점·완료 화면, idle bob | 손으로 만졌을 때 게임처럼 보인다 |

**1·2일이 엔진 없이 진행되는 것이 의도다.** 규칙이 렌더러와 분리돼 있으면 sandbox 검증이
Phaser를 탈락시켜도 3일차부터만 다시 만든다.

### v0가 성공했다고 어떻게 판단하나

일주일 뒤 이 셋을 본다. 재미있을 것이라고 미리 단정하지 않는다.

1. **닫았다 다시 열게 되는가** — 알림 없이, 하루에 두 번 이상.
2. **놓을 자리를 고민하는가** — 빈 칸에 아무 데나 놓고 닫으면 §3의 전제가 틀린 것이다.
   그러면 인접 규칙을 강하게 하거나(칸 사이 차이를 키운다) 칸을 더 줄여야 한다.
3. **배우자가 바꿔 놓은 것을 알아채는가** — 못 알아채면 §6의 재방문 동기가 없는 것이고,
   그러면 시간 압력을 조금 올려야 한다(v0.1의 하루 한 번을 앞당긴다).

## 11. 이 설계가 호스트에 요청하는 것

전부 v0 필수는 아니다. 비용이 작고 값이 큰 순서.

| # | 요청 | 비용 | 값 | v0 필수 |
|---|---|---|---|---|
| 1 | `state.get` 응답에 `updatedAt` 추가(`{ state, updatedAt }`) | 필드 1개 | **서버 권위 시각 앵커**(§4)와 동시 편집 감지(§6)가 공짜로 생긴다 | 아니오(강력 권장) |
| 2 | 미니앱 목록에 **뱃지** 표시 — 상태의 `badge` 숫자만 읽는다 | 호스트 UI 소폭 | 알림 없이 "거둘 것이 있다"를 전달(§4) | 아니오 |
| 3 | `GET /v1/play/:appKey` 응답에 **`lastChangedBy`**(= `created_by`) 추가 → 브릿지로 전달 | 필드 1개. **값은 이미 DB에 있다**(§1) | "마지막으로 바꾼 사람"을 표시(§6). 새로 저장할 것이 없다 | 아니오 |
| 3-b | `host.info`에 `memberId` 추가 | 필드 1개 | 지금 **플레이 중인** 사람을 알 수 있다. 3만으로는 과거만 안다 | 아니오 |
| 4 | **호스트 런타임 복원** + 등록부에 `backyard` 한 줄(`height` 470) | 0.5~1일(§0-1) | 실행 자체 | **예** |
| 5 | 미분류 건수·확인 행동용 브릿지 메서드 | 신규 권한 | "잡일 연동"(§10) | 아니오 |

**요청 1이 없어도 v0는 돈다.** 단말 시계 역행은 `t` 비교로 막고, 앞으로 간 시계는 물건당 1개
상한이 막는다(§4).

## 12. 엔진 — 선행 조사의 추천을 어떻게 쓰는가

정직하게: **v0가 요구하는 것은 격자 그리기 · 탭 히트테스트 · 짧은 tween 셋뿐이고, 이건 Phaser
344 KiB(gzip)가 필요한 일이 아니다.** 그렇다고 v0를 순수 canvas로 만들면 v0.2 이후(스프라이트·씬·
아이소메트릭)에 전부 옮겨야 한다.

그래서 이렇게 가른다.

- **게임 규칙(격자·인접·경제·시각·직렬화)은 엔진과 분리된 순수 JS 모듈**에 둔다.
  이 저장소가 `game-snake.ts` + 테스트로 썼던 패턴이다(b88588a에서 삭제됨).
- **렌더러만 Phaser로 붙인다.** 선행 조사의 추천을 따르되, 병행 검증에서 Phaser가 sandbox에서
  막히면 **3일차 이후만 다시 만든다.**
- 자산은 전부 코드 생성이므로(§8) 검증 항목 중 "이미지 로딩"이 실패해도 v0는 영향받지 않는다.

**v0 착수 전에 확인해야 하는 것은 하나뿐이다: `<script src>`로 엔진 UMD가 불투명 출처 iframe에서
뜨는가.** 그것만 되면 v0는 다른 검증 결과를 기다리지 않는다.

- **밸런스 수치는 검증되지 않았다.** §9의 표는 초기값이며 플레이 없이 정한 것이다. 상수 한곳에 모으고
  일주일 뒤 고치는 것을 전제로 한다.
- **저장 크기는 추정이다.** §7의 바이트 수는 손으로 센 값이며 실제 직렬화 결과로 재지 않았다.
  만든 뒤 한 번 재고 표를 고친다. 다만 기준(API의 raw JSON 8192B)은 코드에서 확인했다.
- **sandbox 실행은 이후 검증됐다(2026-09-06).** 이 문서 작성 시점에는 확인 못 함이었다. [검증 결과](verify-sandbox-engine-2026-09.md)는 Phaser 부팅·인라인 PNG·캔버스 텍스처·postMessage 왕복을 통과로, **동봉 PNG와 JSON의 상대경로 로딩을 CORS 실패로** 기록했다. 즉 §8의 "아트 이미지 0개" 결정은 편의가 아니라 **현재 실행 조건에서 강제되는 것**이다. Capacitor 실기기는 여전히 확인 못 함이다.
- **"재미있다"를 확인하지 않았다.** 이 문서는 왜 그렇게 판단했는지의 근거만 적었고, §9의 마지막 절에
  틀렸을 때 무엇을 보고 알 수 있는지를 함께 적었다.
- 네코 아츠메·동물의 숲에 대한 서술은 인용한 공개 분석·기사에 근거하며, 직접 플레이 검증은 하지 않았다.
