# 뒷마당 재설계 — 내가 서 있고, 화면 밖으로 걸어가는 장소

작성일: 2026-09-06. 상태: 설계 완료, 제품 구현·배포 없음. 기준 커밋: `7739f6b1b9b23f6ae8fe758e72c68ffba8ce8b91`.

**32×24타일(1타일 32월드픽셀, 1024×768)의 연결된 마당에서 캐릭터를 직접 움직인다. iframe은 기본·최대 520 CSS px로 바꾸되 호스트의 실제 남은 높이에 맞춘다. Phaser 4.2.1 고정 UMD를 채택하고, 주민 3명·채집 8종·물고기 8종·공동 도감까지 12개 하루 슬라이스로 만든다.**

## 2. 세계와 카메라 — ADR 1

### 실제 호스트 화면 확인

기존 `docs/evidence/backyard-s6/layout-360.png`를 직접 보았다. 이것은 360×470 iframe만의 캡처다. `scripts/verify-backyard/export.mjs`도 부모 viewport 430×900에서 iframe 폭만 바꿨으므로, 이 증거로 작은 휴대폰 전체 화면 적합성을 주장할 수 없다.

이번에는 해당 스크립트의 **기존 정적 export 서버·인증/API 메모리 fixture 부분만 메모리에서 실행**하여 실제 `/play/app/?key=backyard`를 열었다. 파일·제품 코드·운영 API를 변경하지 않고 부모 viewport 자체를 바꿔 DOM 사각형을 측정했다. Aside의 `aside guide`는 가이드 대신 일반 대화 응답을 반환하여 사용할 수 없었고, 저장소 검증에서 사용하던 Playwright로 확인했다. 실기기·safe-area가 있는 WebView는 **확인 못 함**이다.

| 부모 CSS viewport | iframe 실제 x/y/폭/높이 | 하단 탭 시작 y | 근거 |
|---|---|---|---|
| 320×568 | 16 / 153 / 288 / 470 | 487 | 이번 로컬 export Chromium DOM 실측, safe-area 0 |
| 360×780 | 16 / 153 / 328 / 470 | 699 | 동일 |
| 430×900 | 16 / 153 / 398 / 470 | 819 | 동일 |

모든 관측에서 상단 헤더는 57px였다. 320×568에서는 iframe 아래쪽이 탭 뒤로 들어간다. 따라서 높이를 520으로 일괄 교체하기만 하는 구현은 허용하지 않는다.

예컨대 360×780에서는 내부 약 326×378px가 세계 창이다. 대략 10×12타일만 보이고 세계 전체는 32×24타일이다. 320×568에서는 약 286×176px, 즉 약 9×5.5타일이어도 동일한 세계를 걷는다. 작은 뷰포트를 이유로 지도를 축소하지 않는다.

H가 300px 미만이면 게임 페이지의 제목 부제를 접고 본문 상단 여백을 줄여 다시 측정한다. 그래도 부족하면 세계 시뮬레이션을 일시정지하고 HTML “세로로 돌려서 계속하기” 화면을 표시한다. 이 상태에서 입력이 계속되거나 게임 일부가 탭 뒤에서 동작하지 않는다. 가로 화면·화면 키보드·글자 확대에서의 정확한 높이는 **확인 못 함**이고 슬라이스 2·12에서 검증한다. 일반 페이지 전체의 헤더·탭을 제거하지 않으며 호스트 바깥 영역의 스크롤은 유지한다.

### 지도의 장소와 첫 산책

열·행은 0부터 센다. 지도 경계는 울타리·수풀로 보이고, 격자선은 평소 숨긴다. 장소명은 위치에 따른 작은 HTML 문구이며 씬 전환 없이 연속 이동한다.

- **집 앞 마당:** 열 2~12, 행 13~21. 시작 발 위치 (7,18), 작은 집 출입문과 기존 꾸미기 물건이 있다. 집 안 진입은 이번 범위가 아니다.
- **나무 그늘:** 열 2~14, 행 2~11. 열매·벌레·나무 담당 주민이 있다. 나무 줄기만 충돌하고 수관 뒤로 걸으면 캐릭터보다 앞에 그려진다.
- **연못:** 열 20~29, 행 4~12가 물, 서쪽 둑 열 18~19에 낚시점 3곳. 물 위로는 걸을 수 없고, 물고기 그림자·물결이 방문을 유도한다.
- **오솔길:** 시작→열 16의 남북 길→연못 서쪽 둑→북쪽 그늘로 잇고, 최소 2타일 폭을 유지한다. 고정 길·집 입구·낚시점에는 물건을 놓을 수 없다.

처음에는 북쪽 길이 화면 위로 이어지고 나무 수관 일부만 보인다. 3~5초 걸으면 집이 화면 아래로 사라지고 주민이 나타난다. 주민의 “동쪽 물가에 잔물결이 보이더라”를 듣고 걸어가면 화면 밖에 있던 연못이 보인다. 첫 60~90초에 걷기→인사→채집 하나 또는 낚시 한 번→도감 기록이 가능하도록 배치한다. 이는 **사용성 목표이며 확인된 재미가 아니다**.

지도는 일반 JS 정적 데이터로 동봉하며 타일맵 JSON을 fetch하지 않는다. 저장에는 고정 지형 전체가 아니라 지도 버전·시드·사용자가 바꾼 배치만 넣는다. 미니맵은 이번에 넣지 않는다. 세 랜드마크와 이어진 길로 방향을 익히는 것이 먼저이며, 주요 일곱 기능은 줄이지 않는다.

## 3. 캐릭터와 이동 — ADR 2

**기본 입력은 하단 왼쪽의 고정 가상 패드, 오른쪽의 문맥 행동 버튼이다.** 키보드는 방향키/WASD와 Enter/Space를 지원한다. 모바일에서 화면의 먼 물건을 탭해 즉시 얻는 입력은 없다.

| 후보 | 장점과 실제 비용 | 판정·근거 |
|---|---|---|
| 탭 이동 | 한 손 입력이 쉽지만 목적지 표시·길찾기·도착 취소·움직이는 NPC·물 너머 오탭 처리 필요. 470px급 화면에서는 작은 벌레 탭과 이동 목적지가 경쟁 | **추론:** 이번 기본 조작에서 제외. 패드 검증이 실패할 때 같은 슬라이스 안에서 비교 프로토타입 |
| 고정 가상 패드 | 방향을 직접 바꾸는 감각, 길찾기 불필요. 손가락 공간·pointer capture·부모 스크롤 충돌 처리는 필요 | **추론:** 80×80px 패드를 별도 96px 조작대에 넣어 채택 |
| 둘 다 | 취향 대응 가능하지만 제스처 우선순위·두 설명·회귀 경우 증가 | **추론:** 첫 출하에는 제외. 콘텐츠 범위를 줄이는 결정이 아니라 중복 조작 방식의 선택 |

패드 반경 40px, dead zone 8px, 속도 96 월드px/s(3타일/s), 8방향으로 방향을 양자화한다. 대각선 벡터는 정규화해 직선보다 빨라지지 않는다. 패드에서 시작한 pointer만 이동에 쓰고, 두 번째 손가락은 행동 버튼에 사용할 수 있다. `pointerup`·`pointercancel`·capture 상실·blur·숨김·대화 열림 때 입력을 0으로 만든다. 패드 영역은 `touch-action: none`, HTML 도감 스크롤은 세로 스크롤을 허용한다. 부모 PullToRefresh가 패드 드래그에 반응하지 않는지 실기기로 확인한다.

캐릭터는 머리 원, 몸통 둥근 사각형, 발 타원, 머리카락·모자로 만든다. 발 접점을 위치 기준으로 삼는다. **8방향 외형×걷기 4프레임+방향별 정지 1프레임**, 총 40포즈를 생성하되 원화 40장을 그리는 작업이 아니다. 방향각에 따른 눈·코 위치와 팔·발 위상을 파라미터화한다. 걷기는 8fps, 멈추면 즉시 정지 포즈, 위쪽을 볼 때 얼굴 특징을 숨긴다. 옷 색 2종은 텍스처 생성 파라미터이며 두 사람이 한 공동 캐릭터의 외형을 고를 수 있다. 실시간 상대 캐릭터 동기화는 이번 요청에 없고 제공하지 않는다.

충돌체는 발밑 14×10px 사각형, 지형은 32px 격자의 통행 마스크·정적 사각형이다. Arcade Physics를 사용하고 중력은 0, NPC도 같은 통행 판정을 쓴다. 프레임 복귀 시 큰 delta를 그대로 이동에 곱하지 않는다. 물·울타리·줄기·물건을 통과할 수 없으며 대각선 모서리에서 틈을 비집지 않는지 검사한다. NPC와 플레이어는 서로 밀어 길을 막지 않고 부드럽게 겹칠 수 있다.

꾸미기 배치 검증은 점유뿐 아니라 집 입구→각 채집 장소·낚시점의 도달 가능성을 확인한다. 플레이어나 NPC 발 위치에는 놓을 수 없고, 길을 완전히 막는 배치는 이유를 보여주며 거절한다. 로드한 위치가 새 지도에서 막혔다면 가장 가까운 통행 타일 중심으로 복원하고 없으면 집 앞 시작점으로 복원한다. 저장 데이터 오류를 이 위치 복구와 혼동해 전체 상태를 초기화하지 않는다.

## 4. 다가가서 확인하고 반응하기

대상 발 위치에서 40월드px 이내, 바라보는 방향 ±60도, 중간 차단물 없음일 때 가까운 대상 하나를 선택한다. 같은 거리에서는 고정 ID 순서로 결정해 버튼 문구가 흔들리지 않게 한다. 행동 버튼을 누르는 순간에도 거리·대상 존재를 다시 판정한다. 이동 중인 주민은 범위에 들어오면 멈추고 플레이어를 바라본다.

| 다가가는 대상 | HTML 행동 버튼 | 세계의 반응 | 근거 |
|---|---|---|---|
| 주민 | “말 걸기 · 모루” | 서로 바라보기→대화→끄덕임, 닫으면 산책 재개 | **추론:** 사람과 장소가 연결되는 리듬 |
| 열매나무·바닥 채집물 | “따기” / “줍기” | 손 뻗기 0.35초→획득 카드→도감·가방 갱신 | **추론:** 먼 곳에서 획득 불가 |
| 벌레 | “잡기” | 뜰채 0.4초→종 이름, 도망·소멸 패널티 없음 | **추론:** 그림·이동을 발견하는 재미, 반사신경 강요는 제외 |
| 낚시점 | “낚시하기” | 캐릭터가 물 쪽으로 돌아 낚싯대를 던짐 | **추론:** 별도 전면 미니게임 대신 현재 장소에서 진행 |
| 놓인 의자·우물·화분 | “앉기” / “살펴보기” / “따기” | 의자에 앉음·물결·익은 열매 반응, NPC 평가의 대상 | **추론:** 꾸미기가 배경에 그치지 않음 |
| 집 앞 작업대 | “꾸미기” | HTML 물건 선택 후 내 앞 인접 타일에 미리보기, 확정·취소 | **추론:** 배치 모드에도 캐릭터의 위치가 기준 |

배치 물건은 화분·우물·의자 3종을 기본 무료 제공한다. 최대 48개, 1타일 footprint, 배치 모드에서 이동하거나 보관할 수 있다. 모드 동안에도 패드로 걸을 수 있고 미리보기는 한 타일 앞을 따른다. 배치 대상만 격자로 표시한다. 보관·재배치에 화폐·채집 수량을 차감하지 않아 세계 배치와 가방을 여러 키에 걸쳐 원자 저장할 필요가 없다. 가방의 표본을 소비해 제작하는 시스템은 이번 범위에 추가하지 않는다.

**세계·캐릭터·대상 테두리·낚싯줄은 엔진 canvas, HUD·패드·버튼·대사·도감은 HTML**로 유지한다. 기존 §5의 시스템 한글 폰트, 실제 버튼 초점, 저장 오류 문구, 엔진 밖 규칙 경계가 이번에도 유효하다. 긴 한글 대사와 도감을 canvas에 넣으면 줄바꿈·글자 확대·스크린리더·초점 처리를 다시 만들어야 한다. 세계 가까이에 뜨는 표식에는 짧은 아이콘만 쓴다.

대화는 canvas 하단의 112px 이내 HTML 패널로 덮고 이동·낚시 입력을 멈춘다. 글자 확대 때는 iframe 안에서 스크롤 가능한 대화창으로 전환한다. 도감은 iframe 내부 전체 패널, 배경은 inert, 초점은 닫기/항목 사이에 유지하고 닫을 때 원래 버튼으로 돌아간다. 버튼은 최소 44×44 CSS px. 방향키로 걷기와 Enter 상호작용을 지원하고 현재 장소·근접 대상·획득 결과를 HTML 상태로 제공하지만 완전한 비시각 탐험 접근성은 아직 **확인 못 함**이다.

## 5. 주민 3명 — 대사를 수량이 아니라 상황으로 설계

세 주민은 모두 첫날부터 마당에 산다. 접속을 안 해도 떠나거나 서운함을 표시하지 않는다. 일과는 현재 장소의 변주이고 대화 가능 시간을 제한하지 않는다.

| 이름·모양 | 성격·주요 장소 | 직접 작성할 대사 예 | 근거 |
|---|---|---|---|
| 모루·곰 | 느긋한 관찰자, 집 앞 의자와 길 | “여기 의자에 앉으니 물소리가 들리네.” / “오늘도 천천히 한 바퀴 돌까?” | **추론:** 가구 배치 반응 담당 |
| 두리·새 | 호기심 많은 수집가, 나무 그늘 | “저 잎 아래에 작은 날개가 숨어 있어.” / “새 표본이네. 도감에 같이 남기자.” | **추론:** 채집 위치 힌트 담당 |
| 소담·토끼 | 말수 적은 물가 친구, 연못 둑 | “찌가 움직일 때까지 같이 기다리자.” / “놓쳐도 괜찮아. 여기 또 올 거야.” | **추론:** 낚시의 느린 리듬 담당 |

각자 4~6개 고정 waypoint를 24px/s로 걷고 3~8초 쉰다. 자유 난수 배회 대신 통행 가능한 길에 제한한다. 10초 이상 길이 막히면 안전한 waypoint로 목적지를 바꾼다. 매번 목표가 실패한다고 순간이동을 보여주지 않으며, 화면 밖 재입장 때만 안전 지점 재배치가 가능하다. NPC 위치·걷기 위상은 저장하지 않는다.

대사 예산은 **주민당 고유 완성문 16개, 총 48개**다. 인사 4, 장소 4, 배치 반응 4, 발견 반응 2, 친밀한 대화 2로 나눈다. 공통 상황 템플릿 8개를 더해 총 56개 문장/틀을 작성·검수한다. 명사 슬롯은 `의자 옆`, `우물 옆`, `물가`처럼 조사가 포함된 명사구를 사용한다. 무작위로 문장 조각을 붙여 어색한 말투를 만들지 않는다. 세 성격별 말끝은 각자 완성문에서 관리한다.

기존 “4명=100줄”은 고정 비용이 아니다. 이번에는 3명×16개와 8개 공유 틀, 상황 태그·직전 대사 회피로 작은 문장 세트를 여러 장소에서 다르게 읽게 한다. **56개가 100개만큼 새롭다는 주장은 하지 않는다.** 30회 대화에서 무의미한 반복이 드러나면 연결 규칙보다 문장을 먼저 수정한다. 작성·검수 예산 1작업일은 추정이며 대사 문자열은 저장하지 않고 정적 JS에 포함한다.

친밀도는 NPC당 0~12, 0~3/4~7/8~12의 세 단계다. 서로 다른 상황 태그 12개(인사, 세 장소, 세 물건, 첫 채집, 첫 벌레, 첫 낚시, 표본 보여주기, 함께 앉기)를 처음 경험할 때 +1한다. 매일 접속 보상·반복 클릭 보상은 없다. 표본 보여주기는 소비하지 않는다. 모든 태그는 언제든 다시 만들 수 있어 놓친 날이 진행을 막지 않는다.

저장값은 친밀도를 별도 누계로 중복 저장하지 않고 **12비트 경험 마스크에서 계산**한다. NPC별 마스크·직전 대사 ID·마지막으로 반응한 배치 서명·기억한 표본 ID를 저장한다. 이름·문장·실시간 좌표는 없다. 세 주민 관계 키 전체의 raw 예산은 512B 이하로 잡고 실제 codec 측정 전에는 추정으로 취급한다.

물건 반응은 NPC 반경 3타일 안에서 의자/우물/화분의 존재·물가 인접을 조회한다. `(종류, 위치)`를 정규화한 배치 서명이 바뀌면 한 번 새로운 반응을 우선한다. “배우자가 놓았다”는 작성자 정보를 확인할 수 없으므로 “여기 의자가 생겼네”라고만 말한다. 꾸미기가 주민 대화의 원인이 된다.

### 낚시 한 번의 리듬

1. 낚시점 가까이서 “낚시하기”. 도구는 기본 소지, 미끼·내구도·구매 없음.
2. 캐릭터가 물 쪽으로 보고 찌를 던진다. 2~4초 기다린다. 물결과 찌 움직임이 있다.
3. 입질하면 버튼이 “끌어올리기”로 바뀐다. **입질 상태는 버튼을 누를 때까지 유지**한다. 제한 시간·실패 벌금·물고기 도주 없음.
4. 누르면 0.6초 끌어올림→물고기 이름 카드→가방과 도감에 같은 행동으로 반영한다.
5. 취소하면 비용 없이 걷기로 돌아간다. 배경 전환·도감 열림·앱 숨김 때 진행 타이머를 멈춘다. 재시작하면 던지기 전으로 돌아가며 미획득 결과를 차감하지 않는다.

획득 후보는 낚시점의 종 목록을 순환한다. 아직 발견 못 한 소속 종을 우선하고, 모두 찾았으면 시드에 따른 순환으로 바꾼다. 각 낚시점에서 최대 소속 종 수만큼 성공하면 그곳의 모든 종을 볼 수 있어 무한 무작위 반복이 필요 없다. 저장 실패 중에는 새 획득 행동을 중지하고 “저장 후 계속할 수 있어요 · 다시”를 보여주되 산책은 가능하다. ACK 전에 잡은 물고기는 “저장 중”이며 성공 후 “도감에 남겼어요”로 바뀐다.

### 재방문 이유와 완료

날짜별 변화는 오늘 자주 보이는 벌레 위치·주민 waypoint 선택·추천 낚시점이다. 하루가 지나도 이미 화면에 있는 채집물/입질은 교체하지 않고 다음 방문이나 획득 후 생성에 적용한다. 시계를 뒤로 돌리면 저장된 최대 시각보다 이전인 것으로 시간을 계산하지 않는다. 날짜 건너뛰기에 벌금·연속 기록 초기화·전날 보상 미수령 표시가 없다.

도감은 4종 바닥/열매, 4종 벌레, 8종 물고기 탭이다. 미발견 칸에도 이름 대신 실루엣과 장소 힌트를 제공한다. 발견한 항목을 누르면 이름·큰 그림·처음 기록한 날짜·획득 장소·짧은 관찰문을 보여준다. 한 화면에서 2열 카드, 세로 스크롤, 닫기 고정. 가방은 같은 종별 수량을 표시하며 수량 상한 99에 도달하면 “충분히 모았어요”를 알려 새 채집을 거절한다. 기존 수량은 줄지 않는다. 표본 보여주기·도감 확인은 수량을 소비하지 않는다.

16종 발견 때 “우리 마당의 작은 생명을 모두 만났어요”를 한 번 보여준다. 이후에도 낚시·대화·꾸미기가 남는다. 친밀도 만점이나 모든 칸 점유를 완료 조건으로 강요하지 않는다. 완주 일수는 고정하지 않는다. 하루 몰아서 해도 끝낼 수 있고 며칠씩 쉬어도 조건이 달라지지 않는다.

## 7. 저장 모델 — ADR 3: 원자 행동을 기준으로 키 분리

`app_key='backyard'`를 유지하고 **새 RPG 키 5개**를 둔다. 가구의 세계·도감·가방·주민 관계·캐릭터는 공동이다. 개인 계정별 진행을 가정하지 않고, 현재 `host.info`에 memberId가 없다는 사실을 존중한다. 동시 실시간 멀티플레이는 제공하지 않는다.

| stateKey | DTO 내용·상한 | raw 설계 예산 | 근거 |
|---|---|---:|---|
| `rpg_meta` | 스키마 v=2, mapVersion=1, seed, 초기화 완료, 이전 garden 이전 여부 | 256B | **추론:** 세계 정적 정의와 저장 버전 분리 |
| `rpg_world` | 최대 48개 물건 튜플 `id:kind:col:row`(보관은 위치 대신 b), legacy 열매 기념값 | 3072B | **추론:** 배치 이동·보관을 한 키에 저장, 성장 시각은 collection이 소유 |
| `rpg_collection` | 최대 16종 `species:count:firstSeenAt`, 자연 12+화분 48=최대 60개 `node:readyAt`, 낚시점 3개 순환 인덱스 | 4096B | **추론:** 채집 완료와 가방·도감·재생성 시각을 같은 키로 원자화 |
| `rpg_residents` | 주민 3개 `id:mask:lastLine:layoutSignature:sampleId` | 512B | **추론:** 소비 없는 대화·기억 행동만 변경 |
| `rpg_player` | 지도 버전, x/y(1/16타일 정수 단위), 바라보는 0~7 방향, 옷 0~1, 마지막 시각 | 256B | **추론:** 이동 저장을 큰 세계 키와 분리 |

합계 raw 예산 8192B는 **5개 키 총량 설계 목표**이며 시스템 총 저장 상한이 아니다. 키별 실측·DB 크기는 **확인 못 함**이다. ID는 고정 ASCII이며 위치·수량·시각은 허용 정수 범위를 codec에서 검사한다. 위 예산에는 JSON 객체·배열·따옴표·메타데이터가 포함되어야 한다. 구현 최대 fixture로 `Buffer.byteLength(JSON.stringify(dto),'utf8')`와 실제 DB `pg_column_size`를 따로 측정하고, 키마다 둘 다 8192B 이하를 게이트로 둔다.

외부 객체 키를 반복하지 않는 튜플 문자열은 재사용한다. **현재 codec 함수 자체는 Garden·balance에 결합되어 있으므로 그대로 호출해 RPG 상태를 읽지 않는다.** 정수 토큰 전체 검사·중복 판정·정규화 순서·순수 함수·버전 오류 원칙을 옮긴다. 엔진 Sprite·카메라·Tween·Scene·타이머·문장·프레임 위상은 직렬화하지 않는다. 플레이어 좌표는 엔진 객체에서 추출한 검증된 논리 위치만 변환한다.

### 원자성의 경계

일반 채집·낚시는 `rpg_collection` 한 키에서 수량·최초 발견·다음 획득 상태를 함께 갱신한다. 도감 키와 가방 키를 별도로 쓰다가 “가방에는 있고 도감에는 없는” 상태가 생기지 않게 한다. 관계 행동은 표본을 소비하지 않고, 꾸미기는 무료이므로 관계/배치 변경에 collection 동시 쓰기가 필요 없다.

화분도 `readyAt`을 collection의 `pot-{id}` 채집점에 두어 **수확은 collection 한 키만 변경**한다. 신규 화분의 첫 익음은 즉시 1개로 계산하고 첫 수확 때 채집점 시각을 생성한다. v0 이전 화분 시각은 초기화 단계에서 collection으로 옮긴다. world에는 성장 시각을 중복 저장하지 않는다.

물건 ID는 0~47 고정 슬롯이며 보관도 슬롯을 점유한다. 슬롯의 물건 종류는 첫 생성 뒤 바꾸지 않고, 신규 생성은 빈 슬롯에서만 한다. 이미 사용한 슬롯을 삭제·재발급하지 않으므로 보관/재배치로 화분 시각이 초기화되거나 채집점이 무한 증가하지 않는다. 48개 제한은 보관을 포함한 소유 상한이다. 무료 소유 물건을 모두 한 종류로 고르는 실수를 피하도록 시작 시 화분·우물·의자 각 1개를 제공하고, 추가 선택 때 보관 포함 남은 수를 표시한다. 자연 채집점은 열매나무 4(두 종류 각 2), 바닥 채집 4(두 종류 각 2), 벌레 4(종별 1)로 총 12개다.

### 부팅·저장·복귀

`ready→meta/필수 키 읽기→검증→playable`을 따른다. **GET 실패·timeout을 null 신규로 바꾸지 않는다.** meta가 존재하는데 필수 키가 null이면 초기화하지 않고 복원 오류로 멈춘다. 알 수 없는 버전도 자동 덮어쓰지 않는다. collection·관계의 손상 튜플은 기록을 잃을 수 있으므로 읽기 가능한 내용을 보여주더라도 해당 키 writer는 막고 재시도만 허용한다. world의 손상 위치는 경고와 함께 안전 표시하되 자동 청소 저장하지 않는다.

meta가 성공적으로 null일 때 기존 `garden`과 새 키들을 먼저 읽는다. 새 키가 전부 없으면 결정적 초기값을 준비하고 데이터 4개 키의 ACK 후 meta를 마지막에 쓴다. 부분 초기화가 남아 있으면 기존 새 키를 검증·보존하고 없는 키만 채워 완료한다. 초기화가 끝나기 전에는 플레이·수동 편집을 열지 않는다. 동시 최초 진입이 다른 난수 시드를 쓰지 않도록 초기 세계 seed는 고정값 4821을 사용한다. 개인화가 필요한 나중에만 seed 정책을 바꾼다.

기존 `garden`은 삭제·수정하지 않는다. v1 decoder로 읽고 4×4 배치를 집 앞 열 3~6, 행 15~18에 매핑한다. 시작 발 (7,18)과 겹치지 않는다. 기존 화분 readyAt과 열매 수는 보존하고 열매 수는 “예전 마당에서 모은 열매” 기념값으로만 표시한다. 수량을 화폐나 새 도감 16종으로 임의 변환하지 않는다. 낡은 앱은 garden만 쓰고 새 앱은 rpg 키만 쓴다. 구 앱에서 이후 변경한 내용은 자동 재병합하지 않는 일회성 이전이다. v1 손상이 있으면 이전을 중단하고 원본을 남긴다.

`session.js`의 세대 토큰·ACK 순번·최신 snapshot·1/2/4/8/16/30초 재시도 구조는 키별 writer로 확장한다. 의미 있는 행동은 즉시 저장하고 이동은 멈춘 지 1초 후·걷는 중 최대 10초마다·숨김 시 보조 flush한다. 프레임마다 저장하지 않는다. 저장 안 됨은 HTML에 계속 표시하고 획득·대화 기억·꾸미기 변경은 앞 변경의 ACK까지 잠근다. 걷기·기존 도감 보기는 가능하다. 앱 종료 전 flush가 성공을 보장하지 않으며 ACK 전 변경 소실 가능성은 남는다.

현재 호스트 `state.get` 하나가 매번 전체 list를 호출하므로 5개 키 읽기는 list 5회가 된다. 초기에는 이 고정된 작은 개수를 수용한다. 무제한 키 개수를 이용해 매 걸음·대사마다 새 키를 만드는 로그 저장은 하지 않는다. 새 `state.list` 브릿지·서버 트랜잭션을 당연히 존재하는 것처럼 설계하지 않는다.

### 두 사람이 동시에 열 때의 한계

키 분리는 서로 다른 종류의 행동이 덮이는 범위를 줄일 뿐 **같은 키 동시 편집을 해결하지 않는다**. 읽기 직후 합집합을 만든 뒤 PUT해도 CAS가 없으면 두 기기에서 잃어버릴 수 있다. 부모 키별 큐·클라이언트 revision으로 이를 해결했다고 주장하지 않는다.

이번에는 기존 API의 마지막 쓰기 우선을 유지한다. 진입·백그라운드 복귀 시 최신 상태를 다시 읽고, dirty가 있으면 ACK/실패 해결 전 원격 값으로 메모리를 교체하지 않는다. 두 기기의 같은 collection 변경이나 world 편집은 저장 성공 뒤에도 상대의 늦은 PUT으로 덮일 수 있다. UI 첫 도움말에 “같은 마당을 공유해요. 동시에 바꾸면 마지막 저장이 남아요”를 명시한다. **이는 시간 경과에 따른 감쇠 금지와 별개인 현재 저장 기반의 내구성 한계**다.

슬라이스 10에서 두 클라이언트 경합을 재현하고 손실 범위를 보고한다. 이 한계를 수용할 수 없다면 다음 결정은 API 조건부 저장/트랜잭션 확장이다. 정적 게임만으로 무손실 공동 편집을 약속하지 않으며, 그 변경은 일정·서버 작업을 명시해 별도로 승인받을 대상이다. 게임 설계서 완료와 해당 제품 출하 판단을 구분한다.

## 8. 도형 아트 제작 계획

**도형으로 모든 요청 대상을 표현할 수 있다고 판단한다.** 사실로 확인된 것은 기존 화분·우물·의자와 sandbox 생성 텍스처이고, 신규 주민의 매력·작은 벌레 식별성은 **확인 못 함**이다. 도형이라는 이유만으로 시각 품질을 보장하지 않는다.

| 대상 | 제작 단위 | 예상 작업·검증 | 근거 |
|---|---|---|---|
| 플레이어+주민 3명 | 공용 몸체 생성기 1개, 얼굴/귀/꼬리 실루엣 4개, 40포즈×4=160개 생성 프레임 | 형태·걷기 1일, 작은 화면 식별 검증 포함 | **추론:** 손그림 160장과 다름 |
| 나무·집·길·물·채집물 | 나무 2종, 집 1, 지형 4, 채집 기본형 4 | 지도·환경과 함께 1일 | **추론:** 반복 배치와 색 변주 |
| 벌레 4종·물고기 8종 | 날개·몸·무늬 12개 파라미터 레시피 | 채집/낚시 슬라이스에서 합계 약 1일의 아트 시간 | **추론:** 게임 로직 시간과 중복 합산하지 않음 |
| 기존 물건 3종 | 기존 도형 명령·팔레트 재사용 | 타일 크기·발 위치·깊이 조정 | **추론:** 그림을 그대로 축소하면 가독성이 나쁠 수 있음 |

상시 Graphics를 전부 다시 그리기보다 최초 한 번 canvas에 생성해 텍스처로 등록하고 Sprite를 배치한다. 캐릭터 프레임을 각 32×40 RGBA로 만들면 160×32×40×4 = **819,200B의 비압축 픽셀 계산값**이다. atlas 여백·GPU 복제·엔진 객체·DPR 배율은 별도라 실제 메모리가 이 수치와 같지는 않다. 2배 해상도로 생성하면 픽셀 메모리는 4배다. 정적 나무·바닥도 청크별 캐시를 쓰되 프레임마다 텍스처를 재생성하지 않는다. 발 y 기준 정렬로 나무 앞뒤에 캐릭터가 자연스럽게 가려진다.

벌레는 세계에서 12~18px의 실루엣과 움직임으로 찾고, 도감에서는 64px 이상으로 확대한다. 종별 차이를 색 하나에만 의존하지 않는다. 모루는 작은 귀와 둥근 몸, 두리는 부리와 작은 날개, 소담은 긴 귀로 구별한다. 그림자·물결·나무 수관의 작은 흔들림을 사용하고 화면 흔들기·번쩍임은 넣지 않는다.

도형 식별 테스트가 실패하면 해당 종만 인라인 PNG atlas로 교체한다. **가정:** PNG 합계 24KiB라면 base64는 32,768자, `data:image/png;base64,` 접두부 22자와 JS 문자열 구문 비용이 붙는다. PNG 64KiB라면 base64 87,384자다. 이는 인코딩 산술이고 PNG 실제 크기·OTA 압축 증분·제작 시간은 **확인 못 함**이다. 필요한 실루엣 4종에 한정해 반나절~1일 보정 예산을 잡는다. 외부 PNG 로더나 CORS 완화로 우회하지 않고 동봉 JS 안 data URI만 쓴다.

## 9. 엔진 재검토 — ADR 4: Phaser 4.2.1

**검증된 고정 UMD로 Phaser를 채택한다.** 기존 canvas 선택은 v0의 격자·히트테스트·tween 범위에서 타당했지만, 같은 이유를 걷는 게임에 적용할 수 없다.

| 비교 | 자체 canvas 2D | Phaser 선택의 의미 | 근거 |
|---|---|---|---|
| 카메라 | 좌표 변환·추종·경계·리사이즈 직접 관리 | 카메라 bounds·follow·viewport 기능 사용 | **추론:** 이번 실제 요구와 일치 |
| 움직임·충돌 | 시간 적분·충돌 분리·정렬·입력 수명 직접 관리 | Arcade Physics로 단순 사각형 충돌, Sprite 위치 관리 | **추론:** 중력 없는 탑다운에 필요한 범위 |
| 생성 아트 | canvas 생성 함수는 만들기 쉬움 | 생성 canvas 텍스처를 Sprite로 쓰고 프레임 애니메이션 관리 | **추론:** 도형 아트와 엔진이 양립 |
| 씬·수명 | 로드·세계·일시정지 수명을 직접 조립 | Boot/World 두 씬, 대화·도감은 HTML 상태 | **추론:** 화면마다 별도 엔진 씬을 만들지는 않음 |
| 다운로드 | 엔진 증분 없음, 자체 구현 크기는 미정 | 모든 OTA 사용자에게 약 355KB 추가 부담 | **추론:** 반복 구현·회귀 비용을 줄이는 대가로 수용 |

Phaser 공식 문서에서 [카메라의 세계/뷰포트 구분·추종·경계](https://docs.phaser.io/phaser/concepts/cameras), [Arcade의 사각형·원 충돌과 탑다운 용도](https://docs.phaser.io/phaser/concepts/physics/arcade), [Graphics의 텍스처 생성](https://docs.phaser.io/phaser/concepts/gameobjects/graphics), [Scene 수명](https://docs.phaser.io/phaser/concepts/scenes)을 확인했다. 이 문서의 구체적인 성능·공수 판단은 공식 문서가 보장한 수치가 아닌 위 요구에 대한 추론이다. 최신 문서와 고정 4.2.1의 세부 API 일치는 구현 전에 배포 파일과 대조한다.

+31.56%는 당시 작은 기준 ZIP의 상대 증가다. 기록된 v0 ZIP 1,179,233B를 분모로 같은 354,712B를 단순 나누면 약 **30.08%**다. 이는 새 게임 빌드의 실측 증가율이 아니다. 게임 로직·생성 아트·타입 선언 추가와 옛 코드 제거가 있으므로 최종 OTA는 슬라이스 11에서 다시 잰다. 전체 ZIP 목표는 초기 계획상 v0 대비 +450KiB 이내이며 초과하면 파일별 원인을 검토한다. 기능을 삭제하거나 CDN으로 빼서 수치를 숨기지 않는다.

포기하는 것은 엔진 없는 최소 번들, 기존 renderer/input의 직접 재사용, 작은 자체 수명 시스템이다. 대신 Phaser 버전 관리·UMD 타입 연결·WebView 부팅·전체 Game destroy 검증 책임을 진다. Matter Physics·외부 플러그인·Tiled 로더·실시간 멀티플레이·여러 실내 씬은 필요하지 않다. 가상 패드·NPC 결정·대사·도감·저장 충돌은 Phaser가 대신 만들지 않는다.

일반 `<script defer>`로 향후 `apps/web/public/miniapps/vendor/phaser.min.js`를 동봉한다. 이 제품 경로는 **제안 경로이며 이번에 생성하지 않았다**. 검증용 원본 `scripts/verify-sandbox-engine/vendor/phaser.min.js`와 해시를 맞추고 배포 라이선스 고지를 함께 확인한다. 텍스처와 지도·대사는 일반 script 안에 넣는다. CDN·module import·XHR JSON에 부팅을 의존시키지 않는다.

순수 규칙/codec/session은 엔진 타입에 의존하지 않는다. 엔진 어댑터만 Phaser 타입을 보며 정확한 버전의 선언 파일을 구현 때 검증하고 DOM tsconfig에 연결한다. `any`로 덮지 않는다. 구현 공개 API는 한국어 JSDoc, 외부 입력은 unknown에서 좁힌다. Boot 실패 시 HTML “마당을 열지 못했어요 · 다시”를 표시하고 저장 writer를 만들지 않는다. World 외에 별도 RAF를 앱이 돌리지 않는다.

슬라이스 1에서 카메라·패드·충돌·부팅이 실제 통과하지 않으면 엔진 결정을 다시 연다. 재검토 시에도 세계·캐릭터·주민 범위를 유지하고, 실패한 엔진 어댑터의 비용을 다시 계산한다.

## 12. 기존 원칙 재판단과 설계 검토

| 기존 원칙 | 이번 판단 | 근거 |

스스로 독자 관점에서 지시서의 열 가지 설계 항목을 대조했다. 세계/화면 크기 분리, 실제 호스트 높이, 이동·상호작용, 주민과 대사 비용, 16종 획득, 재방문과 상실 금지, 키별 원자성, 아트 비용, 엔진의 포기 항목, 파일별 판정과 첫날 산책 게이트를 모두 찾을 수 있게 구성했다. 독립 에이전트 리뷰는 수행하지 않았으며, 이 자체 검토를 외부 승인으로 표현하지 않는다.

반복 방지 기록은 다음과 같다. **코드의 사실과 제품 추론을 같은 사실 표에 넣지 않는다. 화면 크기를 세계 크기로 대체하지 않는다. 도형 포즈 수를 손그림 장수로 계산하지 않는다. 키 수 무제한을 원자 저장이나 무손실 공동 편집으로 해석하지 않는다. 기존 캡처의 iframe 폭 시험을 부모 휴대폰 화면 시험으로 대신하지 않는다.**

미확인은 신규 재미·신규 아트 식별성·고정 엔진 API 연결·RPG 최대 직렬화/DB 크기·최종 OTA·Capacitor 실기기 성능이다. 각각 슬라이스 1/2/4/10/11/12의 게이트에 연결했다. 이번에 만든 파일은 이 설계서 하나이며, 설계 완료가 구현·출하 완료를 의미하지 않는다.
