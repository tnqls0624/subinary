# 재설계 지시서 — 전체 화면 3D로 (2026-09-08)

> **이번 작업은 재설계다. 코드를 쓰지 말고 설계서만 쓴다.**
> 12개 슬라이스로 만든 2D 게임이 돌고 배포까지 됐다. 사용자가 두 가지를 지적했다.

## 사용자가 지적한 것

1. **"앱 안에서 조그만한 화면이 아닌 앱을 통해서 새로운 앱의 게임을 여는 느낌"** —
   전체 화면이어야 한다. 지금은 헤더 + 하단 탭 5개 + 카드 여백 안의 470~520px iframe이다.
2. **"현재 그래픽이 너무 안좋아"** — 동물의 숲(New Horizons) 키 아트를 벤치마크로 제시했다.

두 번째에 대해 코디네이터가 사용자와 정리한 사실:
- **New Horizons의 실제 에셋을 쓰는 것은 저작권 침해다.** 그 경로는 없다.
- 그 화면은 3D 스튜디오 프로덕션 아트다. 코드로 재현할 수 없다.
- **동물의 숲의 느낌은 정교한 그림이 아니라 둥근 단순한 형태에 얹힌 부드러운 조명에서 온다.**
  나무는 구 몇 개, 캐릭터는 큰 머리 + 둥근 몸이다. 그것은 손그림이 아니라 **기하와 조명**이다.
- 그래서 3D로 가면 아트 문제가 오히려 풀린다. 2D 스프라이트는 매력이 픽셀에 있어 사람이
  그려야 하지만, 3D는 색·기하·조명이 전부 파라미터다.

**언리얼 엔진은 기각했다.** UE는 HTML5 익스포트를 4.24에서 제거했고 UE5에 공식 웹 타깃이
없다. 모바일 네이티브로 가면 수백 MB의 별도 앱 + 별도 스토어 심사가 되고, OTA 번들 배송·
가구 공유 저장·미니앱 구조가 전부 버려진다. 가계부 앱 안에서 여는 게임이라는 전제가 사라진다.

## 코디네이터가 직접 확인한 것 — 추정하지 말고 이 값을 쓰라

| 항목 | 값 | 근거 |
|---|---|---|
| 현재 OTA ZIP | 1,570,734B | 이번 배포 후 실측 |
| Phaser 원본 | 1,375,976B (gzip 355KB) | `wc -c`, 현재 동봉 중 |
| **Three.js r128** | **603,445B (gzip 145KB)** | cdnjs 실측 + `gzip -9` |
| 교체 시 예상 | **약 772KB 감소** | 위 두 값의 차 |
| `(app)` 레이아웃 | 헤더 + `data-bottom-nav` 하단 탭 + 카드 여백 | `apps/web/src/app/(app)/layout.tsx` |
| 등록 높이 | `miniapp-registry.ts`의 값이며 **상한**으로 쓰인다 | `BackyardViewport`가 `Math.min`에 사용 |

**3D로 가면 번들이 오히려 작아진다.** 이것이 이 재설계의 비용 근거다.

## 이미 정해진 것 — 재검토 대상이 아니다

### 앱 자체 화면으로 간다 (사용자 결정)
iframe 격리를 버리고 게임을 앱의 전역 화면으로 만든다. 같은 origin이 되므로
**CORS 제약이 사라진다**(`docs/verify-sandbox-engine-2026-09.md`의 불투명 origin 문제가
무관해진다). 잠재적 대가는 게임이 부모 DOM을 보게 되는 것이며, 우리가 만든 게임이므로
사용자가 그 교환을 택했다.

### Three.js 스타일라이즈드 3D, 이미지 파일 0개
| 요소 | 방향 |
|---|---|
| 지형 | 낮은 폴리 높이맵, 부드러운 언덕. 잔디 3톤 |
| 나무 | 구 2~3개 층 수관 + 원기둥 줄기 |
| 캐릭터·주민 | 큰 머리 + 둥근 몸(캡슐·구), 툰 셰이딩 2단 + 외곽선 |
| 조명 | 반구 + 방향 라이트 + **부드러운 그림자** |
| 카메라 | 기울인 3인칭 추종 |
| 물 | 반투명 + 잔물결 |
| 하늘 | 그라디언트 + 구름 |

**조명이 이 느낌의 8할이다.** 텍스처 디테일·정교한 표정·손그림 소품은 포기한다.

## 설계할 것

### 1. 전체 화면 라우트
- `(app)` 레이아웃을 어떻게 벗어나는가. 라우트 그룹을 새로 만드는가, 레이아웃에 모드를 두는가.
- **뒤로 가기**를 어떻게 주는가. 하단 탭이 없으면 나갈 길이 필요하다.
- Android 하드웨어 뒤로, iOS 스와이프, safe-area, 상태바.
- 세로 고정인가 가로 허용인가.
- **기존 `/play/app?key=backyard` 경로와 미니앱 구조를 유지하는가 버리는가.** 판단하고 근거를 적어라.

### 2. 저장을 어떻게 하는가
같은 origin이면 브릿지 postMessage가 필요 없을 수 있다. `usePlayStates` 훅을 직접 쓸 수 있다.
다만 **5키 저장 계약과 그 실패 분기(초기 GET 실패 시 PUT=0)는 유지 대상이다.**
`docs/impl-backyard-v0.md` §6.2와 `docs/redesign-backyard-rpg.md` §7을 읽고 무엇을 옮길지 정하라.

### 3. 3D 씬 구성
- 세계 크기와 카메라. 지금은 32×24타일 1024×768 월드픽셀이다. 3D 좌표로 어떻게 옮기는가.
- 조명·그림자 설정과 **모바일 성능 비용**. 그림자 맵 해상도, 드로우콜, 인스턴싱.
- 지형·나무·물·하늘의 구체적 기하와 재질 파라미터.

### 4. 캐릭터와 주민의 3D 표현
- 큰 머리 비율, 툰 셰이딩, 외곽선을 어떻게 만드는가.
- 걷기 애니메이션 — 본 없이 파츠 회전으로 되는가.
- 주민 3명의 실루엣 구분(모루 곰·두리 새·소담 토끼).

### 5. 조작
전체 화면이면 가상 패드 위치·크기가 달라진다. 3인칭 카메라에서 방향 기준이 무엇인가
(월드 기준인가 카메라 기준인가). 근접 판정을 3D에서 어떻게 하는가.

### 6. 성능 목표와 측정 방법
모바일 WebView에서 프레임 예산. **측정 방법을 구체적으로 적어라.**
목표를 못 맞출 때 무엇을 먼저 낮추는가(그림자 → 폴리곤 → 해상도 순서 등).

### 7. 슬라이스
하루 단위로 자르고 **각각 끝났다는 것을 무엇으로 확인하는지** 구체적으로.
**첫 슬라이스는 "동물의 숲처럼 보이는가"를 가장 빨리 확인하는 것**이어야 한다 —
지형 + 나무 + 조명 + 캐릭터 하나를 세우고 스크린샷을 보는 것. 그것이 아니면 나머지가 무의미하다.

이전 재설계가 슬라이스 1을 "걷는 느낌"으로 두어 첫날에 가설을 확인했다. 같은 방식을 쓰라.

### 8. 실패 조건
**이 재설계가 틀렸다는 것을 무엇으로 알 수 있는가.** 3D가 모바일에서 너무 느리거나,
도형 3D가 2D보다 오히려 싸구려로 보이면 어떻게 판단하고 무엇으로 되돌리는가.

## 지켜야 할 것

- **코드를 쓰지 않는다.** 이 설계서 하나만.
- **확인한 사실과 추론을 같은 표에 섞지 마라.** 이전 실패의 직접 원인이다.
  표에 「근거」 열을 두고 추론이면 "추론"이라고 적어라.
- 확인 못 한 것은 **"확인 못 함"**이라고 쓴다. 크기·버전은 실제로 확인하고 근거를 적어라.
- **동물의 숲의 에셋·모델·텍스처를 가져오지 않는다.** 시각 언어만 참고한다.
- 살릴 원칙: 감쇠·상실 없음 · 알림 없음 · 화폐 없음 · 지출 미연동 · 잃는 것을 만들지 않음.
  근거는 `docs/design-tycoon-game-2026-09.md` §3·§4·§7이다. **읽고 이번에도 유효한지 판단하라.**
- 게임 내용(주민 3명·채집 8종·낚시 8종·도감)은 이미 만들어졌다. **다시 설계하지 마라.**
  이번 재설계는 **표현과 화면**이다.
