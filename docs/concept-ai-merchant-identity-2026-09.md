# AI 가맹점 아이덴티티 + AI 활용 확장 — 작업 지시서 (2026-09-04)

> **이 문서는 메타프롬프트다.** 다음 세션에서 대화가 압축된 뒤 이 파일만 읽고 작업을
> 이어갈 수 있도록 자기완결적으로 썼다. 재사용할 자산·실측 근거·지켜야 할 원칙·하지 말
> 것을 모두 담았다. 새로 조사하기 전에 여기 적힌 것을 먼저 신뢰하되, **숫자는 반드시
> 다시 실측한다**(아래 §0 규칙).

---

## §0. 이 프로젝트에서 반복 확인된 작업 규칙

이 세션(2026-09-03~04)에 실제로 값을 치른 교훈이다. 어기면 같은 대가를 다시 낸다.

1. **"막혔다"고 판단하기 전에 그 판단의 전제를 데이터로 확인한다.** D7(예산 초과 표시)을
   "카테고리가 없어 불가능"이라 결론냈는데, 실제 예산을 조회하니 전부 `card` scope였고
   household·category는 0건이었다 — 전제 자체가 틀렸다. 스키마만 보고 판단하지 않는다.
2. **정적 진단은 심각도를 과장한다.** 보고 전에 운영 DB로 직접 확인한다.
3. **자동으로 상태를 바꾸지 않는다. 묻는다.** 시스템이 스스로 결정하면 사용자 모르게
   숫자가 변한다(정기 지출 D4가 그 이유로 `needs_review` 전이를 기각했다).
4. **빠진 것을 숨긴 합계는 거짓말이다.** 합계를 낼 때는 **빠진 건수와 사유**를 함께 낸다.
   사유가 둘이면 나눠 센다 — 사용자가 취할 조치가 다르기 때문이다.
5. **관측된 사실만 말한다.** 예측·추세 외삽은 하지 않는다. 근거를 화면에 함께 띄울 수
   없는 숫자는 내보내지 않는다.
6. **플래그로 잠긴 기능은 "완료"가 아니다.** env가 없어 3주간 화면에 "준비 중"만 뜬
   기능이 있었다. 상태를 `✅ 구현` / `🔓 활성` 둘로 나눠 적는다.
7. **패키지를 고쳤으면 `pnpm typecheck`만이 아니라 `pnpm build:packages`까지 돌린다.**
   tsup DTS 생성이 `tsc --noEmit`보다 엄격해 배포에서만 터진다.
8. **`apps/mobile`에 의존을 추가하면 루트 락파일도 갱신**한다(`pnpm install --lockfile-only`).
9. 배포는 `sh scripts/ops/deploy.sh` 하나다(서버 + 앱 OTA 번들). 디스크 부족이 나면
   `docker system df`로 **이미지인지 빌드 캐시인지 먼저 보고**, 캐시면
   `docker builder prune --all --force --reserved-space 2GB`(10GB는 아무것도 못 지운다).

## §1. 문제 — 같은 가게가 여러 이름으로 갈린다

**실측(2026-09-04, 운영 DB)**: 거래 258건에 서로 다른 `merchant_normalized` **102개**,
등록된 `merchant_aliases` **10건**, `merchant_category_rules` 109건.

102개 안에 아래 유형이 섞여 있다. **유형마다 처리가 달라야 한다** — 하나의 규칙으로
묶으려 하면 반드시 잘못 묶는다.

| # | 유형 | 실측 예 | 자동 병합? |
|---|---|---|---|
| A | **표기 차이**(한글/영문·공백) | `지에스25 영등포도림`(11) ↔ `GS25영등포도림`(7) | 제안 → 사람 확정 |
| B | **어순 차이** | `다이소아성산업`(4) ↔ `아성다이소`(2) | 제안 → 사람 확정 |
| C | **절단** | `도동터미`←도동터미널, `이마트 신`, `코코호도서`, `지에스25영등포`(3) | **기존 규칙이 이미 잡는다**(§2) |
| D | **접두 중복** | `무신사무신사` | 정규화로 처리 |
| E | **다른 브랜드, 비슷한 이름** | `씨유영등포도림`(CU) vs `GS25영등포도림`(GS25) | **⛔ 묶으면 안 된다** |
| F | **같은 브랜드, 다른 매장** | `지에스25여의캐`(7)·`지에스25영등포`(3)·`지에스25 영등포도림`(11)·`지에스25S9샛강` | **정책 결정 필요**(§4-0) |
| G | **결제 대행** | `토스페이`(3)·`네이버페이`(2)·`발트페이`·`카카오` | ⛔ 실제 가맹점 불명 — 묶지 않는다 |
| H | **비가맹점** | `ATM`, `q.scqr.kr/vnJNB8j` | 별도 |

**E가 이 작업의 가장 큰 위험이다.** `씨유영등포도림`과 `GS25영등포도림`은 지명이 같아
문자열 유사도가 높지만 **경쟁 브랜드**다. 묶으면 두 회사 지출이 한 이름으로 합쳐진다.
유사도만으로 판단하는 어떤 방법도 이 사례에서 틀린다 — 브랜드 토큰을 먼저 분리해야 한다.

## §3. 설계 원칙 (이 작업에 특히 적용되는 것)

1. **AI는 후보를 제안하고, 병합은 사람이 확정한다.** 잘못 묶은 가맹점은 금액을 섞고,
   되돌려도 사용자가 그 사이 본 숫자는 이미 틀렸다. ADR-0019 §4가 정한 경계다.
2. **브랜드 토큰을 먼저 분리한다.** 유사도만 쓰면 §1-E(CU vs GS25)에서 틀린다. 브랜드가
   다르면 지명이 같아도 후보로 올리지 않는다.
3. **LLM은 판단 근거를 인용하고, 결정은 결정적 코드가 한다.** L2 파서(quote-grounded)와
   같은 구조 — LLM이 "이 둘은 같다"고 말하는 대신 "브랜드=GS25, 지점=영등포도림"처럼
   **구조를 뽑고**, 병합 여부는 그 구조를 비교하는 순수 함수가 정한다. 그래야 재현
   가능하고, 왜 묶였는지 사용자에게 보여줄 수 있다.
4. **제안에는 근거와 영향 범위를 붙인다.** 몇 건·얼마가 합쳐지는지, 어느 달이 바뀌는지.
   카테고리 소급 재분류(`0055`)가 이미 이 패턴을 쓴다 — 미리보기 → 확정 → 되돌리기.
5. **PII를 LLM에 최소로 보낸다.** 가맹점명은 개인 소비 이력이다. 금액·날짜·구성원은
   보내지 않는다. 이름 목록만으로 충분하다.
6. **비용 상한과 관측을 먼저 둔다.** `CARD_SMS_LLM_DAILY_BUDGET` 패턴을 따른다.
   `ai_invocations`에 기록해 "AI가 무엇을 몇 번 했나"를 셀 수 있게 한다.
7. **규칙이 먼저, LLM은 나중.** 절단(C)·접두중복(D)은 이미 규칙으로 잡힌다. LLM은
   **규칙이 못 잡은 것만** 본다(L0→L1→L2 캐스케이드와 같은 구조).

## §4. 작업 슬라이스

### §4-0. 먼저 답해야 하는 정책 질문 (사용자에게 물을 것)

**같은 브랜드의 다른 매장을 묶을 것인가?**(유형 F) 예: `지에스25여의캐`·`지에스25영등포도림`.

- 묶으면: "GS25에서 이번 달 얼마" 를 알 수 있다. 대신 **어느 지점**인지 잃는다.
- 안 묶으면: 목록이 길어지지만 지점별 소비가 보인다.
- 중간: 별칭은 매장 단위로 두고, **브랜드는 별도 축**으로 집계(카테고리와 같은 계층).

**권장은 중간안**이다 — 병합은 되돌리기 번거롭고, 브랜드 집계는 추가 축이라 되돌릴 게
없다. 다만 이건 제품 결정이므로 **구현 전에 확인**한다.

### §4-1. S1 — 브랜드/지점 구조 추출 (M)

- 규칙 우선: 알려진 브랜드 사전(GS25·CU·세븐일레븐·이마트24·스타벅스·올리브영 …)으로
  브랜드 토큰을 먼저 떼고 나머지를 지점명으로 본다. 사전은 코드에 두고 실측으로 늘린다.
- 규칙이 못 뗀 이름만 LLM에 보낸다. **출력은 `{brand, branch}` 구조**이고, 이름 원문에서
  그 토큰이 실제로 발견되는지 코드가 검증한다(quote-grounded).
- **DoD**: ① 브랜드가 다른 두 이름이 절대 같은 브랜드로 판정되지 않는다(§1-E를 픽스처로
  고정) ② 같은 입력 → 같은 출력(결정적) ③ LLM 실패는 "미판정"이고 잡을 실패시키지 않는다

### §4-2. S2 — 병합 후보 제안 API + 화면 (M)

- 후보 = 절단(기존 `findTruncationCandidates`) + 표기/어순(정규화 비교) +
  브랜드·지점 일치(S1). **각 후보에 유형과 근거를 붙인다.**
- 미리보기: 합쳐질 거래 건수·금액·기간·영향 받는 달. 카테고리 재분류(`0055`)의
  `expectedCount` 패턴으로 사용자가 본 수와 적용 시점 수가 다르면 409.
- 확정 시 `merchant_aliases`에 쓰고 `POST /v1/recurring/recompute`를 한 번 돌린다(별칭이
  정기 지출의 canonical 신원을 바꾼다).
- **DoD**: ① 자동 병합 0건 — 전부 사람 확정 ② 되돌리기 가능 ③ 타인 `private`·`summary_only`
  근거가 섞인 후보에서 이름이 새지 않는다(P0-6 재발 방지)

### §4-3. S3 — 학습 루프 (S~M)

- 사용자의 확정·거절을 append-only feedback으로 남긴다(ADR-0019 §1). 그것이 다음 제안의
  학습 데이터가 된다 — 같은 후보를 두 번 거절했으면 다시 올리지 않는다.
- 기존 파이프라인(데이터셋 스냅샷 → 격리 학습 → 카나리 → 승격)에 얹는다. **새 파이프라인을
  만들지 않는다.**
- **DoD**: 거절한 후보가 재제안되지 않는다 / 제안 정밀도를 지표로 남긴다

## §5. 하지 말 것

| 항목 | 이유 |
|---|---|
| **자동 병합** | 잘못 묶으면 금액이 섞이고, 되돌려도 사용자가 본 숫자는 이미 틀렸다 |
| 유사도(편집거리·임베딩)만으로 판단 | §1-E(CU vs GS25)에서 틀린다. 브랜드 분리가 먼저다 |
| 결제 대행(`토스페이` 등) 병합 | 실제 가맹점을 모른다. PRD §15가 이미 "지어내지 않는다"로 정했다 |

| LLM이 병합 여부를 직접 결정 | 재현 불가하고 사용자에게 근거를 보여줄 수 없다. 구조만 뽑게 한다 |
| 새 AI 파이프라인 구축 | ADR-0017·0018·0022가 이미 있다. 얹는다 |

## §6. AI 활용 확장 후보 (가맹점 외)

원칙(§3)을 통과하는 것만 적었다. **"예측하지 않는다"는 이 제품의 강한 원칙이므로,
추정치를 화면에 올리는 아이디어는 여기 없다.**

| # | 후보 | 왜 원칙을 통과하나 | 규모 | 선행 조건 |
|---|---|---|---|---|
| 1 | **가맹점 아이덴티티**(본 문서) | 제안→사람 확정, 근거 제시 가능 | M | 없음 |
| 2 | **카테고리 분류 정밀도 개선** | 이미 분류기·학습 파이프라인이 있고, 사용자 교정이 쌓였다(실측: 93건을 110번 교정) | M | 데이터셋 스냅샷 재생성 |
| 3 | **카드문자 L2 품질 지표** | 이미 `on`이지만 호출량 0(규칙 파서가 100% 성공). 카드사 문구 개편을 조기 감지하는 관측 자산 | S | ADR-0023 §198 지표 정의 |
| 4 | **자연어 질의 지원 축 확대** | 현재 총지출·카테고리·가맹점만 답하고 나머지는 정직하게 거부한다. 거부 로그가 "무엇을 물어보는가"를 이미 세고 있다 | M | 거부 사유 집계 확인 |
| 5 | **문자 원문 → 구조화 재활용** | 원문이 보존돼 있고(삭제 정책 `none` 동결) 파서 회귀검증 자산이다. 새 카드사 대응 시 LLM으로 레시피 초안 생성 | M | ADR-0023 템플릿 레시피 |
| 6 | ⛔ 이상 지출 감지 | "평소보다 많다"는 **추정**이다. 관측만 말하는 원칙과 충돌. 하려면 "지난달 같은 가맹점 대비" 같은 **비교 가능한 사실**로 좁혀야 한다 | — | 원칙 재확인 필요 |

**착수 순서 권장**: 1 → 2 → 4. 1이 2의 입력 품질을 올리고(가맹점이 정리되면 분류
정확도가 오른다), 4는 앞의 둘이 만든 데이터 위에서 답할 수 있는 질문을 늘린다.
