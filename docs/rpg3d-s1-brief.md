# 구현 지시서 — 3D 슬라이스 1: 매력의 가설 (2026-09-08)

> **이번 작업은 구현이다.** 이 하나가 3D 전환 전체의 가설을 검증한다.

## 왜 이것이 첫날인가

사용자가 지금 2D 그래픽을 보고 **"너무 안좋아"**라고 했다. 3D로 가면 나아진다는 것은
**아직 가설이다.** 설계서 §10이 스스로 그렇게 적었다 —
"3D는 매력을 보장하는 결론이 아니라 검증해야 할 표현 가설이다."

그래서 콘텐츠를 연결하기 전에 **화면 하나를 만들어 사용자에게 보인다.**
아니라고 하면 조명·팔레트·비율만 하루 보정하고, 그래도 아니면 3D를 기각한다.

## 이번에 만드는 것 — 슬라이스 1만

설계서 §9의 1일 행이다.

- Three.js **r128** 동봉 (`603,445B`, SHA-256 `9274bbcec8d96168626c732b5d31c775aa8cfb7eaa0599bec0c175908a2c1ce2`)
  — cdnjs `/ajax/libs/three.js/r128/three.min.js`. 라이선스 고지 함께.
- 32×24 단위 지형 높이맵 + 잔디 3톤 vertex color
- **나무 12그루** — `rules.trees`의 실제 좌표
- 반구광 + 방향광 + **부드러운 그림자**(PCFSoftShadowMap 1024²)
- 캐릭터 **1개** — 큰 머리 비율, 툰 2단 셰이딩, 외곽선
- 하늘 반구 + 안개
- **fixture 장면.** 저장 읽기/쓰기 없음, 걷기 없음, 주민·채집·낚시·도감 없음

**슬라이스 2 이후는 손대지 않는다.** 라우트 이동·저장 연결·걷기·콘텐츠는 이번이 아니다.
기존 2D 게임을 지우지 마라 — 판정이 실패하면 그것이 유지된다.

## 반드시 지킬 것

### 이미지 파일 0개
툰 그라디언트 맵은 **런타임 2×1 `DataTexture`**로 만든다(설계서 §6).
이미지 파일 0개와 GPU에 만드는 2픽셀 데이터는 다른 개념이다.
하늘 이미지·HDRI·normal map·PNG를 쓰지 마라.

### r128에 없는 API를 쓰지 마라
설계서가 확인했다 — **`CapsuleGeometry`가 r128에 없다.** 구 + 원기둥을 결합한다.
`outputEncoding=sRGBEncoding`과 `NoToneMapping`이 r128 기준이며 최신
`outputColorSpace`를 섞지 마라. 의심되면 r128 소스 원문을 확인하라.

### 나무·지도 좌표를 새로 만들지 마라
`rpg-rules.js`의 `trees`·`paths`·`water`·`house`가 단일 출처다. 수관 크기만 변주한다.
좌표를 복제하면 2D와 3D가 다른 지도가 된다.

### 후처리를 쓰지 마라
설계서 §6: 화면 전체 OutlinePass·SSAO·Bloom 없음. 외곽선은 뒤집은 hull이다.

## 완료 게이트 — 설계서 §9의 1일 행

**기술 게이트:**
- 360×800(세로)과 800×360(가로) **같은 장면 스크린샷**
- **조명 on/off 비교 스크린샷** — 조명이 이 느낌의 8할이라는 주장을 눈으로 확인
- 대표 모바일 첫 프레임 시간 기록
- `node --check`, DOM 타입 검사 통과
- 기존 2D 테스트가 깨지지 않음

**시각 게이트 — 이것이 본체다:**
- **기존 2D 화면과 같은 크기로 나란히 놓은 비교 이미지**를 만들어라.
  사용자가 판정할 근거다.
- 설계서 §10의 항목별로 스스로 관찰한 것을 적어라 —
  둥근 형태 / 부드러운 접지 / 캐릭터 가독성.
- **"사용자 시각 승인"은 네가 판정할 수 없다.** 스스로 점수를 매겨 통과했다고 쓰지 마라.
  설계서 §10의 문장을 그대로 따른다:
  "시각 평가는 실제 사용자의 판단이며 작성자의 자체 점수만으로 승인됐다고 쓰지 않는다."
  보고서에 **"시각 승인 확인 못 함"**으로 남기고 코디네이터가 사용자에게 전달한다.
