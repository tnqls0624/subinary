# ADR-0024: 결제 실패(declined) 가시성 — 사유 추출 + 묶음 집계 + 반복 알림

## 제목

`declined` 카드 문자를 거래로 승격하지 않는 기존 결정은 유지하고, **이벤트 층에서 사유를
추출·보존**해 반복 실패를 묶음으로 노출한다. 거절을 거래로 만들거나 별도 도메인 테이블을
두지 않는다.

## 상태

2026-08-04 설계·구현 완료. 마이그레이션 `0043`(enum `card_sms_decline_reason` +
`card_sms_events.decline_reason`).

## 배경

`declined`(승인거절)는 Phase 3부터 파서가 판정하고 승격 파이프라인이 **의도적으로
건너뛴다** — 실제 체결이 아니므로 거래로 만들면 소비 집계·목록에 유령 거래가 잡힌다
(`card-sms-parse.processor` §1.1 주석). 이 판단 자체는 옳다.

문제는 그 결과 **앱 어디에도 나타나지 않는다**는 것이었다. 프로덕션 실측(2026-08-04 조사):

| 항목 | 실측값 |
| --- | --- |
| `declined` 이벤트 | 8건 (+ 파싱 실패 테스트 2건) |
| 최대 사건 | `OO피트니스 99,000원` — **7일 연속**(07/19~07/25) 매일 15:00 |
| 그 가맹점 승인 거래 | **0건** |
| 문자에 적힌 사유 | `분실카드 승인거절` — 파서가 **버리고 있었음** |
| 다른 사건 | `STEAMGAMES 10,038원` 거절 → 8/1 `9,900원` 승인(자체 해결) |

해석: 카드를 분실 신고한 뒤 OO피트니스 정기결제 수단을 갱신하지 않아 카드사가 매일 재시도
하다 7일 만에 멈췄다. 99,000원짜리 멤버십이 조용히 끊겼을 가능성이 크고, 앱은 이 7일을
한 번도 보여주지 않았다.

`card_sms_collection_gap`(유입 공백)과 `card_sms_promotion_stalled`(승격 정체)는 각각
"문자가 안 온다" / "승격이 멈췄다"를 감지한다. 거절은 **정상적으로 수집·파싱된 데이터가
설계대로 승격되지 않은** 경우라 두 감시 어디에도 걸리지 않는다.

## 결정

### 1. 거절을 거래로 승격하지 않는다 (기존 유지)

가시성을 얻으려 `card_transactions`에 `status='declined'` 행을 만드는 방법이 가장 쉽지만
채택하지 않는다. 집계 지점이 10곳이고 그중 6곳이 지출 합계인데, 모든 곳에 "declined 제외"
조건을 새로 심어야 한다. `excludedAt`을 도입할 때 이미 같은 종류의 누락 위험을 겪었다.
**거절은 소비가 아니므로 소비 테이블에 두지 않는다**는 원칙이 더 단순하다.

### 2. 사유를 별도 필드로 추출한다

`transactionType='declined'`만으로는 사용자가 아무것도 할 수 없다. 사유마다 조치가 다르다:

| 사유 코드 | 문구 예 | 사용자가 할 일 |
| --- | --- | --- |
| `lost_or_stolen` | 분실카드/도난 | **정기결제 수단 교체** |
| `limit_exceeded` | 한도초과/이용한도 | 한도 조정 또는 다른 카드 |
| `insufficient_balance` | 잔액부족 | 입금 |
| `expired_card` | 유효기간 경과 | 카드 재발급 |
| `suspended` | 이용중지 | 카드사 문의 |
| `invalid_credential` | 비밀번호 오류 | 정보 재입력 |
| `unknown` | (문구 미인식) | — 거절 사실은 확실 |

`unknown`과 `undefined`를 구분한다: `unknown`은 "거절이지만 사유 문구를 못 알아봤다",
`undefined`(NULL)는 "거절이 아니다". 이 구분이 있어야 사유 파싱 실패율을 셀 수 있다.

패턴 순서는 **조치 강도가 큰 것을 앞에** 둔다(`lost_or_stolen` 최우선) — 카드사 문구가
여러 사유를 나열할 때 과소 판정을 피한다.

저장 위치는 `card_sms_events.decline_reason`이다. 거래 테이블에는 행 자체가 없으므로
실패는 이벤트 층에서만 관측된다.

### 3. 반복 시도를 `(가맹점, 금액)`으로 묶는다

카드사는 정기결제 실패를 **매일 재시도**한다. 시도를 낱개로 보여주면 한 사건이 7줄이 되어
다른 실패를 스크롤 밖으로 밀어낸다. `GET /v1/card-sms-events/declines`가 묶어서 준다.

묶음의 `resolvedAt`은 **마지막 거절 이후 같은 가맹점 승인**이 있었는지로 채운다.
자체 해결(STEAMGAMES)과 미해결(OO피트니스)을 갈라야 사용자가 무엇을 해야 할지 안다.
비교 대상은 정규화 + 사용자 별칭까지 적용한 이름이다(ADR-0025의 `merchant_aliases` 반영) —
표기가 다른 같은 가게가 갈라지면 "3번 실패"가 "1번 + 2번"으로 쪼개진다.

정렬은 **미해결 먼저 → 시도 많은 순 → 최근 순**. 조치가 필요한 것이 위로 온다.

### 4. 알림은 2회부터, dedupe는 주 단위

1회 거절은 흔한 일시적 오류(잔액 일시부족·통신)라 알리면 노이즈다. **2회부터** 구조적
문제로 본다.

dedupe를 일 단위로 하면 7일 연속 거절에 알림이 7번 간다. **주 단위**로 두어 푸시는 주
1회로 제한하고, 지속 노출은 앱 내 배너/화면이 담당한다.

생산자는 파싱 프로세서가 아니라 **스케줄러**(`runDeclineAlertCheck`)다. 파싱 경로에 두면
문자 도착마다 집계·중복판정이 붙어 수집이 무거워지고, 무엇보다 "그 뒤 승인됐는지"를 알 수
없다(승인은 나중에 온다). 최대 1분 지연은 이 사건 성격상 무해하다.

알림 kind `decline`은 **가족 활성 구성원 전원**에게 간다 — 공용 카드의 결제수단을 손댈 수
있는 사람이 카드 소유자가 아닐 수 있고, 놓치면 서비스가 끊긴다.

푸시 문구는 사유를 **조치로 번역**해 싣는다(`분실 신고된 카드예요, 결제수단을 바꿔주세요`).
사유 코드를 그대로 노출하면 의미가 없고, 미등록 사유는 힌트 없이 건수만 알린다(문구를
추측해 잘못 안내하지 않는다).

### 5. 운영 경보가 아니라 사용자 알림이다

`collection_gap`/`promotion_stalled`는 `operational_alerts`(외부 webhook)로 간다 —
시스템 결함이고 수신자가 운영자다. 거절은 **사용자의 결제수단 문제**이므로 FCM 사용자
알림이 맞다. 외부 webhook으로 보내면 가맹점·금액이 유출되기도 한다.

## 결과

- 배너(`/dashboard`)는 미해결이 있을 때만 나타나고, 전용 화면은 `/declines`다.
- 거절 사유 파싱은 파서 5케이스 + 통합 2케이스로 검증(card-parsers 80 tests).
- 기존 승격 동작은 바뀌지 않는다 — `declined`는 여전히 거래를 만들지 않는다.

## 대안 검토

**거래로 승격 후 집계 제외**: 6곳의 지출 집계에 조건 추가 필요. 누락 시 유령 지출이 생긴다.
기각.

**별도 `payment_failures` 테이블**: 이벤트에 이미 모든 정보(가맹점·금액·시각·카드·원문)가
있다. 테이블을 추가하면 파싱 결과를 두 곳에 쓰고 동기화 문제가 생긴다. 기각.

**즉시 알림(파싱 시점)**: 해결 여부를 알 수 없고 수집 경로가 무거워진다. 기각.
