# ADR-0038: iPhone 카드 문자는 App Intent로 전달받는다

## 상태

제안 (2026-11-11). 자동화 조건(결정 3)은 `결정 필요`. 관련: ADR-0007, ADR-0016, [`public-launch-plan-2026-11.md`](../public-launch-plan-2026-11.md) 3장.

## 배경

공개 서비스 오픈 계획은 "앱의 가이드를 따라 하면 iPhone 카드 문자도 자동으로 들어온다"를 핵심으로 정했다. 지금 iPhone 경로는 사용자가 만든 단축어가 'URL 콘텐츠 가져오기' 동작으로 토큰 경로(`POST /v1/mobile-events/card-sms-token`, ADR-0016)를 직접 부른다. 공개 서비스에서는 이 방식에 네 가지 문제가 있다.

1. 사용자가 주소, 헤더, 본문 항목을 단축어의 칸마다 옮겨 적어야 한다. 단계가 많고 틀리기 쉽다.
2. 수집 토큰이 단축어 안에 평문으로 남는다. 단축어를 공유하거나 캡처하면 그대로 샌다. 토큰을 회전하면 사용자가 단축어를 다시 고쳐야 한다.
3. 전송에 실패하면 그 문자는 가계부에 들어오지 않고 끝난다. 단축어는 스스로 재시도하지 않는다.
4. 자동화 조건에 따라 인증번호처럼 카드 문자가 아닌 문자도 서버로 갈 수 있다.

iOS에는 다른 길이 없다.

- 앱이 문자함을 읽거나 수신 이벤트를 받는 공개 API가 없다.
- 메시지 필터 확장은 문자를 서버로 보내지만, 사용자를 알 수 있는 정보를 빼고 보낸다. 어느 계정의 문자인지 알 수 없어서 수집에 쓸 수 없다.
- 앱이 사용자의 단축어 자동화를 대신 만들 수도 없다.

그래서 '문자가 오면 실행'하는 트리거는 계속 사용자가 만든 단축어 자동화가 맡는다. 바꿀 수 있는 것은 그 자동화 안에서 실행되는 동작이다.

## 결정

### 1. 단축어는 문자를 앱에 넘기고, 전송은 앱이 한다

- iOS 앱에 App Intent '카드 문자 기록'을 만든다. 입력은 문자 내용과 보낸 사람이다.
- App Shortcuts로 등록해서, 앱을 설치하면 단축어 앱의 동작 목록에 바로 보이게 한다.
- 사용자는 자동화에 이 동작 하나를 넣고 입력에 '단축어 입력'을 연결한다 `[확인 필요: 실제 단축어 앱의 표시 이름]`.

### 2. 카드 문자인지는 기기 안에서 판별한다

- 자동화 조건(결정 3)과 상관없이, App Intent는 문자 내용과 보낸 사람을 보고 카드 승인·취소 문자인지 판별한다. 아니면 기기 밖으로 보내지 않는다.
- 판별이 확실하지 않은 문자도 보내지 않는다. 개인정보를 우선한다. 이렇게 놓친 거래는 사용자가 알아차렸을 때 붙여넣기 기록으로 채운다. 보내지 않은 문자는 서버도 Signal Doctor도 알 수 없다.
- 기기 안 판별은 '카드 문자인가'만 정한다. 금액, 가맹점, 카드를 뽑아내는 일은 지금처럼 서버의 카드사별 파서가 한다.
- 판별 규칙도 서버 파서와 같은 테스트 fixture(`packages/card-parsers`)로 시험한다.

### 3. 자동화 조건 `결정 필요`

| 안 | 방법 | 판단 |
|---|---|---|
| A. 조건 없음 (추천) | 모든 메시지에 자동화를 실행한다 | 사용자가 넣을 조건이 없다. 인증번호·광고 문자에도 실행되지만 결정 2의 판별로 걸러 낸다. 배터리와 실행 알림 영향은 실기기로 확인한다 (검증 계획) |
| B. 키워드 조건 | '승인', '취소' 등이 든 메시지만 실행 | 키워드마다 자동화를 따로 만들어야 할 수 있다 `[확인 필요]`. 문구가 다른 카드사를 놓친다 |
| C. 발신자 조건 | 카드사 번호에서 온 메시지만 실행 | 카드사 번호를 연락처에 저장해야 고를 수 있을 것으로 보인다 `[확인 필요]`. 카드사마다 번호가 여럿이다 |

### 4. 전송은 기존 HMAC 경로를 쓴다

- 서버 수집 API는 새로 만들지 않는다. `POST /v1/mobile-events/card-sms`(ADR-0007)를 그대로 쓴다. 단축어로는 HMAC을 계산하기 어려워서 토큰 경로를 만들었지만, Swift에서는 계산이 쉽다. 본문 위변조 검사와 nonce를 이용한 재전송 공격(replay) 차단을 되찾는다.
- 다만 이 경로를 실제로 호출하는 클라이언트는 이번이 처음이다. ADR-0007 'HMAC 경로 실사용 현황'(2026-08-10)에 따르면 `device_nonces`가 0행인, 호출되지 않는 예비 경로였다. 그래서 서버 서명 검증(본문 바이트 일치, 시계 오차, nonce 저장)도 함께 검증한다.
- 장치 비밀값은 장치 등록·회전 응답을 받을 때 네이티브 플러그인이 키체인에 저장한다. 접근 수준은 '첫 잠금 해제 이후, 이 기기 전용'(`kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`)으로 둔다. 화면이 잠긴 상태에서도 전송해야 하기 때문이다.
- 웹 화면에는 비밀값을 보여 주지 않는다. ADR-0007의 '등록·회전 응답에서 한 번만 노출' 규약은 그대로다.
- 다른 장치나 웹에서 이 장치의 비밀값을 회전하면, 새 비밀값이 이 iPhone 키체인에 들어오지 않는다. 그러면 전송이 401로 실패한다. 앱은 401을 받으면 대기열을 유지한 채 '이 iPhone 다시 연결하기'를 안내하고, Signal Doctor도 같은 원인을 보여 준다. iPhone 장치의 회전은 그 iPhone 앱에서 하도록 안내한다.

### 5. eventId, receivedAt, 대기열

- `eventId`는 App Intent가 실행될 때 문자마다 새로 만든다(UUID). `receivedAt`은 App Intent가 실행된 시각으로 채운다. 단축어는 정확한 수신 시각을 넘겨주지 않을 수 있다 `[확인 필요]`.
- 두 값은 처음 만든 값을 끝까지 유지한다. `docs/api/card-sms.md`의 '문자마다 다르고, 같은 문자를 다시 보낼 때는 같다' 계약을 따른다.
- 전송에 실패하면 문자를 `eventId`, `receivedAt`과 함께 기기 안 대기열에 저장한다. 다시 보낼 때는 `X-Timestamp`, `X-Nonce`, 서명만 새로 만든다. ADR-0007은 타임스탬프 허용 오차가 300초이고 nonce를 한 번만 쓸 수 있어서, 처음 만든 요청을 그대로 다시 보내면 계속 401이 난다. `receivedAt`을 다시 보내는 시각으로 바꾸면 늦게 들어간 문자의 연도 보정 기준이 틀어진다.
- 대기열 파일은 '첫 잠금 해제 이후' 데이터 보호 등급(`FileProtectionType.completeUntilFirstUserAuthentication`)으로 둔다. 재부팅 뒤 첫 잠금 해제 전에는 키체인도 대기열 파일도 열 수 없으므로, 그 사이에 온 문자는 놓칠 수 있다.
- 다시 보내는 시점은 다음 App Intent 실행 때와 앱이 열릴 때다. 백그라운드에서 재시도를 확실하게 시작할 수단은 없다 `[확인 필요: 백그라운드 작업 예약(BGTaskScheduler)으로 잡은 재시도가 실제로 실행되는지]`.

### 6. 구현 위치

- 판별, 서명, 전송, 대기열은 전부 Swift로 짠다. App Intent가 백그라운드에서 실행될 때는 웹뷰(JS)가 떠 있지 않다.
- Capacitor 네이티브 플러그인 하나로 묶는다. 웹은 장치 등록·회전 응답을 플러그인에 넘기는 일만 한다.
- iOS 26 이상은 `supportedModes`로 백그라운드 실행을 지정한다. 그보다 낮은 버전은 `openAppWhenRun = false`를 쓴다.

### 7. 기존 경로와 운영

- 토큰 경로(ADR-0016)는 유지한다. MacroDroid는 HMAC을 계산하기 어려워서 계속 토큰 경로를 쓴다. 이미 설정된 단축어도 계속 동작한다.
- 장치마다 수집 방식(App Intent / 단축어 직접 호출 / MacroDroid)을 기록한다. 운영 화면에서 어느 장치가 어느 경로를 쓰는지 보고, iPhone에서 단축어 직접 호출 방식을 접을 시점을 판단한다.
- Signal Doctor(`apps/web/src/lib/device-signal.ts`)에 iPhone 전용 원인을 더한다: 자동화가 '실행 전에 묻기'로 바뀜, 자동화 삭제, 재부팅 뒤 첫 잠금 해제 전, 카드 알림이 문자가 아닌 앱 푸시나 알림톡으로 옴, 다른 곳에서 비밀값을 회전해 401이 남.

## 고려한 대안

| 대안 | 기각 이유 |
|---|---|
| 지금 방식 유지 (단축어가 직접 호출) | 개발할 것은 없지만, 배경의 네 가지 문제가 그대로 남는다 |
| 메시지 필터 확장 | 서버로 가는 문자에 사용자 정보가 없어 계정에 연결할 수 없다. 원래 용도(스팸 분류)를 벗어나 앱 심사 위험이 있다 |
| Mac 중계 (문자 메시지 전달 + Mac 프로그램이 메시지 데이터베이스를 읽음) | Mac이 늘 켜져 있어야 한다. 모든 메시지를 읽는 권한이 필요해서 공개 서비스에 맞지 않는다 |
| 통신사 문자 착신전환 | 통신사 안내상 결제·인증 문자는 전달되지 않을 수 있다. 원래 휴대폰에서 문자를 못 받게 될 수 있다 |

## 결과

**좋아지는 점**

- 사용자가 단축어에 채우는 칸이 7~8개에서 1개로 준다.
- 토큰과 비밀값이 단축어에 남지 않는다. 이 iPhone의 앱에서 회전하면 사용자가 할 일이 없다. 다른 장치나 웹에서 회전하면 다시 연결해야 한다 (결정 4).
- 실패한 문자를 다시 보낸다.
- 카드 문자가 아닌 문자는 기기 밖으로 나가지 않는다.

**치르는 비용**

- 우리 iOS 앱을 설치해야만 이 경로를 쓸 수 있다. 지금 방식은 앱 없이도 된다.
- Swift 코드가 생긴다: 판별 규칙, 서명, 대기열. 판별 규칙은 서버 파서와 따로 유지해야 한다.
- 단축어 앱 화면이 iOS 버전마다 달라서 가이드를 버전별로 관리해야 한다.
- 지금까지 쓰이지 않던 HMAC 경로를 운영에서 처음 쓴다.

## 검증 계획

| 시험 | 확인할 것 |
|---|---|
| 지원하는 iOS 버전마다 | '즉시 실행'으로 설정해도 확인 창이 뜨지 않는가 `[확인 필요]` |
| A안으로 하루 이상 사용 | 배터리 사용량, 문자마다 실행 알림이 뜨는가 |
| 화면 잠금 상태 | 정상 전송되는가 |
| 재부팅 후 첫 잠금 해제 전 | 키체인도 대기열 파일도 열 수 없을 때 문자가 어떻게 되는가 (놓쳤다면 Signal Doctor가 알려 주는가) |
| 1분 안에 문자 두 통 | 둘 다 기록되고 `eventId`가 겹치지 않는가 |
| 장문 문자, 해외 결제 문자 | 잘리지 않는가 |
| 모바일 데이터와 Wi-Fi를 끈 상태 (문자는 오고 인터넷만 끊김) | 대기열에 쌓였다가 연결이 돌아오면 다시 보내는가. 다시 보낼 때 타임스탬프·nonce·서명은 새로 만들고 `eventId`·`receivedAt`은 유지하는가 |
| 저전력 모드 | 실행이 늦어지거나 빠지지 않는가 |
| 인증번호·광고 문자 | 기기 밖으로 나가지 않는가 |
| 이 iPhone 앱에서 회전 | 단축어를 고치지 않아도 계속 전송되는가 |
| 다른 장치나 웹에서 회전 | 401을 받고 대기열을 유지한 채 다시 연결을 안내하는가 |
| 서버 HMAC 검증 (첫 실사용) | 본문 바이트 일치, 기기와 서버의 시계 오차, nonce 저장이 실제 클라이언트로 동작하는가 |
