# ADR-0032: Slack Export ZIP 업로드 — 두 겹 방어 · 워커 해제 · 관찰 가능한 import 상태

## 제목

Slack Export **ZIP을 서버가 직접 받아** 워커에서 해제·변환하고(단일 JSON 번들 경로는
유지), 압축 폭탄·경로 탈출을 **선검사 + 해제 중 하드 캡** 두 겹으로 막으며, import를
`slack_imports` 테이블(마이그레이션 `0054`)로 **`queued | processing | completed | failed`**
관찰 가능하게 만드는 설계 채택. ADR-0011 §1의 "ZIP 아님" 결정을 **대체한다**.

## 상태

승인됨 (Accepted) — 2026-08-13. **ADR-0011 §1을 대체(supersede)한다.** ADR-0011의
나머지 결정(§2 소유자 전용 경계, §3 멱등 import, §4 스레드 복원, §5 trgm 검색)은 그대로 유효하다.

## 배경

운영에 **workspace 0개 · 메시지 0건**이다. 업무 기억 화면은 정직한 빈 상태를 보여주고
있지만 **사용자가 데이터를 넣을 방법이 아예 없다.**

ADR-0011 §1은 "클라이언트가 Slack export ZIP을 풀어 하나의 JSON 번들로 합쳐 올린다"를
전제했다. 그 전제의 대가가 지금 드러났다.

- 서버는 업로드를 **UTF-8 문자열로 바꿔 `JSON.parse`** 한다(`slack.service.ts`의
  `parseBundleShallow`). ZIP을 올리면 400이다.
- 즉 사용자는 Slack에서 받은 ZIP을 풀고, `channels.json`·`users.json`·채널 디렉터리의
  날짜별 파일 수백~수천 개를 읽어, **날짜 파일에는 없는 `channel` 필드를 채워 가며**
  하나의 JSON으로 합쳐야 한다. 일반 사용자가 할 수 있는 일이 아니다.
- 업로드 응답은 **항상 `queued`**이고(`packages/contracts/src/slack.ts`), `importId`는
  `source_items.id`인데 그 테이블에 상태 컬럼이 없다. 구조 검증은 워커에서 하므로
  (`slack-import.processor.ts`) **HTTP 200 뒤에 실패할 수 있고, 사용자는 이유를 영영
  알 수 없다.**

PO 판정(Q3)은 이 상태에서 업로드 UI를 여는 것을 "성공할 수 없는 약속"이라 보고 보류하되,
열기 위한 **선행 조건 5가지**를 명시했다: ① 실제 ZIP 파서, ② 해제 후 총 크기·엔트리
수·개별 크기 제한과 zip-slip/zip-bomb 방어, ③ 전부-buffering 제거 **또는** 동시 업로드
메모리 예산, ④ `importId` 기준 상태·안전한 error code·처리 count·재시도 UI,
⑤ 실패·새로고침 뒤에도 복구되는 폴링 계약. 이 ADR은 그 5가지를 어떻게 채웠는지에 대한 결정이다.

**성격**: 이것은 기능 추가가 아니라 **신뢰 경계를 여는 일**이다. 업로드 파일은 사용자가
준 것이고 사용자는 실수하거나 악의적일 수 있다. ZIP은 특히 위험한 형식이다.

## 결정

### 1. ZIP과 단일 JSON을 **둘 다** 받는다 — 판별은 매직 바이트

- `POST /v1/slack/import`이 `PK\x03\x04`(및 빈/분할 시그니처)로 시작하면 ZIP, 아니면 기존
  단일 JSON 번들로 다룬다. **content-type·확장자를 분기 근거로 쓰지 않는다** — 둘 다
  사용자가 마음대로 쓸 수 있다.
- 기존 JSON 경로는 **동작이 바뀌지 않는다.** 고급 사용자·스크립트가 쓰고 있을 수 있고,
  ADR-0011 §1의 번들 계약은 그대로 유효하다.
- 응답에 `format: 'json' | 'zip'`을 추가한다(서버가 무엇으로 읽었는지 사용자가 확인 가능).

### 2. 해제는 **워커**에서 한다. API는 풀지 않는다

- API는 ZIP을 **압축된 채로** MinIO에 저장하고(`slack/<ws>/<id>.zip`) outbox로 넘긴다.
  해제는 CPU·메모리를 쓰는 작업이고, API는 사용자 요청을 붙잡고 있는 프로세스다.
  무거운 일은 이미 MinIO 원문을 읽어 파싱하는 워커의 몫이다(ADR-0011 §3 패턴 계승).
- 다만 API는 **압축을 풀지 않고 central directory만 읽어 선검사**한다. 여기서 걸리는
  아카이브는 CPU를 한 바이트도 쓰지 않고 **즉시 400**으로 돌아간다 — 비동기 실패로
  미루면 사용자는 한참 뒤에야 이유를 알게 된다.

### 3. 방어는 **두 겹**이다 (선검사 + 해제 중 하드 캡)

`packages/slack-parser/src/zip.ts`가 소유한다.

| 겹 | 무엇을 보는가 | 왜 |
|---|---|---|
| ① central directory 선검사 | 엔트리 이름·개수·**선언된** 크기·**선언된** 압축비 | 압축을 풀기 전에 명백한 것을 막는다(무비용) |
| ② `inflateRawSync({ maxOutputLength })` | **실제 출력 바이트** | 선언 크기는 **공격자가 쓴 값**이다. 거짓말한 헤더는 ①을 그냥 통과한다 |

①만 두면 헤더에 거짓을 쓴 폭탄에 뚫리고, ②만 두면 뚫리진 않지만 매번 CPU를 쓴다.
둘 다 한다. `zip.test.ts`가 "선언 크기를 10바이트라고 거짓말한 폭탄"으로 이 경계를 고정한다.

**거절 목록** — 하나라도 걸리면 **아카이브 전체를 실패**시킨다(일부만 처리하면 사용자는
전부 들어온 줄 안다):

- 경로 탈출(zip-slip): `..` 세그먼트 · 절대경로 · 드라이브 문자 · 역슬래시 · NUL
- 심볼릭 링크 엔트리(Unix mode `S_IFLNK`)
- 암호화 엔트리(general purpose bit 0/6)
- deflate/stored 이외의 압축 방식, Zip64, 멀티디스크
- CRC-32 불일치(손상된 업로드)

**역슬래시를 구분자로 되돌리지 않고 거절하는 이유**: `a\..\..\b`는 OS마다 다르게 해석돼,
검사기와 사용처의 해석이 갈리는 순간이 정확히 zip-slip이 뚫리는 지점이다.

**디스크에 풀지 않는데도 경로를 검사하는 이유**: 엔트리 이름을 경로로 쓰는 코드가 나중에
하나라도 생기면 그 순간 취약점이 된다. "이름을 신뢰하지 않는다"를 리더 안에 두면 그
실수가 불가능해진다.

### 4. 상한은 상수로 노출하고, 근거와 함께 `[가설]`로 표시한다

`DEFAULT_ZIP_LIMITS` (`packages/slack-parser/src/zip.ts`):

| 값 | 상한 | 근거 |
|---|---|---|
| 압축 파일 크기 | 50 MiB | 기존 `main.ts` multipart 상한(변경 없음) |
| 엔트리 개수 | 20,000 | Export는 채널당 **활동한 날짜마다 파일 1개**. 55채널×365일 또는 20채널×2.7년 |
| 엔트리 개별 해제 크기 | 32 MiB | 가장 큰 단일 파일은 `users.json`이고 대형 워크스페이스도 한 자릿수 MB |
| 누적 해제 크기 | 128 MiB | **워커 메모리 예산**. JSON 텍스트를 파싱하면 JS 객체가 2~5배로 부푼다 |
| 엔트리 압축비 | 200:1 | 텍스트 JSON은 보통 5~20배. 200배는 정상 Export가 아니다 |
| 압축비 검사 하한 | 4 KiB | 수십 바이트 파일은 헤더 오버헤드로 비율이 무의미 — 정상 파일을 막지 않기 위해 |

**전부 `[가설]`이다.** 저장소에 운영 Slack Export 크기 분포가 없다(PO 판정 Q3의 "모름").
정상 사용자가 막히면 이 상수를 근거와 함께 올린다. `누적 해제 크기`를 올릴 때는 워커
컨테이너 메모리를 함께 재검토해야 한다.

### 5. API 메모리는 **동시 업로드 예산**으로 막는다 (전부-buffering은 유지)

PO 판정 Q3-4는 "전부-buffering 제거 **또는** 동시 업로드 메모리 예산"을 요구했다.
후자를 택했다.

- 진짜 스트리밍(multipart → MinIO)은 `PutObject`에 길이를 미리 주거나
  `@aws-sdk/lib-storage`가 필요하다 — 새 의존성이고, 이번 작업의 위험을 **저장 계층
  재작성까지** 넓힌다. 신뢰 경계를 여는 변경에서 동시에 손댈 표면이 아니다.
- 대신 상한을 숫자로 못 박는다: 프로세스 전역 **150 MiB**(= 50 MiB × 3). 읽기 **전에**
  최악값(파일 1건 상한)으로 예약하고, 넘으면 **503 + `Retry-After`**로 돌려보낸다.
  사용자가 뭘 잘못한 게 아니라 서버가 지금 여유가 없는 것이라 429가 아니다.
- 예약 단위가 실제 크기가 아니라 최악값인 이유: 스트림을 다 읽기 전에는 크기를 모른다.
  모르는 값을 낙관적으로 가정하지 않는다.

### 6. import 상태를 DB에 둔다 (`slack_imports`, 마이그레이션 `0054`)

- `queued | processing | completed | failed` + **안전한 error code** + 처리 건수 +
  `queuedAt`/`startedAt`/`finishedAt`.
- 신원은 `source_item_id`(= 응답의 `importId`)이고 **UNIQUE**다 — 워커 재시도가 행을 늘리지 않는다.
- `GET /v1/slack/imports/:importId`로 조회한다. **owner 전용 경계 유지** — import 행을
  찾은 뒤 그 워크스페이스 소유권을 `requireOwnedSlackWorkspace`로 다시 확인한다.
- **BullMQ 잡 상태에 기대지 않는다.** 잡은 `removeOnComplete: { count: 1_000 }`으로
  사라진다(다른 큐에서 이미 겪은 함정). 새로고침·앱 재시작 뒤에도 복구돼야 하는 값이다.
- 상태 행은 outbox event와 **같은 트랜잭션**에서 만든다. 갈라지면 "잡은 도는데 조회할
  행이 없거나(404), 행은 있는데 잡이 없는(영원한 queued)" 상태가 된다.

**`error_code`는 닫힌 어휘다.** 서버 예외 메시지를 그대로 저장하면 객체 키·파일 경로·
JSON 조각이 사용자 화면까지 새어 나간다(이 저장소의 로깅 규약 위반). 분류되지 않은
실패는 전부 `internal_error`로 접고 상세는 **로그에만** 남긴다. 자유 텍스트 컬럼을
**일부러 만들지 않았다**.

**건수 컬럼은 nullable이다.** `completed` 전에는 모르는 것이고, "모른다"와 "0건"은 다른 사실이다.

### 7. ZIP → 번들 변환은 기존 파서 위에 얹는다

- `parseSlackExport(bundle)`는 검증된 자산이다(구조 검증·정규화·스레드 그룹핑·secret 경고).
  **새 파서를 만들지 않고** ZIP을 그 파서가 받는 입력으로 바꾼다
  (`packages/slack-parser/src/export-zip.ts`). 정규화 규칙이 두 벌이 되면 JSON 업로드와
  ZIP 업로드가 서로 다른 결과를 낳는다.
- 단일 JSON 번들과 실제 Export의 결정적 차이 두 가지를 변환기가 흡수한다.
  1. **날짜 파일의 메시지에는 `channel` 필드가 없다.** 소속 채널은 **디렉터리 이름**이고,
     그 이름을 `channels.json`의 `name`으로 찾아 채널 **id**로 바꾼다.
  2. **편집 시각이 `edited: { user, ts }` 객체다.** 번들 계약의 `edited_ts` 문자열로 편다.
- `groups.json`·`mpims.json`이 있으면 채널 목록에 병합한다(비공개 채널 복구).
  `dms.json`(1:1 DM)은 이번 범위 밖이다 — 이름이 없고 가장 민감하다.
- 엔트리를 **한 번에 하나씩** 풀어 JSON으로 바꾸고 텍스트는 즉시 버린다. 아카이브를
  통째로 이어붙이지 않는다 — 그게 zip-bomb의 표적이다.

### 8. 워크스페이스 신원은 ZIP에서 추측하지 않는다

Slack Export ZIP에는 **워크스페이스 표시명을 담은 표준 파일이 없다.** 그래서:

- 이름은 `workspaceName` 필드(웹이 항상 보낸다) → 업로드 **파일 이름**에서 유도 →
  기본값 `'Slack'` 순으로 정한다.
- ZIP 경로의 `slackTeamId`는 **null로 둔다.** `users.json`의 `team_id`를 읽어 채울 수도
  있지만, 그러면 워커가 나중에 team id를 채워 넣게 되고 **두 번째 import가 이름으로도
  team id로도 매칭되지 않아 워크스페이스를 하나 더 만든다.** ZIP-origin 워크스페이스는
  **이름으로 매칭**한다(같은 이름 = 같은 워크스페이스).
- 파일 이름 폴백이 없으면 모든 ZIP import가 기본 이름 하나로 뭉쳐 서로 다른
  워크스페이스가 한 컨테이너에 섞인다 — 조용한 데이터 오염이라 막아야 한다.

### 9. 웹은 결과를 확인하고 나서 말한다

- `.zip`을 허용한다(PO 판정 Q3-5의 조건이 충족됐다).
- 업로드 응답만으로 성공이라 말하지 않는다. `GET /v1/slack/imports/:id`를 폴링해
  **완료/실패를 실제로 확인**한 뒤 표시한다. 폴링은 30초까지 2초, 이후 5초 간격이고
  10분에 자동 갱신을 멈춘다.
- **10분을 넘겨도 "실패"라고 말하지 않는다.** 처리 시간 SLO는 **모름**이다(문서의 10초는
  폴링 권장 상한이지 완료 보장이 아니다). 자동 갱신만 멈추고 "다시 확인"을 남긴다 —
  아직 도는 작업을 실패라고 부르는 것이 더 나쁜 거짓말이다.
- 실패는 코드별 **행동 가능한 한국어 문구**로 바꾼다. "실패했어요"만으로는 다시 시도할 수 없다.
- **화면을 벗어나도 결과를 잃지 않는다**: `importId`를 로컬에 적어 두고 돌아오면 폴링을
  잇는다. 저장되는 것은 **식별자(UUID)와 시각뿐**이고, 키를 userId로 나누고 24시간 TTL을
  둔다. 조회가 403/404면 그 자리에서 지운다(로그아웃 훅에 기대지 않는 자기 치유 경로).
- **전송 중에는 이어받을 수 없다.** 그 사실을 업로드 중 문구로 미리 알린다 — 조용히
  실패하게 두지 않는다.

## 검토한 대안

1. **ZIP 해제 라이브러리 도입** — `yauzl`/`adm-zip`/`unzipper` 등. 대부분 **압축 해제
   도중 출력 상한을 걸 지점을 노출하지 않아**, 폭탄을 막으려면 결국 라이브러리 밖에서
   감시해야 한다. 그리고 이 경로는 신뢰 경계라 의존성 자체가 감사 대상이 된다. Node
   내장 `zlib.inflateRawSync({ maxOutputLength })`가 필요한 상한을 **inflate 루프 안에서**
   강제하므로 그 위에 얇게 얹었다. 새 의존성(=락파일 변경)도 만들지 않는다.
2. **API에서 해제** — 사용자가 즉시 정확한 오류를 받는다. 그러나 해제는 CPU·메모리
   작업이고 API 프로세스는 요청을 붙잡고 있다. 폭탄 한 발이 API 전체를 흔든다.
   **선검사만 API, 해제는 워커**로 갈랐다.
3. **클라이언트(브라우저)에서 ZIP을 풀어 JSON으로 변환** — 서버 표면이 안 늘어난다.
   그러나 대형 Export를 브라우저 메모리에서 푸는 것은 모바일 웹뷰에서 특히 위험하고,
   **검증을 클라이언트에 두는 것은 검증이 아니다**(악의적 클라이언트는 그냥 건너뛴다).
4. **상태를 BullMQ 잡에서 읽기** — 새 테이블이 필요 없다. 그러나 잡은
   `removeOnComplete`로 사라져 새로고침 뒤 상태가 증발한다. PO 판정 Q3-4가 명시적으로
   금지한 것이다.
5. **`source_items`에 상태 컬럼 추가** — 그 테이블은 카드 문자와 공유한다. Slack 전용
   상태·건수를 넣으면 카드 경로가 영원히 NULL인 컬럼을 들고 다니고, 소스 종류마다
   컬럼이 또 는다. 종류별 상태는 종류별 테이블에 뒀다.
6. **`error_code` 대신 예외 메시지 저장** — 디버깅은 쉽다. 그러나 그 값이 그대로 사용자
   화면까지 가고, 예외 메시지에는 경로·원문 조각이 섞인다. 닫힌 어휘 + 로그 분리로 갈랐다.
7. **DM(`dms.json`)까지 가져오기** — 업무 기억의 커버리지가 넓어진다. 그러나 DM은 이름이
   없어 채널 매핑이 불가능하고 가장 민감한 데이터다. 이번 범위에서 뺐다.

## 장점

- 사용자가 Slack에서 받은 파일을 **그대로** 올릴 수 있다. C-6의 실질적 진입 장벽이 사라진다.
- 방어가 순수 패키지 한 곳(`zip.ts`)에 모여 있고 **공격 아카이브를 직접 조립하는 테스트**가
  경계를 고정한다(zip-slip·심볼릭 링크·암호화·개수·크기·누적·압축비·거짓 헤더·CRC).
- 정상 Export가 통과하는 것을 같은 테스트 파일이 함께 증명한다 — 정상 사용자를 막는
  방어는 실패라는 기준이 코드에 남는다.
- 실패가 **관찰 가능**해졌다. 200 뒤의 침묵이 사라지고, 새로고침·앱 재시작 뒤에도 복구된다.
- 기존 JSON 업로드 경로가 그대로 살아 있어 스크립트·고급 사용자가 깨지지 않는다.
- 상한이 전부 상수로 노출돼 있어, 정상 사용자가 막혔을 때 **어디를 올려야 하는지가 명확**하다.

## 단점

- ZIP 리더를 직접 유지해야 한다(Zip64·데이터 디스크립터 등 형식의 일부를 의도적으로
  지원하지 않는다). 형식 확장이 필요하면 이 파일을 고쳐야 한다.
- API가 여전히 파일 전체를 메모리에 올린다. 상한은 예산으로 못 박았지만 진짜 스트리밍은 아니다.
- 워커가 해제 결과를 **최대 128 MiB까지 메모리에 들고** 있다(그 뒤 JSON 객체로 다시 부푼다).
  더 큰 Export는 청크 스트리밍 파싱이 필요하다.
- **실제 Slack Export 샘플로 대조하지 못했다.** 구조는 공개 문서·형식 지식에 근거하며,
  변환기는 "모르면 실패"하도록 만들었지만(필수 파일 부재 시 명확한 코드) 실물 검증 전까지
  이 부분은 `[확인 필요]`다.
- DM·`integration_logs.json`은 가져오지 않는다.

## 변경조건

- **실제 Export로 검증되면** `export-zip.ts`의 "⚠️ 확인 필요" 주석과 리포트의 해당 항목을
  지운다. 구조가 다르면 변환기를 고치되 `parseSlackExport` 계약은 유지한다.
- 정상 사용자가 상한에 막히면 `DEFAULT_ZIP_LIMITS`를 근거(실제 파일 크기)와 함께 올린다.
  누적 상한을 올릴 때는 **워커 컨테이너 메모리를 함께** 재검토한다.
- 동시 업로드 503이 실제로 관측되면 `SLACK_UPLOAD_MEMORY_BUDGET_BYTES`를 올리거나
  진짜 스트리밍(`@aws-sdk/lib-storage`)으로 전환한다. 그때도 상한은 남긴다.
- 처리 시간 SLO가 관측으로 확정되면 웹의 `POLL_GIVE_UP_MS`와 문구를 그 값에 맞춘다.
- DM 가져오기가 필요해지면 별도 동의·범위 결정을 먼저 하고 연다(개인 대화는 다른 층위다).
