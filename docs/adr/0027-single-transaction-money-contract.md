# ADR-0027: 단일 거래 금액 계약 — 역사 환율 스냅샷 · 원통화 취소 상계 · 액션 근거 파싱

## 제목

거래를 만드는 자동 승격·수동 입력·사람 검토와 금액을 바꾸는 취소 연결·수정 경로가 모두
`TransactionMoneyService`를 통과하게 한다. 외화는 거래일의 불변 환율 스냅샷으로 KRW 환산하고,
취소는 원통화 잔액으로 연결한 뒤 승인 환율로 상계한다. 자동 파싱 금액은 거래 액션에 결박된 원문
span이 있을 때만 이 서비스에 들어올 수 있다.

## 상태

승인됨 (Accepted) — 2026-08-08 제안, 2026-08-18 enforce 배선 완료. 이 문서는 ADR-0009의
금액·취소 규약을 보강하고 ADR-0026의 지출 합계 정의는 유지한다.

### 7단계 결과 (2026-09-03)

회귀 기준("수리 전후 월 합계 차이 = 수리 로그의 행별 delta 합")이 **양변 모두 0**으로
성립했다. auto 경로가 금액 축을 건드리지 않도록 설계했으므로 이것은 우연이 아니라 구조다.

실행 중 두 번 멈췄고, 두 번 다 설계를 교정했다(아래 §3 구현 노트). 그 과정에서 57건이
반쪽 적용된 상태로 남았지만 전부 delta 0이라 사용자에게 보이는 값은 한 번도 흔들리지
않았다 — **"자동 적용은 금액을 바꾸지 않는다"는 제약이 실패를 무해하게 만들었다.**

### 4단계에서 배운 것 — shadow만으로는 게이트가 닫히지 않는다

전환 조건(3단계)은 "delta 0건" 꼴인데, **표본이 0이어도 delta는 0**이다. 실제로 2026-08-18
판정에서 6개 쓰기 경로 중 2개만 관측됐고 외화는 한 건도 없었다. 원인은 shadow의 구조다 —
`observe()`는 쓰기 **직후**에 불리므로 관측 표본이 "배포 이후 손댄 거래"로 제한되고, 쓰지 않는
경로(수동 입력·취소 연결)와 오래된 거래는 **기다려도 표본에 들어오지 않는다.**

그래서 4단계에 재생을 넣었다(`scripts/replay-money-contract.mjs`). 같은 관찰기를 기존 행
전체에 돌리되 sink를 메모리로 갈아끼워 아무것도 쓰지 않는다. 179건 전수에서 순액 delta 0건,
`match` 178 · `link_manual_only` 1(설계대로)이었다.

게이트에는 `N/A` 상태를 추가했다 — **UNVERIFIED와 엄격히 구분한다.** "확인하지 못했다"가
아니라 "그 성격의 행이 운영에 0건임을 확인했다"(= 전환이 바꿀 기존 결과가 없다)일 때만 붙인다.
그 경로가 처음 쓰일 때의 정확성은 게이트가 아니라 도메인 단위 테스트가 담보한다.

외화는 표본 부족이 아니라 **공급자 미배선**이 원인이었다. `fx_rate_snapshots`는 `0049`로
만들어졌는데 `fixate()` 호출부가 저장소에 0건이라 테이블이 비어 있었고, 스냅샷이 없으면
계획기는 외화를 `fx_snapshot_missing`으로 거절한다. 역사 환율 공급자를 새로 붙이는 대신
v1 거래에 **이미 적용된** 환율을 그 기준일의 스냅샷으로 승격했다
(`scripts/fixate-legacy-fx-snapshots.mjs`). 값의 교정이 아니라 **재계산해도 흔들리지 않게**
만드는 것이 §3의 목적이므로, 사용자가 본 금액은 그대로 두는 이 방향이 맞다. 고정 전후 재생에서
delta가 0으로 유지된 것이 그 검증이다.

## 배경

### 1. 금액 계약이 경로마다 갈라졌다

ADR-0009는 모든 거래를 KRW 정수로 저장하고, 승인 거래는
`netAmount = amount - cancelledAmount`, 취소 거래는 `netAmount = 0`으로 두기로 했다. 자동
승격은 이 규약에 맞춰 외화를 환산하고 취소를 승인에 연결한다. 그러나 나중에 추가된 수동 입력과
사람 검토는 자동 승격의 금액 로직을 재사용하지 않고 `card_transactions`를 직접 쓴다.

확정된 P0 네 건은 다음과 같다.

#### D-1. 외화 승인과 취소가 승격일 환율로 각각 환산된다

- `apps/worker/src/promotion/fx-rate.service.ts:54-75`의 `getRateToKrw(currency)`는 거래일을
  받지 않고 `new Date()`의 서울 날짜를 캐시 키로 쓴다.
- `apps/worker/src/promotion/transaction-promotion.service.ts:301-330`은 승인과 취소 모두 이
  함수를 독립 호출한다.
- 취소 후보는 같은 원통화가 아니라 환산된 KRW 잔액으로 비교한다
  (`transaction-promotion.service.ts:523-570`).

USD 100 승인을 1달러=1,300원일 때 승격하면 130,000원이다. 같은 USD 100 전액취소를
1,400원일 때 승격하면 140,000원이 되어 `130000 >= 140000` 후보 조건을 통과하지 못한다.
취소는 미연결되고 130,000원 지출이 남는다. 취소 때 환율이 1,200원이면 연결되지만 10,000원이
남는다. 승격 시각이라는 가변 입력이 재시도 결과를 바꾸므로 PRD의 “계산은 LLM이 하지 않는다”보다
더 넓은 원칙인 **금액 계산은 결정적이어야 한다**는 조건도 위반한다.

#### D-2. 사람 검토 취소가 승인을 상계하지 않는다

- `apps/api/src/card-sms/card-sms-review.service.ts:216-248`은 검토 결과로 거래를 직접 삽입한다.
- 취소이면 `status='cancelled'`, `netAmount=0`, `parentTransactionId=null`인 독립 행만 만들고,
  자동 승격의 후보 탐색·연결·승인 잔액 갱신은 실행하지 않는다.
- 별도의 수동 연결 경로도 `apps/api/src/transactions/transaction.service.ts:855-928`에 다시
  구현돼 있어 취소 산술이 두 앱에 중복돼 있다.

승인 10,000원 뒤 3,000원 부분취소를 사람이 확정해도 승인 순액은 10,000원으로 남는다. 기대값은
7,000원이다. 전액취소 10,000원도 기대 순액 0원이 아니라 10,000원이 남는다.

#### D-3. 수동·검토 외화가 KRW 저장 계약을 우회한다

- `apps/api/src/card-sms/manual-entry.service.ts:223-238`은 입력 금액과 통화를 거래에 그대로
  넣고 `originalAmount`·`originalCurrency`·`exchangeRate`를 비운다.
- `apps/api/src/card-sms/card-sms-review.service.ts:229-236`도 같은 방식이다.
- 분석은 `apps/api/src/analytics/analytics.service.ts:486-500`에서 KRW만 포함한다.
- 가맹점 목록은 `apps/api/src/merchants/merchant.service.ts:47-63`에서 통화 구분 없이
  `netAmount`를 합치고, 계약은 이를 원 단위로 선언한다(`packages/contracts/src/merchant.ts:11-18`).

수동 입력한 USD 10.00은 `amount=1000,currency=USD`로 저장된다. 대시보드에서는 0원 기여지만
가맹점 화면에서는 1,000원처럼 보인다. 같은 거래의 금액 의미가 화면에 따라 달라진다.

#### D-4. 범용 파서가 거래 액션과 무관한 첫 금액을 고른다

- 범용 게이트는 본문 어딘가에 금액·액션·카드 문맥이 각각 있는지만 확인한다
  (`packages/card-parsers/src/parsers/generic.parser.ts:26-36,104-116`).
- 공통 금액 파서는 첫 `N원`을 선택한다
  (`packages/card-parsers/src/parsers/base.parser.ts:29-30,153-167,335-343`).
- 광고·혜택 문맥 배제와 액션-금액 span의 관계 검증이 없다.

`삼성카드 8/10 온라인 결제 시 5,000원 할인`은 5,000원 승인으로 승격될 수 있다.
`삼성카드 이용한도 1,000,000원 / 승인 10,000원`은 기대값 10,000원 대신 첫 토큰
1,000,000원을 고른다. 이는 환산 이전의 입력 자체가 잘못된 경우라, 저장 서비스만 공통화해서는
막을 수 없다.

### 2. 문제는 네 패치가 아니라 하나의 신뢰 경계다

금액은 다음 세 단계에서만 확정돼야 한다.

1. **증거 확정**: 자동 파싱은 원문에서 거래 액션과 금액 span의 관계를 결정적으로 입증한다.
2. **정규화**: 원통화 정수와 고정된 기준일을 불변 환율 스냅샷으로 KRW 정수에 변환한다.
3. **원장 반영**: 승인·취소 행과 승인 잔액을 하나의 DB 트랜잭션에서 멱등하게 기록한다.

현재는 워커 자동 승격, API 수동 입력, API 사람 검토, 거래 수동 연결·금액 수정·연결 취소가 각자
이 단계 일부를 소유한다. 새 진입점을 추가할 때 규약을 기억해서 복사하는 구조가 재발 원인이다.

### 3. 하나의 ADR로 묶는 이유

D-1~D-3은 동일한 쓰기 계약 우회다. D-4는 그 계약에 자동 입력을 넘기기 직전의 증거 게이트다.
둘을 별도 ADR로 승인하면 “저장 경로만 통합되고 잘못된 파서 금액은 계속 들어오는 상태” 또는
“파서는 안전하지만 사람 경로가 계속 우회하는 상태”를 정상 중간 상태로 오인할 수 있다. 따라서
하나의 종단 간 금액 계약으로 승인하되, 구현 경계는 **파서 증거 게이트**와 **금액 도메인 서비스**로
명확히 나눈다. 환율 공급자 교체나 파서별 문법 확장은 이 계약을 지키는 별도 후속 결정으로 둘 수
있다.

## 결정

### 1. 단일 `TransactionMoneyService`를 금액 쓰기의 유일한 초크포인트로 둔다

공유 도메인 패키지 `@family/transaction-domain`에 `TransactionMoneyService`를 둔다. API와
worker는 같은 구현을 가져다 쓰며 한 앱의 Nest 서비스에 다른 앱이 의존하지 않는다. 서비스는
호출자가 시작한 DB 트랜잭션도 받을 수 있어, 검토 라벨·원문 이벤트 갱신과 거래 반영을 원자적으로
묶을 수 있어야 한다.

서비스가 소유하는 명령은 다음과 같다.

- 승인 생성
- 취소 생성 및 자동 연결
- 사람이 선택한 승인에 취소 연결
- 금액·원통화·거래시각 수정에 따른 재정규화
- 연결된 취소 제거·연결 해제에 따른 승인 잔액 복원
- 마이그레이션용 승인-취소 체인 재계산

`amount`, `currency`, `originalAmount`, `originalCurrency`, `exchangeRate`, 환율 스냅샷,
`cancelledAmount`, 원통화 취소 누계, `netAmount`, `parentTransactionId`, 금액에서 파생되는
`status`는 이 서비스만 쓴다. 가맹점·카드·카테고리·공개범위 결정은 기존 서비스가 수행하되 완성된
메타데이터를 금액 명령에 넘긴다. 비금액 필드 수정은 기존 서비스에 남는다.

아키텍처 테스트는 `card_transactions`의 생성과 위 보호 컬럼 갱신이 이 패키지 밖에 남으면
실패해야 한다. 런타임 규약을 코드 리뷰 기억에만 맡기지 않는다.

### 2. 모든 생성 경로가 같은 명령과 불변식을 사용한다

진입점별 차이는 금액 계산이 아니라 출처뿐이다.

| 진입점 | 출처 증거 | 공통 서비스 동작 |
| --- | --- | --- |
| worker 규칙·레시피·LLM span | 원문 amount/action span과 파서 출처 | 검증 → 환산 → 승인/취소 반영 |
| API 수동 필드(v1은 approval만 지원) | 사용자가 명시한 원통화 금액·통화·거래시각 | 환산 → 승인 반영 |
| API 사람 검토 | 사람이 확정한 필드와 검토 라벨 | 환산 → 승인/취소 반영 |
| 거래 수정·취소 수동 연결 | 기존 거래 id + 사람이 바꾼 값/선택한 부모 | 체인 잠금 → 재계산 |

모든 생성 명령은 안정적인 멱등 키가 필수다. 현재 경로는 수동 입력이 먼저 만든 event를 포함해
`sourceEventId` UNIQUE를 사용한다. 취소 연결과 승인 잔액 갱신은 승인 행을 잠근 한 DB
트랜잭션에서 실행하며, 같은 취소 재시도는 승인 잔액을 두 번 줄이지 않는다. 서로 다른 부분취소가
동시에 오면 승인 원통화 잔액을 직렬화해 음수 잔액을 막는다. 부모를 바꾸는 재연결은 이전·새 부모
id의 오름차순으로 행을 잠가 교착과 이중 상계를 막는다.

연결된 체인의 금액·통화·거래시각 수정은 일부 행만 고치지 않고 체인 전체를 재계산한다. 새 값이
원통화 취소 누계를 승인액보다 크게 만들거나 승인-취소 통화를 다르게 만들면 수정 전체를 거부한다.
자동 연결 해제나 조용한 `pending_review` 전환은 하지 않는다. 사람이 부모를 바꾸려면 별도의 명시적
재연결 명령을 사용한다.

### 3. 환율 기준일을 입력으로 고정하고 스냅샷을 불변으로 저장한다

외화 승인 환율의 기준일은 서울 날짜의 `occurredAt`이다. 원문에 거래시각이 없으면 ADR-0026의
기간 근사와 같은 이유로 `receivedAt`을 사용한다. 선택한 기준 시각과 날짜는 명령 입력이며
`new Date()`나 승격 실행 시각을 금액 계산에 사용하지 않는다.

마이그레이션 `0049`부터 `fx_rate_snapshots`를 도입한다. 한 스냅샷은 최소한 원통화, KRW, 기준일,
고정 소수 환율, 공급자·공급자 버전, 금액 계약 버전, 취득 시각을 가진다. 같은
`(원통화, 기준일, 금액 계약 버전)`의 첫 성공 값을 불변으로 고정하고 모든 재시도가 같은 행을
참조한다. 금액 산술은 스냅샷의 고정 소수 값을 정수 산술로 반올림하며 기존
`double precision exchangeRate`는 호환 표시값이지 계산 원본이 아니다.

환율 단위는 **원통화 1 major unit당 KRW**이고, 스냅샷은 `numeric(24,12)`로 저장한다. 원통화
minor units가 `M`, ISO 4217 지수가 `e`, 12자리 정수 스케일 환율이 `R`이면 KRW는
`M × R / (10^e × 10^12)`를 **0.5 이상 올림(ROUND_HALF_UP)**해 구한다. 금액은 음수가 아닌
정수이고 계산 중간값은 bigint를 사용한다. API·worker·복구 작업이 이 한 함수를 공유해 1원 차이를
허용하지 않는다. 지원 통화의 지수는 한 ISO 매핑에서만 가져오며 통화나 지수를 모르면 환산하지
않고 검토로 보낸다.

환율 공급 실패 때 오늘 환율이나 날짜 없는 상수 폴백을 쓰지 않는다. 이미 고정된 스냅샷이 있으면
계속 사용하고, 없으면 이벤트를 재시도/검토 상태로 두어 거래를 만들지 않는다. 운영자가 승인한
대체 환율은 반드시 해당 기준일의 새 스냅샷으로 출처를 남겨야 한다. 가용성을 위해 조용히 다른
날짜의 금액을 쓰는 것보다 지연을 선택한다.

최초 스냅샷이 공급자 오류로 잘못됐음이 뒤늦게 확인돼도 행을 수정하지 않는다. 새 금액 계약 버전의
정정 스냅샷을 만들고 영향 거래를 감사 가능한 수리 배치로 재계산한다. 과거 결과를 같은 id 아래에서
바꾸지 않아 재시도 재현성을 지킨다.

새 KRW 승인은 취소 전 `amount=netAmount`, `currency='KRW'`로 만들고 원통화·환율 필드는
비운다. 이후 취소가 연결되면 §4의 공통 잔액 규칙으로 `netAmount`를 줄인다. 외화 승인은
`currency='KRW'`로 저장하고 원통화 minor units와 통화, 스냅샷을 함께 보존한다.

### 4. 외화 취소는 원통화에서 연결하고 승인 환율로 상계한다

자동 후보의 기본 조건은 모두 AND다: 같은 household, 같은 `cardId`(미연결이면 양쪽 모두 null),
같은 원통화, 승인시각이 취소시각보다 앞섬, 원통화 잔액이 취소액 이상이다. 승인번호가 있으면
정확히 같은 승인번호를 추가로 요구하고, 없으면 `merchantNormalized`가 양쪽에 있을 때 정확히
같아야 한다. 카드·시각·가맹점 증거가 빠졌다고 조건을 느슨하게 풀지 않으며 그 경우 사람 선택으로
보낸다. 이 필터 결과가 정확히 한 건일 때만 자동 연결한다. 외화 승인의 원통화 잔액은
`originalAmount - originalCancelledAmount`다. KRW 승인은 기존
`amount - cancelledAmount`를 쓴다. 유일한 후보만 자동 연결하고 0개 또는 여러 개면 취소 행을
`pending_review`로 남겨 사람이 원승인을 선택한다.

이때 행의 종류는 계속 `transactionType='cancellation'`이고 `status='pending_review'`는 연결 검토
상태다. 종류와 처리 상태를 한 값으로 합치지 않는다. 연결되면 취소 행 status를 `approved`로 바꾸고
부모 승인의 status를 원통화 잔액에 따라 `partially_cancelled` 또는 `cancelled`로 계산한다.

연결된 외화 취소는 취소일 환율을 쓰지 않고 승인에 저장된 환율 스냅샷을 재사용한다. 부분취소 후
KRW 순액은 “승인 원통화 잔액 × 승인 환율”에서 다시 유도하고, KRW 취소 누계는
`approval.amount - approval.netAmount`로 정한다. 이 방식은 부분취소별 반올림 순서와 무관하며
원통화 잔액이 0이면 `netAmount=0`, `cancelledAmount=amount`를 강제한다. 따라서 환율이 오르거나
내려도 원통화 전액취소는 정확히 0이다.

아직 연결되지 않은 외화 취소는 취소 기준일의 스냅샷으로 표시용 KRW 금액을 잠정 기록할 수 있지만
`netAmount=0`이고 집계에는 들어가지 않는다. 나중에 연결할 때 승인 스냅샷으로 금액·환율을
원자적으로 교체한다. 잠정값은 승인 후보 판정에 사용하지 않는다.

### 5. 자동 파서 금액은 거래 액션에 결박된 span이 있어야 한다

자동 파서 결과는 숫자만이 아니라 최소한 `amount span`, `action span`, 파서 출처를 금액 명령에
제공한다. span offset은 정규화본이나 byte가 아니라 저장된 `rawContent`의 JavaScript UTF-16 code
unit 기준 `[start,end)`이며 `slice(start,end)`가 실제 증거 문자열을 그대로 복원해야 한다. 사람의
수동 입력·검토는 명시적 사람 확정이 증거이므로 span이 없어도 된다.

범용 파서는 모든 금액 후보를 열거하고 줄·슬래시·파이프 단위의 거래 구간을 만든 뒤 다음 규칙을
결정적으로 적용한다.

1. `승인`·`취소`·`환불` 등 실제 거래 액션과 같은 구간에 있는 후보만 남긴다. **(→ 아래 §5-1 개정)**
2. `할인`·`혜택`·`쿠폰`·`이벤트`·조건형 `결제 시` 같은 판촉 구간과
   `이용한도`·`잔여한도`·`누적`·`누계`·`청구예정` 구간의 금액은 제외한다.
3. 유효 후보가 정확히 하나일 때만 확정한다. 0개 또는 여러 개면 임의로 첫 값을 고르지 않고
   현재 계층의 실패로 처리한다.

#### §5-1 개정 — 구간 결박은 2단계여야 한다 (shadow 측정 결과, 2026-08-08)

위 규칙 1을 **문자 그대로** 구현하면 한국 카드 문자의 지배적 레이아웃이 전부 탈락한다.
액션과 금액이 다른 줄에 있는 것이 정상이기 때문이다.

```
신한카드(1234)승인      ← 액션 구간
12,500원 일시불          ← 금액이 여기 있다
```

shadow 구현(`packages/card-parsers/src/action-amount.ts`)의 실측: 확정 38건 중
**Tier 1(액션과 같은 구간) 17건 / Tier 2(구간 밖) 21건**. 규칙 1만 인정하면
**정상 승인의 55%가 L0에서 떨어진다.** L1→L2로 내려가므로 즉시 오계산이 되지는 않지만,
LLM 호출량과 사람 검토 적체를 그만큼 늘리고 ADR-0023의 계층 설계 의도를 무너뜨린다.

따라서 규칙 1을 다음으로 대체한다.

1. **Tier 1** — 액션이 있는 구간 안의 유효 후보. 하나라도 있으면 여기서 확정하고 끝낸다.
2. **Tier 2** — **Tier 1이 비었을 때만**, 규칙 2로 실격되지 않은 전 구간의 유효 후보를 본다.

Tier 1이 비었을 때만 내려가는 것이 안전장치다. `이용한도 1,000,000원 / 승인 10,000원`은
Tier 1에서 `10,000원`이 잡히므로 한도액과 애초에 경합하지 않는다. 규칙 2(판촉·한도·누적 실격)와
규칙 3(유효 후보가 정확히 하나)은 **두 Tier 모두에 그대로 적용**된다.

금액 명령에 넘기는 증거에는 어느 Tier에서 확정됐는지를 포함한다. 6단계(게이트 활성화)에서
Tier별 오탐·미탐을 따로 측정해야 하기 때문이다.

> 이 개정은 설계 오류를 구현이 잡아낸 사례다. shadow 단계를 건너뛰고 곧바로 게이트를 켰다면
> 정상 승인 절반이 L0에서 탈락한 뒤에야 알았을 것이다.

전용 규칙 파서와 L1 레시피도 최종적으로 같은 span 불변식을 반환한다. ADR-0023의 L2 LLM은 이미
원문 quote만 지목하고 결정적 함수가 값을 계산한다. LLM이 금액·환율·후보 우선순위를 계산하게
하지 않으며, action span은 LLM 출력이 아니라 로컬 결정적 추출기가 확정한다. L0 실패는 L1→L2로
계속 내려가고, 어느 계층도 유효 증거를 만들지 못했을 때만 `quarantined`/사람 검토로 보낸다.

### 6. 기존 ADR과의 관계

- **ADR-0009**: 승인 `netAmount` 합과 취소 행 `netAmount=0`, 별도 취소 이력,
  `sourceEventId` 멱등을 유지한다. 취소 연결 비교 축을 환산 KRW에서 원통화 잔액으로 정교화하고,
  모든 경로가 같은 구현을 쓰도록 보강한다.
- **ADR-0023**: 규칙 → 레시피 → LLM span → 사람 검토 캐스케이드와 `quarantined` 게이트를
  유지한다. quote-grounded 원칙을 L0 범용 파서의 금액·액션 관계까지 확장한다.
- **ADR-0024**: `declined`는 계속 거래로 승격하지 않는다. 거절 문자의 금액 span은 가시성에
  활용할 수 있지만 금액 도메인 서비스의 거래 생성 명령을 호출하지 않는다.
- **ADR-0025**: 자산 이동 카테고리와 `notTransferCategory()`는 바꾸지 않는다.
- **ADR-0026**: 공식 지출 모집단
  (`approval + 미제외 + 비자산이동 + 집계통화 + 기간 + 공개범위`)과
  `pending_review`/`duplicate_suspected` 포함 결정을 바꾸지 않는다. 다만 잘못 저장된 행을
  바로잡으면 그 행의 KRW 값 또는 통화가 바뀌므로 총액은 의도적으로 달라질 수 있다.

## 데이터 마이그레이션 계획

### 1. `0049`은 추가형 스키마만 배포한다

기존 최신 마이그레이션은 `0048`이다. `0049`은 기존 동작을 즉시 바꾸거나 행을 삭제하지 않고
다음을 추가한다.

> **후속 마이그레이션 번호를 문서에 박지 말 것.** 실제로 이 ADR이 예약해 둔 `0050`을
> P0-9 수집 멱등(`0050_card_sms_idempotency_provenance`)이 먼저 가져갔다. 실재하는 파일이
> 우선이므로, 아래 단계들은 번호 대신 **역할**로 부른다.
>
> 이 ADR 초안은 `0046`이 최신이던 시점에 쓰였고, 같은 라운드의 보안·동시성 수정이 `0047`(장치
> 수집 자격·credential 부분 유니크)과 `0048`(가구 예산 부분 유니크)을 먼저 가져갔다. 여기 번호는
> 그에 맞춰 밀어 둔 것이며, **구현 착수 시점에 다시 확인해야 한다** — 그 사이 다른 마이그레이션이
> 들어오면 또 밀린다.

- 불변 `fx_rate_snapshots`
- `card_transactions.original_cancelled_amount`
- `card_transactions.fx_rate_snapshot_id`
- `card_transactions.money_contract_version`(기존 행은 v1, 새 계약은 v2)
- 배치·사유·대상 transaction id·보호 금액 컬럼의 before/after·현재 행 체크섬을 보존하는
  `transaction_money_repair_log`. 거래 제거가 필요하면 복원에 필요한 전체 거래 행·연결 관계·
  source event 상태의 before image도 함께 보존한다.

v2 불변식은 “모든 저장 통화 KRW”, “외화 원본이면 원통화·스냅샷 필수”,
“approval amount = cancelledAmount + netAmount”, “cancellation netAmount = 0”다. 처음에는
`NOT VALID` 또는 애플리케이션 검증으로 추가해 v1 행 때문에 배포가 막히지 않게 한다.

외부 환율 API 호출은 DB 마이그레이션 안에서 하지 않는다. 중단·재개 가능한 별도 복구 작업이
스냅샷과 수리 로그를 채운다.

### 2. 적용 전 읽기 전용 인벤토리와 dry-run을 만든다

수리 대상은 source event·검토 feedback·승인-취소 체인을 조인해 다음으로 분류한다.

| 분류 | 판별 예 | 처리 |
| --- | --- | --- |
| 자동 외화 v1 | `originalCurrency IS NOT NULL`이지만 거래일 스냅샷 없음 | 거래일 스냅샷으로 승인 체인 재계산 |
| 수동·검토 외화 우회 | `currency <> 'KRW'`이고 original/환율 없음 | 현재 금액·통화를 원통화로 승격해 KRW 환산 |
| 사람 검토 취소 미연결 | 검토 라벨은 cancellation인데 `parentTransactionId IS NULL` | 원통화 후보가 유일하면 연결, 아니면 검토 큐 |
| D-4 의심 | 다중 금액·판촉·한도·누적 문구이고 새 증거 결과가 기존과 다름 | 자동 삭제하지 않고 before/after와 원문 이벤트 id를 검토 큐에 기록 |

dry-run은 행을 바꾸지 않고 가구·월별 대상 건수, 이전/이후 공식 지출, 차이, 취소 연결 변화,
모호해 자동 처리하지 못한 건수를 출력한다. 원문·가맹점·금액을 운영 로그에 쓰지 않고 제한된
수리 테이블과 집계 수치만 사용한다.

### 3. 자동 수리는 결정적으로 재현 가능한 행만 가구 단위로 적용한다

각 가구에 advisory lock을 잡고 짧은 DB 트랜잭션에서 승인과 연결된 취소를 체인 단위로 처리한다.
dry-run 결과를 그대로 믿지 않고 적용 직전에 대상 행과 체크섬을 다시 읽어 새 거래·사용자 수정이
끼어든 manifest를 거부한다.

1. transaction id 순서로 before image와 체크섬을 수리 로그에 기록한다.
2. 기준일 스냅샷을 upsert하고 새 서비스의 `repair` 명령으로 체인을 재계산한다.
3. 합계 불변식과 원통화 잔액이 맞을 때만 같은 트랜잭션에서 v2로 표시한다.
4. 실패하거나 후보가 모호하면 전체 체인을 롤백하고 검토 대상으로 남긴다.

#### §3 구현 노트 — "재현 가능"을 가장 좁게 읽었다 (2026-09-03)

실행기(`repair.ts`)는 §3의 "결정적으로 재현 가능한 행만"을 **자동 적용은 금액을 한 원도
바꾸지 않는다**로 구현했다. 관찰기가 `match`나 `link_manual_only`를 낸 행에 필요한 것은
재계산이 아니라 **계약 버전 스탬프**뿐이다 — `after` 이미지가 `before`와 같고
`net_amount_delta`가 0이라, 위 회귀 기준("월 합계 차이 = 로그 delta 합")이 자명하게 성립한다.

`krw_amount_delta` · `fx_amount_delta` · `plan_failed` · `link_target_differs`는 **하나도
자동 적용하지 않는다.** manifest에 남겨 사람이 본다.

**`link_manual_only`가 이 구분을 만든 사례다.** 이 판정은 금액이 이미 맞지만 신규 규칙이
후보를 특정하지 못해 `planned.parentTransactionId`가 `null`이다. 계획을 곧이곧대로 적용하면
**사람이 한 연결이 끊긴다.** 그래서 auto 경로는 계획을 적용하지 않고 버전만 올린다 —
"재현 가능하다"와 "계획을 그대로 써도 된다"는 다르다.

적용은 행마다 짧은 트랜잭션에서 `FOR UPDATE` + 체크섬 재확인을 거치고, manifest가 낡았으면
그 행을 건너뛴다. 이미 v2인 행은 세기만 하므로 재실행이 안전하다(멱등).

**관문은 둘이어야 했다 (2026-09-03 실행이 교정한 것).** 첫 구현은 관찰기 판정만 보고
186건 전부를 auto로 분류했다. 적용 58번째 행에서 `card_transactions_v2_fx_snapshot_check`에
걸려 멈췄고, 앞선 57건은 이미 커밋된 뒤였다(행마다 별도 트랜잭션이라 롤백되지 않는다).

**`match`는 "새 계약이 같은 금액을 만든다"이지 "v2로 올려도 된다"가 아니다.** 스탬프는
행을 v2로 **선언**하는 행위라 §1의 v2 불변식을 통과해야 한다. 걸린 행은 외화인데 환율
스냅샷이 없는 경우 — 위 §2 분류표가 "자동 외화 v1"으로 이미 분류해 둔 유형이다. 분류표를
읽고도 관찰기 판정만으로 auto를 정한 것이 설계 오류였다.

그래서 `v2ConstraintViolations()`(`@family/database`)를 `0049`의 CHECK 6종과 1:1로 두고,
계획·적용 두 지점에서 본다. DB CHECK는 위반을 **막지만** 수리는 "어떤 행을 자동으로 올릴
수 있는가"를 적용 **전에** 알아야 한다 — DB에 물어보는 유일한 방법이 "UPDATE 해 보고
터지는지 본다"라면 그건 이미 반쪽 배치를 남긴 뒤다.

> 이것은 이 ADR이 기록하는 **두 번째 "구현이 설계를 교정한 사례"**다(첫 번째는 §5-1 개정).
> 두 번 다 같은 모양이다: 한 축만 보고 "안전하다"고 판단했고, 실행이 다른 축을 보여줬다.

D-4 과거 행은 새 파서가 다르게 판단했다는 이유만으로 소비를 삭제하지 않는다. 사람 검토에서
실제 거래와 올바른 금액을 확정한 뒤 같은 서비스로 수정한다. 광고 등 비거래로 확정된 행은 원문
이벤트를 `quarantined` 감사 근거로 남기고 거래 행을 제거하되, 제거 전 전체 행을 수리 로그에
보존한다. 이 단계가 끝날 때까지 “기존 D-4 수리 대기 건수”를 운영 지표로 노출한다.

### 4. 되돌림

`0049`은 추가형이라 코드 롤백 시 기존 앱이 새 컬럼을 무시할 수 있다. 금액 수리 배치는 batch id
단위로 역순 복원한다. 적용 후 사용자가 해당 거래를 수정하지 않았다면 체크섬을 확인하고 before
image와 원래 연결 관계를 그대로 되살릴 수 있다. 삭제한 D-4 행도 같은 id와 sourceEventId로
복원한다.

적용 후 사용자가 거래를 수정해 체크섬이 달라졌다면 자동 되돌림은 그 수정을 덮어쓰지 않고
중단한다. 이 경우 before/after와 현재값을 사람이 병합한다. 환율 스냅샷과 수리 로그는 롤백해도
삭제하지 않는다. 전체 수리가 검증되기 전에는 v1 컬럼이나 호환 읽기 경로를 제거하지 않는다.

### 5. VALIDATE 마이그레이션에서 v2 제약을 검증한다

모든 생성 경로가 v2를 쓰고 자동 수리·사람 검토 큐가 끝난 뒤 **VALIDATE 마이그레이션**에서 **v2 행에만 적용되는**
CHECK/FK를 VALIDATE한다. 롤백 창에는 컬럼 기본값을 v1으로 유지하고 새 서비스가 v2를 명시해서,
이전 바이너리로 돌아가도 조건부 v2 제약과 충돌하지 않게 한다. v1 행이 의도적으로 남으면 이유와
건수를 기록하고 강제 전환하지 않는다. 한 릴리스의 롤백 관찰 기간이 끝난 뒤 **별도 정리 마이그레이션**에서
기본값 v2 전환과 호환 경로 제거를 검토한다. VALIDATE 단계에서는 컬럼·로그·legacy 읽기 경로를 삭제하지
않는다.

## 회귀 테스트 전략

### 금액 도메인 단위 테스트

1. KRW 승인 10,000원은 `amount=netAmount=10000`, 환율 필드 없음.
2. USD 100 승인(승인일 1,300원)은 130,000원과 원통화 10,000 minor units를 보존.
3. 위 승인의 USD 100 전액취소는 취소일 환율이 1,400원·1,200원 어느 쪽이어도 승인 순액 0.
4. USD 30 부분취소 후 원통화 잔액 USD 70, KRW 순액 91,000원; 여러 부분취소를 합쳐
   USD 100이 되면 반올림 누적과 무관하게 0.
5. `occurredAt`이 없으면 고정된 `receivedAt` 서울 날짜를 사용하고 재시도 결과가 동일.
6. 이미 있는 스냅샷은 공급자 장애에도 사용하고, 스냅샷이 없으면 오늘 환율로 대체하지 않고 실패.
7. 환산 몫이 정확히 0.5원 경계일 때 API·worker·복구 작업이 모두 ROUND_HALF_UP으로 같은 값.
8. 승인 10,000원 + 사람 검토 취소 3,000원은 부모 연결, 승인 순액 7,000원.
9. 후보 0개/2개인 취소는 `pending_review`, 부모 승인 금액은 불변.
10. 같은 취소 재요청은 한 번만 상계되고, 동시 부분취소도 원통화 잔액을 초과하지 않음.
11. 연결·연결 해제·취소 제거·금액 수정 뒤 승인/취소 불변식이 모두 복원됨.

### 파서 테스트

1. `삼성카드 8/10 온라인 결제 시 5,000원 할인`은 approval 거래를 만들지 않음.
2. `삼성카드 이용한도 1,000,000원 / 승인 10,000원`은 10,000원 span을 선택.
3. 누적/누계가 앞·뒤에 있는 실제 승인 문자는 액션 구간 금액만 선택.
4. L0에서 유효 금액 후보가 둘이면 첫 값을 선택하지 않고 L1→L2를 진행하며, 끝까지 유효 증거가
   없을 때 `quarantined`.
5. 전용 규칙·레시피·LLM span이 같은 원문에서 같은 amount/action evidence를 산출.
6. declined는 사유·표시 금액을 보존하되 거래 생성 명령은 호출하지 않음.

### 경로·통합 테스트

1. 같은 원통화 입력을 자동 승격·수동 필드·사람 검토로 넣으면 출처 외 금액 컬럼이 동일.
2. 검토 라벨, 이벤트 상태, 거래 생성/취소 상계가 한 트랜잭션으로 함께 성공·실패.
3. API와 worker의 직접 `card_transactions` 금액 쓰기가 남지 않았음을 아키텍처 테스트로 확인.
4. 수동 USD 거래가 analytics·예산·가맹점 화면에서 같은 KRW 금액을 보임.
5. 수리 dry-run과 적용 후 차이가 수리 로그의 행별 delta 합과 일치하고, rollback 후 before와
   바이트 단위로 같은 보호 컬럼·연결을 복원.

### ADR-0026 무회귀 기준

공식 모집단 조건과 `pending_review`/`duplicate_suspected` 포함은 그대로 테스트한다.

**기준선은 `docs/money-contract-baseline-2026-08.md`를 쓴다** (2026-08-08 실측). ADR-0026이
박아 둔 2026-07 `812,414원/63건`은 **2026-08-06 시점 스냅샷이고 그 뒤 두 사건으로 데이터가
바뀌었다** — 사용자가 4건을 지출에서 제외(`−119,693원`), `충전소` 카테고리 규칙 수정으로
`transport` 2건이 자산이동에서 해제(`+60,000원`). 합 `−59,693원`이 현재값 `752,721원/61건`과
정확히 맞는다.

둘 다 **ADR-0027과 무관한 사건**이므로 옛 값에 억지로 맞추면 이 둘을 전환의 탓으로 잘못
귀속하게 된다. 다만 현재 데이터에서 `812,414원`이 **원 단위로 정확히 재구성된다**는 사실은
ADR-0026 집계 정의의 무회귀를 실증한다(재구성 절차는 기준선 문서에 있다).

기준선 문서의 값을 복제 DB의 golden fixture로 보존한다.

- 수리 대상이 없는 fixture에서는 두 기준값과 건수가 정확히 같아야 한다.
- 수리 대상이 있는 fixture에서는 차이가 `transaction_money_repair_log`의 승인
  `netAmount` delta 및 새로 KRW 정규화되어 모집단에 들어온 행의 합과 정확히 같아야 한다.
- 변경 후에도 analytics/monthly, transactions/summary, budgets spent가 같은 달에 일치해야 한다.
- 자산 이동, `excludedAt`, 기간 창, 공개범위 결과는 바뀌지 않아야 한다.

즉 **합계 정의는 무회귀**이고, 잘못된 금액 사실을 바로잡아 생기는 설명 가능한 delta만 허용한다.

## 롤아웃 순서

실서비스 중간 상태에서 새·옛 계약의 쓰기가 섞이지 않게 다음 순서를 지킨다.

1. **관측 기준 고정**: 배포 직전 읽기 전용 스냅샷에서 가구·월별 공식 합계, 외화·미연결 취소·
   D-4 의심 건수를 저장한다.
2. **`0049` 추가형 배포**: 스냅샷·v2 메타데이터·수리 로그만 추가한다. 사용자 동작은 불변이다.
3. **양쪽 앱 shadow 배포**: API와 worker 모두 새 서비스를 포함하되 기존 쓰기 결과와 새 명령의
   예상 결과만 PII 없이 비교한다. 파서 액션 게이트도 shadow로 오탐/미탐을 측정한다. retained
   카드문자 corpus를 전수 재생하고 live shadow를 최소 7일이면서 50건 이상 모은다. 기존 정상 KRW
   결과의 금액 delta 0건, 설명되지 않은 외화 delta 0건, 기존 정상 승인 신규 격리 0건,
   D-4 negative fixture 통과 100%가 전환 조건이다.
4. **공급자·dry-run 게이트**: 역사 환율 스냅샷의 날짜·재시도 안정성과 수리 manifest를 검토한다.
   설명되지 않는 월 delta가 하나라도 있으면 진행하지 않는다.
5. **쓰기 펜스 후 동시 전환**: 짧게 worker 승격 소비를 일시 정지하고 API 수동 입력·검토·금액
   수정/취소 연결을 503 또는 대기 상태로 막는다. API와 worker의 enforce 플래그를 모두 v2로
   바꾼 뒤 다시 연다. 한 경로라도 legacy인 동안 사용자 쓰기를 재개하지 않는다.
6. **파서 게이트 활성화**: 새 범용 파서는 유일한 action-grounded 금액만 L0 성공으로 인정한다.
   L0 실패는 L1→L2를 계속하고 최종 실패만 `quarantined`로 보낸다. 큐 적체와 정상 승인 미탐을
   관찰한다.
7. **기존 데이터 수리**: 가구 단위 작은 배치로 적용하고 매 배치 뒤 ADR-0026 세 경로 합계,
   원통화 잔액, 연결 무결성, 수리 delta를 확인한다. 실패 배치만 즉시 되돌린다.
8. **VALIDATE 검증**: 사람 검토 큐까지 비운 뒤 v2 제약을 VALIDATE하고 legacy 직접 쓰기를 탐지하는
   아키텍처 테스트를 필수화한다. DB 호환 컬럼·v1 기본값·롤백 플래그는 유지한다.
9. **롤백 창 종료**: 한 릴리스 동안 invariant 위반 0건, 설명되지 않은 월 delta 0건,
   24시간 넘은 금액 검토 적체 0건을 확인한 뒤에만 **정리 마이그레이션**으로 기본값 v2 전환과 호환 경로 제거를
   검토한다.

쓰기 펜스를 사용할 수 없는 배포 환경이면 이 전환은 진행하지 않는다. API와 worker를 순차로
enforce해 잠시라도 서로 다른 계약의 거래를 만드는 것은 허용하지 않는다. enforce 이후 금액
불변식 위반·설명되지 않은 delta·기존 정상 승인의 신규 격리가 한 건이라도 발생하면 쓰기 펜스를
다시 걸고 shadow 모드로 되돌린다.

## 결과

- 자동·수동·사람 검토가 같은 금액 표현과 취소 산술을 사용한다.
- 승격 실행일이나 재시도 시각이 환율을 바꾸지 않는다.
- 외화 전액취소는 환율 방향과 무관하게 승인 순액을 정확히 0으로 만든다.
- 잘못된 첫 금액은 자동 승격보다 복구 가능한 `quarantined`를 선택한다.
- ADR-0026의 지출 합계 정의는 유지되고, 데이터 수리로 달라진 총액은 행별 감사 로그로 설명·
  조건부 되돌림할 수 있다.

대가는 역사 환율 스냅샷 운영, 공유 도메인 패키지, 짧은 쓰기 펜스, 기존 데이터 검토 큐다. 정확한
금액을 즉시 만들 수 없을 때 거래 반영이 지연될 수 있으나, 조용히 틀린 지출을 확정하는 것보다
안전하다.

## 미해결·보류

- 역사 환율 공급자의 최종 선택, 라이선스·SLA·휴일/비영업일 기준은 공급자 평가 후 별도 결정한다.
  단, 어떤 공급자든 `(통화, 기준일, 계약 버전)` 불변 스냅샷 계약은 바꾸지 않는다.
- 카드사 매입 후 확정되는 실제 KRW 청구액과 추정 환율 금액의 조정 원장은 범위 밖이다. 확정 청구액
  수집 경로가 생기면 새 정정 이벤트로 다룬다.
- 승인번호가 없는 다중 취소 후보를 사람이 선택하는 UI와 승인번호 추출 확대는 후속 작업이다.
- PostgreSQL `integer` 범위를 넘는 통화 minor units 문제는 이번 P0와 별개다. `bigint`/`numeric`
  전환 ADR에서 다룬다.
- 가맹점 API의 공개범위·기간·자산이동 조건 누락은 이 ADR이 해결하지 않는다. 이 ADR은 통화 혼합
  합산만 원천 차단하며, 가맹점 집계 모집단은 별도 보안/집계 수정이 필요하다.
- 과거 D-4 의심 행은 기계적으로 전부 삭제하지 않는다. 사람 검토 큐의 운영 주체와 완료 기한을
  롤아웃 체크리스트에서 지정해야 한다.
