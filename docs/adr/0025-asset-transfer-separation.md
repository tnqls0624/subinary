# ADR-0025: 자산 이동을 지출에서 분리 — 카테고리 플래그 + 집계 초크포인트

## 제목

현금 인출·선불 충전처럼 **소비가 아니라 잔액을 옮긴** 거래를 지출 집계에서 제외한다.
새 `transactionType`이나 별도 테이블 대신 **카테고리에 `is_transfer` 플래그**를 두고,
집계 조건을 `notTransferCategory()` 헬퍼 하나로 공유한다.

## 상태

2026-08-04 설계·구현 완료. 마이그레이션 `0043`(`expense_categories.is_transfer`) +
시스템 카테고리 `transfer`(자산이동) 시드.

## 배경

프로덕션 실측(2026-08-04):

| 가맹점 | 금액 | 당시 카테고리 | 실제 성격 |
| --- | --- | --- | --- |
| ATM | 50,000 | 기타 | 현금 인출 = 자산 이동 |
| 모바일티머니선불 ×2 | 60,000 | **교통** | 선불 충전(사용 시점 다름) |

두 종류의 거래가 지출로 계상돼 있었다. 두 종류의 왜곡이 생긴다:

1. **총액 부풀림** — 현금을 뽑은 것은 아직 쓴 게 아니다.
2. **이중 계상** — 충전한 티머니를 실제로 쓸 때(교통 이용) 다시 잡힌다. `모바일티머니선불`이
   `티머니` 키워드에 걸려 교통비로 분류된 것이 특히 나쁘다 — 충전과 사용이 같은 카테고리에
   섞여 어느 쪽이 실제 소비인지 알 수 없다.

**토스페이 58,956원은 대상이 아니다.** 결제 대행일 뿐 실제로 어딘가에서 물건을 산 것이므로
소비다(사용자가 `쇼핑`으로 확정해 둔 상태). 초기 검토에서 168,956원으로 잡았다가 제외했다.

## 결정

### 1. 카테고리 플래그로 표현한다

세 가지 방법을 검토했다.

| 방법 | 문제 |
| --- | --- |
| `transactionType`에 `transfer` 추가 | 파서가 문자만 보고 판정해야 하는데, "ATM 출금"인지 "ATM 옆 가게 결제"인지는 가맹점명으로만 갈린다. 승격·취소연결·netAmount 규약이 전부 `approval`/`cancellation` 이분법에 묶여 있어 파급이 크다. |
| 별도 `asset_transfers` 테이블 | 같은 카드 문자에서 온 같은 형태의 데이터를 두 테이블에 나눠 쓰게 된다. |
| **카테고리 `is_transfer` 플래그** | 채택 |

판정 기준이 결국 **"이 가맹점이 무엇인가"** 이고, 그 판단 경로(키워드 규칙 → 사용자 확정 →
`merchant_category_rules` 자가학습)가 **이미 카테고리에 붙어 있다.** 새 축을 만들면 같은
판단을 두 곳에서 학습해야 한다. 사용자 입장에서도 별도 토글을 배우는 것보다 "카테고리를
자산이동으로 바꾼다"가 기존 조작과 일관된다.

시스템 카테고리 `transfer`(자산이동)를 `DEFAULT_CATEGORIES`에 추가하고, 시드는
`onConflictDoUpdate`로 `is_transfer`를 **동기화**한다 — 신규 삽입만 하면 이미 존재하는
카테고리에 플래그를 소급 적용할 수 없다. 시스템 카테고리는 사용자가 수정할 수 없으므로
(`category.service`가 403) 덮어써도 편집을 잃지 않는다.

### 2. 키워드 규칙을 목록 맨 앞에 둔다

`CATEGORY_KEYWORD_RULES`는 위에서부터 첫 매치가 이긴다. `모바일티머니선불`이 기존
`티머니 → transport`에 걸리므로, transfer 규칙(`선불`/`충전`/`atm`/`현금서비스`)이 **먼저**
와야 한다.

단, `충전소`(전기차·수소)는 실제 소비이므로 transfer보다 **더 앞에서** `transport`로
걸러낸다. 광범위한 키워드(`충전`)를 쓸 때는 예외를 앞에 두는 것이 순서 규약과 일관된다.

### 3. 제외는 "지출 합계"에만, 헬퍼 하나로

`isNull(excludedAt)`가 있는 지점을 전수 조사한 결과 **10곳**이며, 성격이 갈린다.

**제외 적용(6곳 — 지출 합계)**

| 지점 | 역할 |
| --- | --- |
| `analytics.service` `periodApprovalConditions` | monthly/categories/members/cards/merchants 공통 초크포인트 |
| `analytics.service` 권한제외 카운트 | 합계에 없는 행은 이 카운트에도 없어야 함(이중 집계 방지) |
| `budget.service` `computeSpent` | 예산 사용률 |
| `transaction.service` 요약 | `/transactions/summary` |
| `promotion.service` `budgetScopeSpent` | 예산 알림 임계 판정 |
| `notification-scheduler` 주간 요약 | 주간 소비 푸시 |

**제외 안 함(4곳)**

| 지점 | 이유 |
| --- | --- |
| 거래 목록 | 자산 이동도 목록에 보여야 한다(분류·수정 대상) |
| `merchant.service` 가맹점 목록 | ATM도 별칭 병합·정리 대상 |
| `notification-scheduler` 확인 리마인더 | 자산 이동도 검토 대상 |
| `transaction.service` 라벨 후보 | ATM을 `자산이동`으로 학습시키는 것이 곧 목적 |

조건은 `@family/database`의 `notTransferCategory()` 하나로 공유한다. `excludedAt`을 도입할
때 집계 지점마다 손으로 조건을 넣었고 "새 지점을 추가하면 조건도 넣어야 한다"는 규약이
사람의 기억에 의존하게 됐다. 이름 있는 함수면 grep 한 번으로 적용 여부를 확인할 수 있다.

`NOT EXISTS` 서브쿼리를 쓴다 — JOIN이나 `is_transfer = false` 비교로는 `categoryId`가
NULL(미분류)인 거래가 조용히 탈락한다. 미분류는 자산 이동이 **아니므로** 남아야 한다.

## 결과

- ATM 50,000 + 티머니선불 60,000이 지출·예산·주간요약에서 빠진다(이력은 보존).
- 사용자는 거래 상세에서 카테고리를 `자산이동`으로 바꾸면 되고, 별도 UI를 배울 필요가 없다.
- 새 집계 지점을 추가할 때 `notTransferCategory()` grep으로 누락을 잡을 수 있다.

## 남은 것 (비범위)

- **충전액의 실제 사용 추적**: 티머니 잔액을 어디에 썼는지는 카드 문자에 오지 않는다.
  충전을 지출에서 빼면 그 돈은 "어디에도 안 잡히는" 상태가 된다 — 정확하지만 불완전하다.
- **계좌 잔액/자산 관리**: 자산 이동의 반대편(계좌)을 모델링하지 않는다. 복식부기는 이
  앱의 범위가 아니다.
- **결제 대행 정산**: 토스페이 같은 대행은 실제 가맹점을 알 수 없어 소비로 둔다.

## 관련

ADR-0009(거래 모델·승격), ADR-0010(집계 SQL·예산), ADR-0019(가맹점 라벨 검토 경계),
ADR-0024(결제 실패 가시성 — 함께 배포). `excludedAt`(중복 제외, 마이그레이션 0011)과는
**직교하는 축**이다 — 중복은 "같은 결제가 두 번 잡혔다", 자산 이동은 "이건 소비가 아니다".
