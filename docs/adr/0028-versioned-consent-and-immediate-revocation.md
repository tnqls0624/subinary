# ADR-0028: 버전된 동의 + 즉시 철회 — 개인정보 Control Center 1단계

> ⚠️ ADR 번호는 같은 웨이브의 다른 작업과 충돌할 수 있다. 이 문서의 내용은 번호와
> 무관하므로, 충돌하면 파일명만 다음 번호로 바꾸면 된다(이 저장소에는 `0022`가 두 개
> 있는 선례가 있다).

## 제목

동의를 **버전된 append-only 이력**으로 다루고, 철회가 **실제로 수집을 멈추게** 한다.
보존정책 선택·원문 purge·데이터 내보내기는 **하지 않는다**.

## 상태

2026-08-09 설계·구현 완료. 마이그레이션 `0051`(`household_consents`에 상태 전이 컬럼).
격리 스택에서 철회 → 수집 401 실측 완료. **운영 미적용**(배포 절차에서 적용).

## 배경

로드맵 C-3의 문제 정의는 세 문장이었다.

> 가입 동의는 "공동 지출과 예산 열람"만 알린다. 어떤 문자 원문이 DB와 객체 저장소에
> 얼마나 남는지 설명하지도, 고르게 하지도 않는다. 동의 철회 표면도 없다(그리고
> 철회해도 P0-2 때문에 수집이 멈추지 않는다).

세 번째 문장이 핵심이었고, 그 원인은 **화면이 없는 게 아니라 모델이 철회를 표현하지
못한다는 것**이었다. `household_consents`는 `consentedAt`만 있고 취소를 적을 자리가
없었다. 철회 버튼을 붙이려면 스키마가 먼저였다.

괄호 안의 P0-2는 `0047`이 이미 해소했다(탈퇴 후 장치 자격 잔존 차단). 그래서 이제
철회가 실제로 동작할 수 있는 상태가 됐다.

## 결정

### 1. 철회는 삭제가 아니라 상태 전이, 재동의는 새 행

`household_consents`에 `status`(`granted`/`revoked`)·`revoked_at`·`revoked_reason`을
더한다. 철회는 기존 행을 `revoked`로 전이시키고, 재동의는 **새 행을 추가**한다.

- 덮어쓰지 않는 이유: 동의 이력 자체가 증빙이다. "언제 동의했다가 언제 철회했는가"를
  잃으면 개인정보 화면이 답할 수 있는 게 없어진다.
- `0047`이 장치·자격증명에서 삭제 대신 상태 전이를 택한 것과 같은 선례를 따른다.
- **재동의는 이전 granted 행을 revoked로 바꾸지 않는다.** 문구 개정은 철회 사건이
  아니고, 없던 철회를 기록하면 이력이 거짓말을 한다. 그래서 granted 행이 여러 개
  남을 수 있고, 현재 상태는 **"가장 최근 행"** 규칙 하나로 확정한다.

두 CHECK가 DB에서 불변식을 강제한다.

| 제약 | 막는 것 |
| --- | --- |
| `household_consents_status_check` | 어휘 밖 상태 |
| `household_consents_revoked_at_check` | "철회했다는데 언제인지 모르는 행" |

**부분 유니크(가구·사용자당 granted 1행)는 일부러 걸지 않았다.** 나갔다가 재합류하면
서로 다른 시점의 정당한 동의 행이 여러 개 생기고, 인덱스를 붙이려면 그 이력을 사람이
지워야 한다. "동의 이력을 지워야 제약이 붙는다"는 이 작업의 목적과 정면으로 충돌한다.
대신 철회가 살아있는 granted 행을 **전부** 전이시켜 잔여 granted를 남기지 않는다.

### 2. 문구 원문은 코드가 단일 출처

`@family/contracts`에 `CURRENT_HOUSEHOLD_CONSENT_VERSION` 상수와
`householdConsentDocuments` 레지스트리(버전 → 문구 전문)를 둔다. DB에는 버전 문자열만
남는다. 규칙은 하나다 — **문구를 고치면 버전을 올리고 이전 버전 문서를 지우지 않는다.**

- api(버전 기록)와 web(문구 표시)이 함께 의존하는 패키지가 contracts뿐이라 여기 둔다.
  서버가 `v2`를 기록하는데 화면은 `v1` 문구를 보여주는 어긋남을 타입으로 막는 것이 목적.
- `create()`·`acceptInvitation()`은 DB 기본값(`'v1'`)에 기대지 않고 현재 버전을
  명시적으로 박는다. 기본값에 기대면 문구를 개정해도 새 동의가 옛 버전으로 기록되어
  개정 자체가 무의미해진다.
- 동의 요청은 **클라이언트가 자기가 보여준 버전을 실어 보낸다.** 현재 버전이 아니면
  409다 — 캐시된 옛 화면의 동의가 최신 버전으로 기록되는 것을 막는다.
- 마이그레이션 `0051`은 레지스트리에 없는 `consent_version`이 DB에 있으면
  `RAISE EXCEPTION`으로 **멈춘다**(`0048`과 같은 태도). 원문을 되짚을 수 없는 행이
  하나라도 있으면 "무엇에 동의했는가"를 영영 말할 수 없기 때문이다.

문구는 `v1`(가족 열람만) → `v2`(가족 열람 + 문자 수집 + **원문 보관** + 철회)로 올렸다.
기존 행은 전부 `granted`로 백필하고 버전은 그대로 둔다 — 개정은 "재동의 요청"이지
"동의 취소"가 아니므로 수집이 끊기지 않고 화면이 안내만 한다.

### 3. 철회는 기존 초크포인트를 통과한다

```
revokeConsent()
  → (1) 내 활성 기기 전부 DeviceService.revokeDevice()   ← 기존 초크포인트 재사용
  → (2) 살아있는 granted 동의 행 전부 revoked로 전이
  → (3) 이후 새 기기 등록은 DeviceService.registerDevice()가 403으로 막는다
```

- **폐기 UPDATE를 새로 짜지 않는다.** 이 저장소는 "자동 경로만 계약을 구현하고 나중에
  붙은 사람 개입 경로가 각자 구현"한 사고를 금액 4건·visibility 5곳에서 반복했다.
  철회 경로를 새로 짜면 같은 병을 하나 더 만드는 것이다.
- **순서가 뒤집히면 안 된다.** 동의를 먼저 끊고 기기 폐기가 실패하면 "철회했는데 계속
  수집됨"이 되어 P0-2와 같은 사고다. 기기부터 끊으면 최악의 중간 상태가 "수집은 멈췄는데
  동의 표시가 아직 살아 있음"이라 사용자 피해가 없고 재시도로 수렴한다.
- (3)이 없으면 철회는 연극이다 — 사용자는 수집을 껐다고 믿는데 다음 기기 등록 한 번으로
  조용히 되살아난다. 판정은 화면·가드가 같은 함수(`household-consent.ts`)를 쓴다.
- 멤버십 제거(`removeMember`)도 같은 트랜잭션에서 동의를 `member_removed`로 전이시킨다.

**수집 가드(`DeviceTokenGuard`/`DeviceHmacGuard`) 자체에는 동의 조인을 넣지 않았다.**
장치 폐기가 이미 같은 트랜잭션에서 수집을 끊고, 가드는 문자 한 통마다 도는 경로라
"최신 동의 행" 서브쿼리를 매번 붙이는 비용이 정당화되지 않는다. 등록 차단이 우회 경로를
막으므로 현재 구조에서 동의 없는 수집이 성립하는 조합은 남지 않는다.

### 4. 보존은 **보여주기만** 한다

로드맵 5-1의 보류 사유를 그대로 존중한다.

> 법적 보관·삭제 요구가 관할·운영 정책 검토를 필요로 한다. 8주에 불완전하게 밀어 넣으면
> "지웠다고 했는데 남아 있다"가 되어 P0-2보다 나쁜 신뢰 사고가 된다.

그래서 화면은 **지금 무엇이 얼마나 보관돼 있는가**만 읽기 전용으로 보여준다: DB의 문자
건수·최초 수신일, 파일 저장소의 총 바이트와 경로 접두사. 선택지는 없다.

계약의 `retentionPolicySchema`는 값이 **`'none'` 하나뿐인 열거형**이다. 화면이 "N일 뒤
삭제"를 표시할 방법 자체가 타입에 없다 — 지키지 못할 약속을 코드로 막는다. purge 잡이
생기면 그때 값을 늘린다.

화면은 이렇게 말한다: *"동의를 철회하면 새 문자 수집은 즉시 멈추지만, 이미 보관된 문자
원문은 이 화면에서 지워지지 않아요."*

## 실측 (격리 스택 `-p fma-verify`)

이 작업에서 유일하게 증명이 필요한 주장은 "철회가 실제로 수집을 멈추는가"였다.
코드 독해가 아니라 실행으로 확인했다(30개 체크 전부 통과).

| 단계 | 결과 |
| --- | --- |
| 기기 등록 → 수집 POST | 200 accepted |
| **동의 철회** | 200, `revokedDeviceCount: 1` |
| **같은 토큰으로 수집 POST** | **401** |
| 철회 상태에서 새 기기 등록 | **403** |
| 옛 버전으로 동의 시도 | 409 |
| 재동의 → 기기 재등록 → 수집 | 200 / 201 / 200 |
| 폐기된 옛 수집 토큰 | 401 (되살아나지 않음) |
| 이력 | 2행(철회된 최초 동의 + 새 동의), `consentedAt`·`revokedAt` 모두 보존 |

CHECK 제약과 `RAISE EXCEPTION` 가드도 psql에서 직접 위반시켜 발화를 확인했다.

## 결과

- 철회가 표면과 모델 양쪽에서 실제로 존재한다. **되돌릴 수 있다**(재동의) — 되돌릴 수
  없으면 사용자는 무서워서 못 누른다.
- 동의 문구가 버전으로 추적되고, 개정 시 재동의를 **차단 없이** 요청한다.
- 사용자가 "지금 무엇이 보관돼 있는지"를 처음으로 볼 수 있다. 삭제는 약속하지 않는다.

## 남은 것 (다음 분기)

로드맵 5-1의 "Control Center 본체"가 그대로 남아 있다.

- 보존정책 선택 + 원문 purge 잡 + 삭제 이력 → `retentionPolicySchema`에 값을 늘리는 것이
  그 작업의 시작점이다.
- owner 데이터 내보내기 · 가족 그룹 삭제(PO B9) — 같은 데이터 모델을 쓰므로 함께.
- 사용자 문구의 법적 성격 검토. 지금 문구는 **서비스가 실제로 하는 일의 서술**이지
  법적 고지가 아니다.
