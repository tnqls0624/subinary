# 금액 계약 전환 기준선 — 2026-08-08

ADR-0027(단일 거래 금액 계약) 롤아웃 **1단계 "관측 기준 고정"**의 산출물이다.

ADR-0027의 전환 조건은 3·4단계 전부 **"delta 0건"** 형태다(`docs/adr/0027-single-transaction-money-contract.md:379-388`).
비교 대상 기준선이 없으면 전환 후 무엇이 바뀌었는지 증명할 수 없다. 이 문서는 전환 **직전** 운영
데이터의 상태를 고정하고, 각 숫자가 **어떤 정의로 계산됐는지**와 **전환 후 달라져도 되는지**를 함께
남긴다. 정의가 없는 숫자는 나중에 아무 의미가 없다.

## 측정 조건

| 항목 | 값 |
| --- | --- |
| 측정 시각 | 2026-08-08 (Asia/Seoul) |
| 대상 | 운영 DB `family_memory` (컨테이너 `family-memory-ai-postgres-1`) |
| 모집단 | household 1개 · 구성원 2명 · `card_transactions` 127행 · `card_sms_events` 139행 |
| 측정 시점 저장소 HEAD | `21dd400` |
| 재현 명령 | `node scripts/snapshot-money-baseline.mjs --twice` |
| 본문 해시 | `sha256:807f53a506f0ee59` (측정 시각을 담지 않으므로 데이터가 같으면 값도 같다) |

수집은 **읽기 전용**이다. 프로브가 모든 조회를
`set transaction isolation level repeatable read, read only` 트랜잭션 안에서 돌리고, 수집을 시작하기
전에 무해한 `where false` UPDATE를 시도해 PostgreSQL이 SQLSTATE `25006`으로 거부하는 것을 매 실행
증명한다. 운영 컨테이너 파일시스템에는 아무것도 쓰지 않는다(`docker cp` 없이 stdin 주입).

지출 합계는 SQL을 새로 쓰지 않고 `packages/database/src/query-helpers.ts`의
`spendPeriodWindow`·`notTransferCategory`를 **호출**해서 구했다. 정의가 갈라지는 것이 ADR-0026이
막으려던 문제 자체이기 때문이다.

## 1. 가구·월별 공식 지출

**정의**: ADR-0026 공식 모집단 6조건 —
`householdId` + `transactionType='approval'` + `excludedAt IS NULL` + `notTransferCategory()`
+ `currency='KRW'` + `spendPeriodWindow(from,to)`. 합계 컬럼은 `netAmount`.
**status 조건은 없다** — `pending_review`/`duplicate_suspected`도 합계에 포함한다(검토 플래그일
뿐이라 제외하면 과소집계가 된다).

| 월 | 건수 | 순지출 | 승인액 | 취소액 |
| --- | ---: | ---: | ---: | ---: |
| 2026-03 | 2 | 1,338원 | 1,338원 | 0원 |
| 2026-07 | 61 | **752,721원** | 881,721원 | 129,000원 |
| 2026-08 (8일까지) | 51 | 1,086,819원 | 1,086,819원 | 0원 |

> 월 버킷은 Asia/Seoul 기준이다. `spendPeriodWindow`는 `approvedAt`이 있으면 그것을, 없으면
> `createdAt`을 쓴다. 같은 값을 analytics `months()`의 `to_char(coalesce(approved_at, created_at)
> at time zone 'Asia/Seoul','YYYY-MM')` 그룹핑으로도 따로 계산해 **3개 버킷 전부 일치**를 확인했다.
> 두 경로가 갈라지면 그 자체가 발견이므로 스크립트가 매 실행 교차검증한다.

**전환 후 판정: `무회귀`.** ADR-0027은 "합계 정의는 무회귀"라고 못박았다. 이 표의 값이 달라진다면
`transaction_money_repair_log`의 행별 delta 합으로 정확히 설명되어야 하며, 설명되지 않는 1원 차이도
버그다.

### 1d. 공식 합계 분해

**정의**: 공식 합계 = `전체 KRW 승인 − 제외분(excludedAt IS NOT NULL) − 자산이동분(is_transfer)`.
delta가 생겼을 때 요인을 귀속시키기 위한 축이다.

| 월 | 전체 승인 | 제외분 | 자산이동분 | = 공식 |
| --- | ---: | ---: | ---: | ---: |
| 2026-03 | 2건 1,338원 | 0건 0원 | 0건 0원 | 1,338원 |
| 2026-07 | 69건 943,002원 | 7건 140,281원 | 1건 50,000원 | 752,721원 |
| 2026-08 | 51건 1,086,819원 | 0건 0원 | 0건 0원 | 1,086,819원 |

제외가 적용된 시각 — 전환 delta를 **사용자 행위**와 구분하는 축:

| 거래 월 | 제외된 날 | 건수 | 순액 |
| --- | --- | ---: | ---: |
| 2026-07 | 2026-07-17 | 1 | 52원 |
| 2026-07 | 2026-07-18 | 1 | 52원 |
| 2026-07 | 2026-07-31 | 1 | 20,484원 |
| 2026-07 | 2026-08-06 | 4 | 119,693원 |

**전환 후 판정: `무회귀`(전체 승인·자산이동분) / `사용자 행위에 따라 변동`(제외분).**
사용자는 언제든 거래를 제외할 수 있다. 제외분이 늘어난 것은 전환의 문제가 아니다 — 그래서 제외
시각을 함께 남긴다.

## 2. 외화 인벤토리

**정의**: `card_transactions`의 통화 관련 컬럼 상태. ADR-0027 D-1(승격일 환율)과 D-3(KRW 저장 계약
우회)의 현재 노출 규모다.

| currency | 종류 | 건수 | 순액 |
| --- | --- | ---: | ---: |
| KRW | approval | 126 | 2,181,124원 |
| KRW | cancellation | 1 | 0원 |

| 항목 | 건수 | 정의 |
| --- | ---: | --- |
| KRW 아닌 통화로 저장된 행 (**D-3**) | **0** | `currency <> 'KRW'`. 수동·검토 경로가 원통화를 그대로 저장한 행 |

| 원통화는 있는데 환율 결측 | 0 | `original_currency IS NOT NULL AND exchange_rate IS NULL` |
| 원통화는 있는데 원금액 결측 | 0 | `original_currency IS NOT NULL AND original_amount IS NULL` |

D-1 후보 1건의 내역: `original_amount=2200`, `original_currency='USD'`,
`exchange_rate=1486.949463`, `amount=32713`, 거래일 2026-07-20.

**D-3가 현재 0건인 것은 "코드 경로가 안전하다"는 뜻이 아니다.** `manual-entry.service.ts:223-238`과
`card-sms-review.service.ts:229-236`은 여전히 입력 통화를 그대로 저장한다. 사용자가 아직 외화를 수동
입력하지 않았을 뿐이다. 0을 기준선으로 고정해 두면 전환 전에 D-3 행이 새로 생기는 것을 즉시 잡을 수 있다.

**전환 후 판정: D-3·결측 항목은 `감소 기대(0 유지)`. D-1 후보 1건의 KRW 값은 `설명 가능한 delta 허용`**

`transaction_money_repair_log`의 해당 행 delta와 정확히 일치해야 한다. 이 1건은 2026-07 공식 합계에도
포함되므로 **2026-07 총액이 이 delta만큼 움직이는 것은 허용**된다.

## 3. 미연결 취소 (D-2)

**정의**: `transaction_type='cancellation' AND parent_transaction_id IS NULL`.
사람 검토 경로가 취소를 확정해도 부모 승인에 연결하지 않아 생기는 행이다
(`card-sms-review.service.ts:244`가 `parentTransactionId: null` 고정).

| 항목 | 값 |
| --- | ---: |
| 취소 행 전체 | 1건 |
| 부모 미연결 | **0건 / 0원** |

유일한 취소 행(2026-07-22, 129,000원)은 부모에 정상 연결돼 있고 워커 자동 승격이 만든 것이다.

**D-3와 마찬가지로 0건이 "안전하다"는 뜻은 아니다.** 사람 검토로 취소를 확정한 사례가 아직 없을 뿐,
코드 경로는 그대로다.

**전환 후 판정: `감소 기대(0 유지)`.** 전환 후 이 값이 0보다 커지면 회귀다.

## 4. D-4 의심 후보

**정의**: 범용 파서가 거래 액션과 무관한 금액을 골랐을 가능성이 있는 승격 건.
`card_transactions.source_event_id → card_sms_events.raw_content`를 조인해 판정한다.
**확정이 아니라 후보 집계**다.

| 판정 | 건수 | 기준 |
| --- | ---: | --- |
| 강한 의심 | **0** | 첫 금액 토큰의 **인접 문맥**(앞 12자~뒤 8자)에 판촉/한도 토큰이 있고 그 값이 실제로 채택됨 |
| 약한 의심 | **46** | 채택 지점은 깨끗하나 원문에 금액 토큰이 2개 이상이고 판촉/한도 문맥이 따로 있음 |
| 원문에 `N원` 토큰 없음 | **5** | 원문에 `N원` 패턴이 없는데 승격됨(외화 표기 `USD 22.00`·수동 입력 합성 이벤트) |
| 비거래 문맥 승격 | **3** | 원문에 `출금\|입금\|이체\|송금` 문맥이 있는데 `approval`로 승격됨 |

판촉/한도 토큰: `할인|혜택|쿠폰|이벤트|결제 시|이용한도|잔여한도|누적|누계|청구예정`.
스캔 대상은 승인 126건 전부.

### 이 기준을 왜 이렇게 잡았는가

처음에는 ADR-0027 §5의 문구를 그대로 옮겨 **"원문 어딘가에 판촉/한도 토큰이 있고 첫 금액 토큰을
채택"** 으로 쟀다. 승인 126건 중 **46건(37%)** 이 걸렸다. 원인은 `누적`이었다 — 42건이 여기 걸린다.
카드 문자는 관용적으로 문자 **끝**에 "누적 N원"을 붙이고, 첫 금액 토큰은 멀쩡한 승인액이다.
실제로 첫 금액 토큰이 속한 구간의 형태를 뽑아 보면 `N원 일시불`(80건), `N원 결제`(35건)처럼 전부
정상이었다.

**"원문 어딘가"는 신호가 아니다.** D-4의 실제 실패 모드는 *채택된 금액 자체가 판촉/한도 문맥에
들어 있는 것*이다(`삼성카드 이용한도 1,000,000원 / 승인 10,000원`). 그래서 판정을 **채택 지점의
좁은 인접 창**으로 좁혔고, 그 결과 강한 의심이 0건이 됐다. 46건은 "지금은 우연히 맞았을 뿐
ADR-0027 §5가 요구하는 결정적 근거는 없는" 구조적 위험으로 남겨 약한 의심에 두었다.

`base.parser.ts:30`의 `AMOUNT_RE`가 비-global `match`라 **첫 매치를 무조건 채택**하는 것이 이 판정의
전제다.

**전환 후 판정: `감소 기대`.**
- 강한 의심 0건은 **유지**되어야 한다.
- 약한 의심 46건은 새 파서가 action-grounded 근거를 요구하면 **분류가 바뀔 뿐 금액은 그대로여야
  한다**. 이 46건의 금액이 하나라도 달라지면 ADR-0027 롤아웃 3단계의 "기존 정상 KRW 결과의 금액
  delta 0건" 조건 위반이다.
- 새 파서 게이트가 이 46건 중 일부를 `quarantined`로 보내면 "기존 정상 승인 신규 격리 0건" 조건
  위반이므로 게이트를 되돌려야 한다.
- **비거래 문맥 3건과 `N원` 토큰 없음 5건은 별도 조사 대상**이다(아래 "후속 확인 필요" 참조).

## 5. 취소 연결 무결성 · v2 불변식 사전 위반

**정의**: ADR-0027이 `0050`에서 VALIDATE할 v2 불변식을 지금 데이터에 미리 적용한 결과.

| 항목 | 건수 | 정의 |
| --- | ---: | --- |
| 자식 취소를 가진 승인 | 1 | 참고값 |
| `cancelled_amount` ≠ 자식 취소 `amount` 합 | **0** | 승인의 취소 누계와 실제 자식 행이 어긋난 경우 |
| 승인 `net_amount` ≠ `amount − cancelled_amount` | **0** | ADR-0009 순액 규약 위반 |
| 취소 `net_amount` ≠ 0 | **0** | 취소 행은 순액 0이어야 한다 |
| `currency` ≠ KRW | **0** | v2 "모든 저장 통화 KRW" 위반 |
| 음수 금액 | **0** | `amount`/`net_amount`/`cancelled_amount` 중 음수 |
| 취소-승인 통화 불일치 | **0** | 연결된 취소와 부모 승인의 통화가 다름 |

**전환 후 판정: `감소 기대(전부 0 유지)`.** 하나라도 0보다 커지면 즉시 쓰기 펜스를 걸고 shadow로
되돌려야 한다(ADR-0027 롤아웃 마지막 문단).

## 6. ADR-0026 기준값과의 대조 — 조사 결과

ADR-0026은 2026-08-06 측정으로 2026-07을 **`812,414원 / 63건`** 으로 박아 두었다
(`docs/adr/0026-single-spend-aggregation-contract.md:23-37`).
현재 값은 **`752,721원 / 61건`** — **Δ −59,693원 / −2건**이다.

7월은 닫힌 달이므로 이 차이는 반드시 설명되어야 한다. **전부 설명된다.**

| 단계 | 건수 | 금액 | 근거 |
| --- | ---: | ---: | --- |
| 2026-07 전체 KRW 승인 | 69 | 943,002원 | 현재 실측. 이 값 자체는 변하지 않았다 |
| − 2026-08-06 **이전**에 제외된 3건 | −3 | −20,588원 | 제외 시각 7/17·7/18·7/31 |
| = 자산이동 포함 합계 | **66** | **922,414원** | ADR-0026 본문의 괄호 수치와 **정확히 일치** |
| − 당시 자산이동 3건 | −3 | −110,000원 | 현재 자산이동 1건 50,000원 + 아래 재분류된 2건 60,000원 |
| = **재구성된 ADR-0026 값** | **63** | **812,414원** | 기준값과 **정확히 일치** |

즉 Δ −59,693원은 두 요인의 합이다.

1. **−119,693원 / −4건** — 2026-08-06에 사용자가 4건을 지출에서 제외했다(`excluded_at`).
   ADR-0026 측정보다 나중에 일어난 **사용자 행위**다.
2. **+60,000원 / +2건** — 2026-08-06 23:39~23:40에 `transport` 30,000원 2건이 자산이동에서
   빠져나왔다. 두 행의 `updated_at`이 그 시각이고, 이는 `packages/shared/src/categorization.ts:78`의
   `{ keyword: '충전소', slug: 'transport' }` 규칙이 적용된 결과다 — 전기차·수소 충전소는 실제
   소비이므로 `충전` 키워드의 `transfer` 매칭보다 먼저 걸러야 한다는 **카테고리 규칙 수정**이다.

`−119,693 + 60,000 = −59,693`. 건수도 `−4 + 2 = −2`로 맞는다.

### 판단: 이번 기준선은 812,414원이 아니라 **752,721원**을 쓴다

ADR-0026 값은 그 시점 데이터의 스냅샷이고, 그 이후 사용자 행위와 카테고리 규칙 수정이라는
**ADR-0027과 무관한 두 사건**이 데이터를 바꿨다. 억지로 812,414에 맞추면 그 두 사건을 전환의 탓으로
잘못 귀속하게 된다.

**더 중요한 결론**: 위 재구성이 원 단위로 정확히 맞는다는 것은 **ADR-0026의 집계 정의가 무회귀임을
실증**한다. 정의가 흔들렸다면 66건/922,414원이라는 중간값이 재현되지 않았을 것이다. 전환 후에도 같은
재구성이 가능해야 한다.

## 7. 알려진 한계 — 이 문서의 숫자를 읽을 때 반드시 함께 볼 것

### 승격 경로 식별은 간접 신호다

`card_transactions`에 `source`·`parser_tier`·`created_via` 류 컬럼이 **없다**. 따라서 §2의 경로
분포는 조인으로 근사한 값이며 다음 한계가 있다.

- **파서 티어(L0 규칙 / L1 레시피 / L2 LLM span)는 영속되지 않는다.**
  `apps/worker/src/processors/card-sms-parse.processor.ts:141`의 `parseSource`는 지역 변수이고
  로그에만 남는다. **"이 거래를 어느 계층이 만들었나"를 SQL로 물을 방법이 지금은 없다.**
- **`manual_text`(문자 붙여넣기) 6건은 신뢰도가 낮다.** 판별이 `registered_devices.name = '수동 입력'`
  이라는 문자열에 의존하고, `sender`는 사용자가 덮어쓸 수 있다(`manual-entry.service.ts:99-106`).
  이 경로는 이후 워커 승격을 타므로 자동 경로와 사실상 구분되지 않는다.
- **`worker_auto` 115건은 소거법**이다. 위 셋에 걸리지 않은 나머지일 뿐이다.

ADR-0027이 `0049`에 추가하기로 한 `money_contract_version`은 **계약 버전이지 승격 경로가 아니다.**
ADR-0027 §데이터 마이그레이션 계획의 분류표(자동 외화 v1 / 수동·검토 외화 우회 / 사람 검토 취소
미연결 / D-4 의심)를 SQL로 뽑으려면 위 간접 신호에 계속 의존해야 한다. **`0049`에 경로·티어 컬럼
(예: `card_sms_events.parse_source`)을 함께 넣는 편이 나은지 2단계 담당이 판단해야 한다.**

### `visibilityScope`는 주 수치에서 뺐다

actor에 따라 결과가 달라지므로 기준선이 될 수 없다. §1c의 visibility 분해로 대신했고, actor별 화면
값이 필요하면 그 분해에서 재구성한다.

### 0건 항목은 "안전"이 아니라 "아직 발생하지 않음"이다

D-2(미연결 취소)와 D-3(비KRW 저장) 모두 현재 0건이지만 **코드 경로는 그대로 열려 있다.**
`manual-entry.service.ts`·`card-sms-review.service.ts`는 여전히 `TransactionMoneyService`를 거치지
않는다. 이 0을 고정해 두는 이유가 그것이다 — 전환 전에 새 행이 생기면 즉시 드러난다.

### 후속 확인 필요 (이번 라운드 범위 밖)

- **비거래 문맥 승격 3건** — 원문이 `공룡통장 모임통장에서 N원이 출금됐어요` 형태인데 `approval`로
  승격됐다. `generic.parser.ts:51`의 `NON_CARD_RE`에 `출금`이 있는데도 통과한 경로를 확인해야 한다.
  ADR-0027 §5 규칙 1(실제 거래 액션과 결박)의 위반 후보다. 이 중 일부는 자산이동으로 분류돼 공식
  합계에서 이미 빠져 있다.
- **원문에 `N원` 토큰 없음 5건** — 외화 표기(`USD 22.00`)와 수동 입력 합성 이벤트가 섞여 있다.
  §5의 amount span을 만들 근거가 원문에 없는 축이므로 파서 게이트 담당이 분류해야 한다.

## 재현 방법

```bash
node scripts/snapshot-money-baseline.mjs             # 사람이 읽는 표
node scripts/snapshot-money-baseline.mjs --json      # 원시 JSON
node scripts/snapshot-money-baseline.mjs --twice     # 재현성 검증(2회 대조)
node scripts/snapshot-money-baseline.mjs --out baseline.json
```

진단 로그는 stderr, 리포트/JSON은 stdout으로 나가므로 리다이렉트로 그대로 파일에 담을 수 있다.
스크립트는 다음을 매 실행 자동 확인한다.

1. 읽기 전용 가드 실증 (SQLSTATE `25006`)
2. `spendPeriodWindow` 순회 = analytics `to_char` 그룹핑 교차검증
3. ADR-0026 고정 기준값 대조 + 불일치 시 요인 분해 출력
4. (`--twice`) 두 실행 결과 해시 일치

관련: ADR-0009(거래 모델), ADR-0023(파싱 캐스케이드), ADR-0026(지출 합계 단일 정의),
ADR-0027(단일 거래 금액 계약).
