# 다음 기능 기획 — 카테고리 교정 수고 줄이기

> 작성 2026-08-19. 실측 기반. 선행: ADR-0019(가맹점 라벨 검토 경계) · ADR-0026(단일 지출 집계).

## 0. 한 줄

같은 가맹점을 **네 번까지 다시 고치고 있다.** 규칙은 만들어지는데 **과거에는 적용되지 않기 때문**이다.

---

## 1. 실측 — 문제는 분류 정확도가 아니다

운영 데이터(승인 186건, 2026-08-19 읽기 전용 조회):

| 지표 | 값 | 읽는 법 |
|---|---|---|
| 자동분류 결과 | `etc` 20건(10.7%) · 미분류 2건 | **자동분류는 잘 돌고 있다** |
| 사람 교정 | **110회 / 93거래** | 전체 거래의 **절반**을 손으로 고쳤다 |
| 생성된 규칙 | 86개(human 84 · model 2) | 고칠 때마다 규칙은 만들어진다 |
| 교정한 가맹점 | 82개 — 그중 **규칙 보유 82개** | 규칙이 있는데도 계속 고쳤다 |
| 같은 거래 재교정 | 15건 (최대 **3회**) | 한 거래를 세 번 고친 적이 있다 |
| 가맹점 별칭 | 2개 | 병합 도구는 거의 안 쓴다 |

**같은 가맹점을 반복 교정한 상위:**

```
모바일티머니선불   4회 / 3거래
쿠팡               4회 / 3거래
브루다여의도백상   3회 / 1거래   ← 거래 하나를 세 번
커피온리샛강역사   3회 / 1거래   ← 거래 하나를 세 번
씨제이올리브영     2회 / 2거래
지에스25 영등포도림 2회 / 2거래
```

**"4회 / 3거래"가 이 기획의 전부다.** 쿠팡 거래가 이미 3건 쌓인 상태에서 하나를 고치면 규칙이 생기지만 나머지 2건은 그대로다. 그래서 나머지도 하나씩 또 고친다.

## 2. 원인 — 코드가 그렇게 하겠다고 적어 뒀다

```
 * Changing `categoryId` with `applyRule` upserts a `merchant_category_rules`
 * entry `(householdId, merchantNormalized) → categoryId` so *future*
 * promotions/reclassifications pick it up (never retroactive).
   — apps/api/src/transactions/transaction.service.ts:612-614
```

`never retroactive`는 **의도된 안전장치**다. 규칙 하나가 과거 수백 건을 조용히 재분류하면 지난달 통계가 사용자 모르게 바뀐다 — D-3(예산 소급 변경)이 정확히 그 병이었다.

그러나 그 안전장치가 **대안 없이** 놓여 있다. 사용자에게 남은 선택지는 "하나씩 다 고치기"뿐이고, 실측이 보여주듯 실제로 그렇게 하고 있다.

**빠진 것은 소급 적용 자체가 아니라, 소급을 사용자가 보고 결정할 방법이다.**

### 곁가지 관찰: 규칙 86개를 볼 화면이 없다

`merchant_category_rules`를 조회하는 웹 화면이 0개다(`/transactions`가 쓰기만 한다). 무엇이 자동으로 붙고 있는지 사용자가 확인·수정·삭제할 수 없다. "한 거래를 세 번 고침"의 일부는 여기서 온다 — 왜 자꾸 그 카테고리가 붙는지 알 수 없으니 다시 고쳐 보는 것이다.

## 3. 설계 결정

| # | 결정 | 이유 |
|---|---|---|
| **D1** | 규칙 저장 시 **"과거 N건에도 적용할까요?"** 를 제안한다. 기본값은 **적용 안 함** | 소급은 사용자가 **보고** 결정할 일이지, 시스템이 조용히 할 일이 아니다 |
| **D2** | 제안에는 **영향 건수·기간·금액 합계**를 함께 보여준다 — "쿠팡 3건 · 7/12~8/14 · 46,800원" | 되돌릴 수 없는 것에 대한 최소 예의(ADR-0027 4단계에서 쓴 것과 같은 원칙) |
| **D3** | 소급 적용은 **되돌릴 수 있다.** 한 번의 적용을 batch로 묶어 기록하고 "되돌리기"를 제공한다 | 15건이 재교정된 이력이 말해준다 — 사람은 분류를 바꿨다가 되돌린다 |
| **D4** | **금액 컬럼은 건드리지 않는다.** 카테고리만 바꾼다 | ADR-0026 총지출 정의를 우회하는 새 쓰기 경로를 만들지 않는다 |
| **D4-1** | ⚠️ **구현이 교정함(2026-08-20)**: "카테고리만 바꾸니 총액 불변"은 **조건부로 거짓**이다. `expense_categories.is_transfer`가 다른 카테고리로 옮기면 자산이동은 지출 합계에서 빠지므로(ADR-0025) **그 달 총지출이 실제로 변한다.** 미리보기가 `transferBoundaryCrossed`로 이 경우를 분리하고 화면이 다른 문장으로 경고한다 | 조용히 진행하면 무회귀 DoD가 실패하고, 사용자는 "카테고리만 고쳤는데 총액이 왜 바뀌었지"를 겪는다 |
| **D5** | **category 스코프 예산이 걸린 달은 경고한다** | 과거 달의 카테고리를 바꾸면 그 달 예산 달성률이 바뀐다. D-3(과거 예산 소급 변경)을 다른 문에서 재현하지 않는다 |
| **D6** | 규칙 목록 화면을 연다 — 조회·수정·삭제·우선순위 | 무엇이 자동으로 붙는지 볼 수 없으면 사용자는 계속 "다시 고쳐" 본다 |
| **D7** | 별칭 병합(P1-17)이 `human_confirmed` 규칙을 지우지 않게 고친다 | 별칭 2개뿐인데도 이미 알려진 결함이다. 규칙을 신뢰 자산으로 만들려면 먼저 닫아야 한다 |

## 4. 범위 — 3 슬라이스

### S1. 소급 적용 제안 (M) — 본체 ✅ 구현됨(2026-08-20)

- 거래 수정에서 카테고리를 바꾸고 `applyRule`을 켜면, **같은 canonical 가맹점의 다른 거래 수**를 세어 제안
- `GET /v1/merchants/{canonical}/recategorize-preview` — 건수·기간·합계·영향 받는 달
- `POST /v1/merchants/{canonical}/recategorize` — batch id를 만들고 일괄 적용
- **DoD**: ① 총지출 무변화(`scripts/snapshot-money-baseline.mjs` delta 0), ② 미리보기 건수 = 실제 적용 건수, ③ 타인 `private` 거래는 세지도 바꾸지도 않는다

### S2. 되돌리기 + 적용 이력 (S) ✅ 구현됨(2026-08-20)

- `category_recategorize_batches`(batch id · 가맹점 · 이전/이후 카테고리 · 건수 · 실행자 · 시각)
- 거래별 이전 카테고리를 batch에 저장해 정확히 복원
- `/more/merchants`에 최근 적용 이력 + 되돌리기
- **DoD**: 되돌린 뒤 카테고리 분포가 적용 전과 완전히 일치

### S3. 규칙 목록 화면 + P1-17 (M) ✅ 구현됨(2026-08-20)

- `/more/category-rules` — 규칙 86개 조회·수정·삭제, 출처(사람/모델) 표시
- 규칙 하나에서 바로 "과거에도 적용" 실행
- P1-17: 별칭 병합이 `human_confirmed`를 남기고 `model_prediction`만 정리하도록 수정
- **DoD**: 별칭 병합 후에도 사람이 만든 규칙 0건 유실

## 6. 리스크

| 리스크 | 대응 |
|---|---|
| **소급이 총지출을 바꾼다** | D4 — 카테고리 컬럼만 UPDATE. 기준값 스크립트로 전후 delta 0 확인 |
| 과거 예산 달성률이 바뀐다 | D5 — 영향 받는 달에 category 예산이 있으면 미리보기에 경고. ADR-0030 월 원장이 이미 달별로 분리해 뒀다 |
| 타인 private 거래를 건드린다 | 공용 헬퍼(`visibilityScope`) 통과 강제 + member 계정 자동 검사(P0-6 재발 방지) |
| 대량 UPDATE가 잠금을 오래 잡는다 | 가구당 거래가 수백 건 규모다. 한 트랜잭션으로 충분하되 상한을 두고 초과 시 거부 |
| 되돌리기가 최신 수정을 덮어쓴다 | 되돌릴 때 `previous_category_id`와 **현재 값이 batch 적용값과 같은 행만** 복원 |

## 7. 하지 않는 것

| 항목 | 이유 |
|---|---|
| 자동 소급(제안 없이) | D1 — 조용한 재분류는 D-3과 같은 신뢰 사고다 |
| 카테고리 구조 개편(대분류·소분류) | custom 2개뿐이다. 수요가 확인되면 그때 |
| LLM 분류 정확도 개선 | 실측상 자동분류는 이미 잘 된다(`etc` 10.7%). 문제는 정확도가 아니라 **반복 노동**이다 |
| 별칭 병합 UX 개선 | 별칭 2개 = 거의 안 쓴다. P1-17 결함만 닫고 표면은 그대로 둔다 |

## 8. 구현이 설계를 교정한 것 (2026-08-20)

| 기획 | 구현에서 드러난 사실 | 결과 |
|---|---|---|
| "카테고리만 바꾸니 총액 불변"(D4) | `is_transfer` 경계를 넘으면 **총지출이 실제로 변한다** | `transferBoundaryCrossed`를 계약에 추가, 화면이 다른 문장으로 경고 |
| from 카테고리 = 단일 값 | 대상들의 현재 카테고리가 **제각각(일부 NULL)** 이다 | batch에 단일 `from` 컬럼을 두지 않고 **items에 행별로** 이전 값 저장 |
| "같은 canonical 가맹점" | `merchant_normalized` 등호 비교로는 별칭 미적용 경로(수동 입력·검토 확정)로 들어온 거래가 빠진다 | 대상 판정을 `merchant_raw` **재해석** 기준으로(공유 resolver 통과), 원문 없는 수기 거래만 저장값 사용 |
| 예산 경고 = `category` 스코프만 | `is_transfer`가 바뀌면 **네 스코프 전부** 영향 | 경계를 넘는 경우 모든 스코프를 경고 대상으로 |
| 예산 경고 = boolean | 그 달에 예산 행이 **없으면** "영향 없음"이 아니라 "판단 근거 없음" | `budgetAffected`와 `budgetKnown`을 분리(0054 규약과 같은 원칙) |
| 규칙 목록만 보여주기 | 목록만으로는 "그래서 과거는 어떻게 되어 있나"에 답하지 못한다 | 규칙마다 `staleTransactionCount`를 함께 내보내고, 0건이면 버튼을 띄우지 않는다 |

### 재사용으로 막은 세 번째 사본

학습 revoke 연쇄(dataset snapshot → training run → evaluation → alias → canary)가 이미
두 곳에 복사돼 있었다. 소급 적용이 세 번째 사본을 만들면 다섯 테이블 중 하나를 빠뜨린
사본이 조용히 남는다 — 그래서 `@family/database`의 `revokeMerchantRuleLineage`로 추출하고
기존 호출부(`transaction.service.ts`)도 그것을 부르게 바꿨다.
